## 1. 옛 LLM 게이트웨이 지원 범위 (2026-07-28)

**목적**: 임베딩 API를 쓸 수 있는지 확인. 안 되면 pgvector 계획 전체를 다시 짜야 했다.

| 엔드포인트 | 결과 |
|---|---|
| `POST /v1/chat/completions` | HTTP 200 |
| `POST /v1/embeddings` | **HTTP 200** · `text-embedding-3-small` · **1536차원** |

**결론**: 임베딩 지원됨. pgvector 컬럼은 `vector(1536)`으로 잡는다.

**주의**: 프로토타입 단계의 임베딩 실측(메모리·속도·쿼리 적중률)은 전부 **BGE-m3(1024차원)** 기준이라 그대로 쓸 수 없다. 관련성 품질은 `text-embedding-3-small`로 다시 재야 한다.

**한글 인코딩**: 페이로드를 UTF-8 바이트로 보내면 한글이 정상 왕복한다(`"성수동 카페거리..."` → `"성수동, 서울숲"`). 중간에 깨져 보였던 것은 Windows 콘솔(cp949)과 Git Bash의 인라인 인자 처리 문제였고 API 문제가 아니었다. FastAPI는 기본이 UTF-8이라 구현에서는 문제되지 않는다.

## 2. ★ 생성 모델 비교 — `gpt-4.1-mini` vs `gpt-5-nano` (2026-07-28)

**방법**: 실제 태깅 시나리오(인스타 본문 → 태그 + `has_actionable_content`)를 **동일한 프롬프트로** 두 모델에 넣고 비교.

**응답은 완전히 동일했다:**
```json
{"tags": ["성수동 카페거리", "브런치 맛집", "어니언 성수", "대림창고", "자그마치"],
 "has_actionable_content": true}
```

| | `gpt-4.1-mini` | `gpt-5-nano` |
|---|---|---|
| 응답 품질 | 동일 | 동일 |
| completion_tokens | **45** | **1,398** |
| └ 그중 reasoning(사용자에게 안 보임) | **0** | **1,344** |
| 소요 시간 | **2.2초** | **11.2초** |

**결론**: `gpt-4.1-mini`로 확정. `gpt-5-nano`는 추론 모델이라 결과가 같아도 숨은 토큰을 태우고 5배 느리다. 태깅은 사용자가 스피너를 보며 대기하는 화면(S-25-C)이라 11초는 이탈 구간이다.

> **⚠️ 이 결론은 뒤집혔다 (2026-07-28 당일).** 두 가지가 빠져 있었다 — ① **크레딧 단가**를 아예 재지 않았다 ② "사용자가 대기하는 화면"이라는 전제가 실제 주력 경로(URL 공유 = `@Async`)에서 틀렸다. **태깅은 `gpt-5-nano` 유지**로 확정됐다. 아래 [#7](#7--동일-워크로드-재비교--gpt-41-mini-vs-gpt-5-nano-2026-07-28)을 함께 볼 것. 위 토큰·시간 측정 자체는 유효하다.

**한계**: 프롬프트 1개, 각 1회 측정. 소요 시간에는 네트워크 변동이 섞여 있다. 다만 `reasoning_tokens`는 모델 구조에서 나오는 값이라 재측정해도 크게 달라지지 않는다.

## 7. ★ 동일 워크로드 재비교 — `gpt-4.1-mini` vs `gpt-5-nano` (2026-07-28)

**배경**: #2는 짧은 인스타 본문 하나로 잰 것이었다. 실제 저장된 자료(네이버 블로그, 8,823자)로 다시 쟀다. 그리고 **#2에는 크레딧 축이 아예 없었다.**

**방법**: DB의 `archive_items` id=1 본문을 그대로 사용. 두 모델에 **동일한 시스템 프롬프트·동일 입력**.

| | 입력 | `gpt-4.1-mini` | `gpt-5-nano` |
|---|---|---|---|
| 태그만 (현재 운영 형태) | 4,000자 | 1.91초 · 2,634 tok | 5.07초 · 3,223 tok |
| 제목+태그+요약 (통합) | 8,823자 | 4.54초 · 6,034 tok | **22.74초** · 9,469 tok |

통합 호출에서 `nano`의 completion 3,636 토큰 중 **3,456개가 reasoning**(사용자에게 안 보임).

**품질 차이(관측)**: `nano`가 제목을 중간에서 잘랐다.
```
mini : 부산여행 2박 3일 코스 추천 : 부산여행지도+직접 가본 맛집 15곳 주관적 정리
nano : 부산여행 2박 3일 코스 추천 : 부산여행지도+직접 가본 맛집 15곳 주      ← 절단
```
태그도 `mini` 5개 / `nano` 4개.

**결론 두 가지.**
1. **총 토큰은 `nano`가 1.2~1.6배 더 쓴다.** 게이트웨이 대시보드의 "1회 평균 3.0 vs 10.0 크레딧"(3.3배)은 **짧은 입력·짧은 출력 기준**이라 우리 워크로드(입력 거대·출력 극소)에 그대로 적용되지 않는다. 정확한 값은 대시보드 크레딧 차감으로 확인해야 한다.
2. **"태깅은 사용자 대기 화면"이라는 #2의 전제가 틀렸다.** URL 공유 등록은 `@Async`라 사용자를 붙잡지 않는다(`ArchiveCrawlProcessor:43`). 22.74초도 목록에 빈 카드가 그만큼 떠 있을 뿐이다. 동기인 경로는 앱 내 등록과 텍스트 공유뿐.

**한계**: 자료 1건, 각 1회. `nano`의 고유명사 보존은 **재지 않았다** — 추천에 쓸지 판단하려면 평가셋 15개로 따로 재야 한다.

## 8. 자료 요약 통합 호출 (2026-07-28)

**목적**: 요약을 별도 호출로 붙일지, 태깅 호출에 합칠지.

`gpt-4.1-mini` · 같은 본문 기준.

| | 시간 | prompt | completion |
|---|---|---|---|
| 요약만 · 4,000자 | 5.1초 | 2,610 | 163 |
| 제목+태그+요약 · 4,000자 | 3.62초 | 2,657 | 179 |
| 제목+태그+요약 · 전체 8,823자 | 4.1초 | 5,834 | 202 |

**결론 1 — 통합이 사실상 공짜다.** 태그만 받던 것에 제목·요약을 얹는 비용은 prompt +47 tok, completion +16 tok. 별도 호출을 추가하면 LLM 호출이 2회가 되지만 통합하면 1회 그대로다. (시간이 3.62초로 요약 단독보다 짧게 나온 건 네트워크 변동으로 본다 — 1회 측정이라 단정하지 않는다.)

**결론 2 — 4,000자 자르기가 손해다.** 전체를 넣은 쪽이 제목이 깨끗하고("경상도" 네비 부스러기 없음) 본문의 "맛집 15곳"을 포착했다. 시간 차이는 0.5초.

**결론 3 — 요약의 진짜 값어치는 추천 비용이다.** 추천은 아카이브 전체를 프롬프트에 넣는다.

| 자료 20건을 프롬프트에 넣을 때 | 토큰(추정) |
|---|---|
| 본문 그대로 (실측 5,834 tok/건) | 약 117,000 |
| 요약만 (약 130 tok/건) | 약 2,600 |

**주의**: 요약은 원문의 재진술이라 **원문 문자열 대조로는 검증할 수 없다.** 환각 대응 방법을 따로 정해야 한다.

## 9. 제목 추출에 AI는 불필요 (2026-07-28)

공유 등록에서 제목이 URL로 남는 문제(`title = https://m.blog.naver.com/...`)를 AI로 풀지 검토했다.

같은 페이지에서 실제로 뽑히는 값:

```
og:title  = 부산여행 2박 3일 코스 추천 : 부산여행지도+직접 가본 맛집 15곳 주관적 정리
AI 생성   = 부산여행 2박 3일 코스 추천 : 부산여행지도+직접 가본 맛집 15곳 주관적 정리
```

**문자열까지 동일하다.** LLM 호출 0회로 해결된다.

원인은 AI가 아니라 서버 코드다 — 동기 경로는 `title = crawled.title()`을 쓰는데(`ArchiveItemService:109`), 비동기 경로는 body/source/thumbnail만 반영하고 title을 빠뜨린다:

```java
// ArchiveCrawlProcessor.java:53
item.markCrawlDone(crawled.bodyText(), crawled.source(), crawled.thumbnail());
```

`<title>`에는 ` : 네이버 블로그`가 붙으므로 **`og:title` 우선, 없으면 `<title>`** 순서가 낫다. 사용자가 제목을 직접 고친 경우엔 덮어쓰지 않아야 한다(`specs/0014` "수정 가능").

## 10. ★ 옛 LLM 게이트웨이의 구조화 출력 지원 확인 + 추천 1회 실측 (2026-07-29)

**목적**: 추천 착수 전 최대 리스크였던 것 — `#1`에서 게이트웨이는 `chat/completions`와 `embeddings`만 확인했고,
**구조화 출력(function calling / json_schema)이 프록시를 통과하는지는 재본 적이 없었다.** 안 되면
프롬프트로 JSON을 강제하고 손으로 파싱 + 재시도하는 폴백을 만들어야 했다.

**방법**: `langchain-openai`의 `ChatOpenAI(...).with_structured_output(SuggestionResponse, include_raw=True)`로
`base_url`만 게이트웨이로 돌려 실제 호출. 자료 2건(오픽 공부법 / 시험장 후기)이 든 요청.

**결과: 통과.** Pydantic 모델로 파싱된 응답이 그대로 돌아왔다 — **폴백은 만들지 않는다.**

| | 값 |
|---|---|
| 모델 | `gpt-4.1-mini` (잠정 기본값) |
| 자료 | 2건 |
| prompt_tokens | **1,078** |
| completion_tokens | **192** (그중 reasoning **0**) |
| 소요 시간 | 7.4초 / 8.5초 (2회) |

`reasoning_tokens`가 0인 것은 `#2`에서 잰 `gpt-4.1-mini`의 성질과 일치한다.

**품질(관측)**: 후보 7개 전부 원문에 실제로 있는 내용이었고 `source_item_id`도 정확히 갈렸다
(공부법 4건 → id=12, 시험장 후기 3건 → id=15). **고유명사 손상 없음** — "강남 시험센터"가 그대로 유지됐다.
기존 투두("교재 사기")는 다시 제안되지 않았다.

**⚠️ 관측된 편향 — 새 카테고리를 만들지 않는다.** 후보 7개가 전부 기존 카테고리 `공부`로 갔다.
시험 당일 준비(신분증·도착시간)는 별도 카테고리가 자연스러운데도 그렇다. 프롬프트 규칙 4의
"기존 카테고리를 우선한다"가 세게 먹은 것으로 보이는데, `full_spec.md` S-16-B는 **새 카테고리 제안도**
요구한다.
→ **지금 프롬프트를 고치지 않는다.** 규칙 하나를 더해 한 케이스를 잡으려다 다른 케이스를 깨뜨린
전례가 있다(`ai/CLAUDE.md` 규칙). 무엇을 잴지 정한 뒤에 재본다.

**한계**: 자료 2건·1개 프롬프트·2회 측정. 토큰 수는 자료 개수에 비례해 늘어난다 —
`#8`의 요약 도입 근거(자료 20건 = 본문 약 117,000 tok)가 그대로 유효하다.

## 11. 에뮬레이터 E2E 실측 — 실제 크롤링 본문 토큰량 + 프롬프트 캐시 통과 (2026-07-29)

**목적/방법**: 앱(에뮬레이터) → Spring → FastAPI → 게이트웨이 전 구간을 실제 UI로 2회 호출.
자료 3건은 사용자가 공유하기로 등록한 **실제 크롤링 본문**(부산 여행 관련) — 실험용 짧은 자료가 아니다.

| | 1회차 | 2회차 |
|---|---|---|
| prompt_tokens | 20,372 | 20,372 |
| completion_tokens | 261 | 259 |
| cache_read | 0 | **20,224** |

- **실제 본문은 자료당 약 6.8k tok** — [#10](EXPERIMENTS.md)의 실험 자료(2건 = 1,078 tok)보다 자료당 12배 크다.
  자료 3건에 이미 20k. [#8](EXPERIMENTS.md)의 요약 도입(20건 기준 45분의 1 압축)이 **예상보다 시급하다.**
- **OpenAI 프롬프트 캐싱이 게이트웨이 프록시를 통과한다.** 같은 방을 다시 호출하면 프롬프트의 99%가
  캐시 읽기로 잡혔다. 자료가 변하지 않는 한 재호출(같은 후보 재생성 포함)의 실질 비용이 크게 준다.
- **품질(관측)**: 후보 8개 전부 원문 근거 있음. 그중 1개가 새 카테고리(`맛집`)를 생성 —
  [#10](EXPERIMENTS.md)에서 관측된 "새 카테고리를 만들지 않는 편향"의 **반례**다. 단발 관측 두 개가
  서로 반대이므로, 프롬프트 규칙 4를 손대는 판단은 역시 평가셋 없이는 못 한다.

**캐시 무효화 조건(같은 날 추가 관측)**: 자료를 3건 → 4건으로 늘리자 `cache_read`가 **0으로 떨어졌고**,
같은 4건으로 다시 호출하니 22,739 중 22,528(99%)이 다시 잡혔다. 프롬프트 접두사가 바뀌면 캐시가 끊긴다는
뜻이다 — **아카이브에 자료를 담을 때마다 그 방의 캐시는 리셋된다.** 캐시 이득은 "자료가 고정된 동안의
반복 호출"에서만 나온다.

**한계**: 방 1개·자료 3~4건·소수 회차. 응답 시간은 이번에 재지 않았다(로그에 시각만 남음).

## 12. ★ 크롤링 본문 추출 정제 — 정제 전/후 (2026-07-29)

**목적/방법**: `JsoupUrlCrawler`가 `doc.body().text()`로 페이지 전체를 공백 하나로 이어붙이고 있었다.
이 문자열이 태깅·요약·추천 세 프롬프트의 입력이므로, 노이즈 제거 후 문자 수를 실제 URL로 나란히 쟀다.
측정은 운영과 같은 조건(`followRedirects(false)`)으로 돌렸다.

| URL | 정제 전 | 정제 후 | 비고 |
|---|---|---|---|
| 위키백과 Kotlin | 28,520 | 24,518 | `main` 1개가 body의 99.9% |
| MDN `<article>` | 9,563 | 3,860 | `main` 1개가 body의 99.1% |
| spring.io 블로그 | 3,384 | **1,148** | `<article>` 3개(카드 UI) — 아래 참고 |
| m.blog.naver.com ×2 | 1,820 / 3,612 | 1,728 / 3,507 | 5% / 2.9% |

- **⚠️ `selectFirst("article")`은 함정이다.** 첫 구현이 그랬는데, spring.io는 목록 카드마다 `<article>`을
  쓰기 때문에 **92자짜리 홍보 카드**가 본문으로 선택돼 본문 3,384자가 통째로 날아갔다(body 대비 7.4%).
  → 고친 방법 둘: ① 후보 중 **텍스트가 가장 긴 것**을 고른다 ② 후보가 (노이즈 제거 후) body의 **50% 미만**이면
  셀렉터가 헛짚은 것으로 보고 body를 쓴다. 정상 케이스는 99% 이상이라 두 무리가 멀리 떨어져 있다.
  가드가 걸렸을 때의 결과는 "덜 걷어낸 body"이므로 틀려도 본문을 잃지 않는다.
- **실사용 워크로드(모바일 네이버 블로그)에서 토큰 이득은 사실상 없다** — 3~5%. 모바일 네이버 페이지는
  원래 잡음이 적다. **이 변경의 실질 가치는 토큰이 아니라 "한 줄로 뭉개진 텍스트가 문단으로 나뉜 것"**이다.
- **네이버 블로그 PC 주소는 본문이 0자다.** `blog.naver.com/{id}/{logNo}`는 `iframe` 껍데기이고 본문은
  `PostView.naver`에 있다(5,428 / 7,228자). 제목도 `og:title`이 **블로그 이름**이지 글 제목이 아니다.
  **정제 이전부터 그랬다**(정제 전 값도 0). 모바일 공유는 `m.` 주소로 오므로 실사용 경로는 무사하다.
- **클라이언트 렌더링(SPA) 상용 사이트도 본문이 0자다** *(2026-08-01, agoda 호텔 상세 — 사용자 실사용 제보)*.
  위 네이버 케이스와 **원인은 다르지만 결과가 같다** — iframe이 아니라 애초에 HTML에 글자가 없고 JS가 그린다.
  같은 User-Agent(`Mozilla/5.0 (compatible; ModiArchiveBot/1.0)`)로 실측:

  | 항목 | 값 |
  |---|---|
  | HTTP 상태 | **200** (차단·리다이렉트 아님 — 403이나 3xx를 의심하면 헛짚는다) |
  | HTML 크기 | 315KB |
  | `og:title` / `<title>` | 없음 / 빈 문자열 → `toCrawlResult`가 `title = url`로 폴백 |
  | `<body>` 길이 | 192KB |
  | **스크립트 제거 후 텍스트** | **0자** → `본문을 찾을 수 없는 링크예요` → `FAILED` |

  재현: `curl -A "Mozilla/5.0 (compatible; ModiArchiveBot/1.0)" '<url>'` 후 `script/style/noscript/iframe`
  블록을 지우고 태그를 걷어내 길이를 센다(`JsoupUrlCrawler.NOISE_SELECTOR`와 같은 조작).
  → **헤드리스 브라우저 없이는 해결되지 않는다.** 메타태그로 제목·썸네일만 채우는 우회도 여기선 안 먹힌다(메타태그가 없다).
  지금 방침은 `FAILED`로 두고 앱이 그 사실을 정직하게 말하는 것이다(`specs/0014` 상태 표).
- **리다이렉트가 조용히 빈 본문을 만든다.** spring.io는 308, MDN은 301을 돌려주는데 Jsoup은 3xx를 에러로
  보지 않아 예외 없이 빈/스텁 본문으로 `DONE` 저장된다. `specs/0010`은 "리다이렉트 미추종 → 크롤링 실패로
  처리"라고 적혀 있어 **스펙과 구현이 어긋나 있다**(위 표의 spring.io·MDN 수치는 리다이렉트를 따라간
  하네스로 잰 값이라 운영과 다르다 — 운영 조건에서 유효한 것은 위키백과와 네이버 모바일뿐이다).

**리뷰에서 잡힌 것 (같은 날 수정)**:
- `header`/`footer`를 위치 무관하게 지우면 `<article><header><h1>글 제목</h1></header>`이 통째로 사라진다.
  기존 `body().text()`에는 남아 있던 정보이고, **태깅 프롬프트에 들어가는 건 `bodyText`뿐이라 제목이 AI 입력에서도 빠진다.**
  → `article`/`main` 바깥의 것만 제거하도록 고쳤다.
- **비율 가드는 댓글이 긴 블로그에서 사실상 꺼진다.** 본문 42%(기사 + 긴 댓글) 페이지가 body로 폴백했다.
  위 "실사용 이득 3~5%"의 원인 중 하나일 수 있다 — 다음 라운드에서 볼 것.

**⚠️ 알려진 한계 — `<pre>` 코드블록 서식이 이번 변경으로 오히려 뭉개진다**:

| | 결과 |
|---|---|
| 기존 `body().text()` | `fun main() {\n    println(1)\n}` (개행·들여쓰기 보존) |
| 새 `blockText` | `fun main() { println(1) }` (한 줄) |

Jsoup의 `text()`는 `<pre>`를 `preserveWhitespace`로 예외 처리하는데 `blockText`에는 그게 없고, 있더라도
`normalize`의 `[^\S\n]+`가 다시 뭉갠다. **"LLM 입력이라 문단 경계가 의미를 가진다"는 이 변경의 명분이 코드 블록에서는
반대로 작동한다.** 개발 블로그를 많이 담게 되면 실질 손실이므로 그때 고친다 — 지금은 손이 꽤 가서 미뤘다.

**한계**: 5개 URL. 한국어 블로그는 네이버 2건뿐이고 티스토리·브런치는 재지 않았다.

**원인이 하나로 모인다: 원문에 병기된 주소·날짜·기관명을 그대로 베껴 넣는다.** 장소명만 나열된

### ⚠️ 그래서 프롬프트를 지금 고치지 않았다

확정된 설계는 추천 입력을 **본문 → 요약**으로 바꾸는 것이다([#8](EXPERIMENTS.md), `DECISIONS.md`).

규칙 5를 조이면 곧 사라질 입력에 맞춰 튜닝하는 셈이다 — 이번 라운드에서 이미 한 번 저지른
종류의 실수다(아래 "다시 하지 말 것").

→ 요약 도입(별도 티켓, `V5` 마이그레이션 필요) 후 같은 15건을 다시 돌려 **위 스냅샷과 나란히**
비교한다. 그때 제목 길이 분포·지역명 중복·어미 일관성을 지표로 쓴다.

**한계**: 자료 15건·각 1회. **토큰 수를 비용 추정에 쓰면 안 된다** — 자료당 약 1,000 tok인데

## 14. ★ 요약 전용 모델 — 태깅 모델(`gpt-5-nano`)을 그대로 쓰면 안 된다 (2026-07-30)

**목적**: 요약을 별도 호출로 분리하기로 정한 뒤([DECISIONS](DECISIONS.md)), 그 호출에 어느 모델을 쓸지.
처음엔 태깅과 같은 `ChatClient`(=`gpt-5-nano`)를 공유하려 했다.

**방법**: 서버의 실제 요약 프롬프트로 픽스처 3건을 각 1회.

> ⚠️ **아래 수치는 프롬프트 v1 로 낸 것이다**(그 뒤 v3 까지 갔다 — [#15](EXPERIMENTS.md)).
> **모델 결론은 그대로 유효하다** — `gpt-5-nano` 의 추론 토큰 낭비는 프롬프트가 아니라 모델의 성질이다.
> 시간·토큰 절대값을 인용할 때만 v1 기준임을 밝힐 것.

| 픽스처(본문) | `gpt-5-nano` | `gpt-4.1-mini` | **`gpt-5.4-nano`(채택)** |
|---|---|---|---|
| 001 (553자) | 23.88초 · completion 3,637 (**추론 3,520**) | 1.93초 · completion 100 | **2.82초 · completion 144** (추론 0) |
| 011 (132자) | 12.88초 · completion 1,597 (**추론 1,536**) | 1.50초 · completion 52 | **1.29초 · completion 76** |
| 015 (532자) | 15.82초 · completion 2,339 (**추론 2,240**) | 2.55초 · completion 101 | **2.05초 · completion 111** |

**결론 1 — `gpt-5-nano`는 completion의 94~97%를 숨은 추론에 쓴다.** 150자 요약을 쓰려고 추론 토큰
3,520개를 태운다. 8배 느리고 30배 많은 completion을 쓰면서 **품질은 동등했다** — 둘 다 고유명사를
보존했고(`카페툇마루`·`강문어화횟집`·`이기적 스터디 카페`), 오히려 `nano` 쪽이 계정명 잡음을 덧붙였다
(`먹구리의 먹스타그램님의`, `을지로먹보님의`).

**결론 2 — 이 픽스처는 실사용보다 훨씬 짧다.** 132~553자인데 실제 크롤링 본문은 자료당 약
6.8k tok이다([#11](EXPERIMENTS.md)). 격차는 실사용에서 더 벌어진다.

### 게이트웨이에 `gpt-5.4-nano` 가 있다 → 이걸 쓴다

`/v1/models` 는 게이트웨이가 400으로 막지만(`Model not found in request for domain`), 채팅 호출로
직접 찔러보면 `gpt-5.4-nano`·`gpt-5.4`·`gpt-5.4-mini` 가 **전부 응답한다.**

**결론 3 — `gpt-5.4-nano` 가 두 축을 다 만족한다.** `gpt-4.1-mini` 만큼 빠르면서(1.3~2.8초 vs
1.5~2.6초) **추론 토큰을 0으로 쓰고** nano 등급 크레딧을 유지한다. `gpt-5-nano` 대비 시간은
6~9배 짧고 completion은 21~25배 적다.

고유명사 보존도 오히려 가장 풍부했다 — `사근진해변`·`경포호`·`최일순 짬뽕순두부`·`유리알유희`·
`을지로3가역`·`뚝섬역`·`이기적 스터디 카페`. 이 요약이 추천의 입력이므로 이게 핵심 품질 축이다.
요약 길이는 125·159·188자로 프롬프트가 요구한 **200자 이내를 지켰다**(컬럼은 500자라 여유가 있다).

→ **요약 모델 = `gpt-5.4-nano`**(사용자 결정). `modi.archive.summary-model` 프로퍼티,
`ARCHIVE_SUMMARY_MODEL` 로 덮을 수 있다.

**관측(고치지 않음)**: 세 모델 모두 `Instagram의 …님이` 처럼 **계정명을 요약 앞에 붙인다.**
추천 후보에 계정명이 새어들 여지가 있으나 프롬프트를 지금 손대지 않았다 — [#13](EXPERIMENTS.md)이
같은 판단을 한 이유(곧 바뀔 입력에 맞춰 튜닝하지 않는다)와, 프롬프트 변경은 평가셋으로 검증한다는
규칙(`ai/CLAUDE.md`) 때문이다. 요약이 들어간 추천 출력을 먼저 보고 판단한다.

### 사슬 연결 확인 — 요약을 넣고 실제로 추천을 받아봤다

`gpt-5.4-nano`가 낸 001 요약을 그대로 `content`로 실어 실행 중인 FastAPI에
`POST /v1/todo-suggestions` 를 1회. 7.7초 · 후보 8개 · 필터 탈락 0.

```
강릉 최일순 짬뽕순두부 맛집 위치 확인하기 / 경포호 산책 코스 계획 세우기
강릉 카페 3곳 리스트 만들기 / 사근진해변 방문 시간 정하기
유리알유희 소품샵 탐방 일정 짜기 / 모퉁이 소품샵 위치 및 영업시간 조사하기
오리둥지 소품샵 방문 계획 수립하기 / 강릉 당일치기 맛집 투어 코스 최적화하기
```

요약에 보존된 고유명사가 그대로 후보의 근거가 됐고, 8개 전부 `source_item_id` 를 제대로 붙였다.
위에서 관측한 `Instagram의 …님이` **잡음은 후보로 새어들지 않았다.**

**⚠️ 이것은 [#13](EXPERIMENTS.md) 과의 전/후 비교가 아니다.** 자료 1건·1회이고 방 정보도 러너의
`FIXED_ROOM` 과 다르다. 제목이 짧아 보이는 것(최대 21자, #13은 최대 40자)을 개선 근거로 인용하면
안 된다 — 조건이 통제되지 않았다. 진짜 비교는 15건 전부를 요약한 뒤 같은 러너로 돌려
`data/snapshots/` 에 동결해야 성립한다.

**한계**: 픽스처 3건·각 1회. 본문이 132~553자인데 실사용은 자료당 약 6.8k tok이다.
⚠️ **크레딧 축은 이 실험에 없다** — #2를 뒤집은 것이 바로 그 축이었고(`nano 3.0` vs `mini 10.0`),
[#7](EXPERIMENTS.md)이 "그 단가는 짧은 입력·짧은 출력 기준이라 우리 워크로드에 그대로 적용되지 않는다,
정확한 값은 대시보드 크레딧 차감으로 확인해야 한다"고 못 박았다. 대시보드 확인은 아직 안 했다.

> **태깅(`gpt-5-nano`)도 같은 낭비를 하고 있을 수 있다** — #2에서 태그 5개를 내면서 추론 1,344 tok을
> 썼다. `gpt-5.4-nano` 로 바꾸면 크레딧 등급을 유지하면서 빨라질 가능성이 있으나, **이번 티켓에서는
> 태깅을 건드리지 않았다**(잘 돌고 있는 것을 건드리지 않는다는 결정). 별도로 재볼 가치가 있다.

## 15. ★ 요약 프롬프트 v1 → v3 — 규칙을 한 줄씩 붙여가며 잰 것 (2026-07-30)

**목적**: 요약이 곧 추천의 입력이므로, 요약에 남는 잡음은 추천 후보의 잡음이 된다. 무엇을 지시해야
잡음이 사라지는지 한 번에 알 수 없어 **관측 → 규칙 추가 → 재측정**을 세 바퀴 돌렸다.

`gpt-5.4-nano` 고정 · 픽스처 3건 · 각 1회. 각 라운드에서 프롬프트 복사본이 Java 상수와 **문자 단위로
같은지 스크립트가 먼저 단언**하고 측정했다(눈으로 맞췄다고 믿으면 측정이 조용히 거짓이 된다).

| | v1 | v2 | **v3 (현재)** |
|---|---|---|---|
| 프롬프트 길이 | 226자 | 400자 | **285자** |
| 001 요약 | 188자 | **231자** ⚠️ | **157자** |
| 011 요약 | 125자 | 118자 | **88자** |
| 015 요약 | 147자 | 147자 | **117자** |
| 001 prompt / completion | 591 / 144 | 691 / 178 | **630 / 133** |

### v1 → v2 에서 관측된 것

v2 는 "실천 가능한 계획(To-do) 중심", "과거 경험·감상·배경 제외", "날짜·시간 제외"를 넣었다.

- ✅ **날짜·시간이 사라졌다.** v1 의 `청량리 07:52 출발, 강릉 20:30 복귀(3월 15일 일요일)` 가 없어졌다.
- ❌ **길이가 오히려 늘었다(231자, 스스로 요구한 200자 위반).** "To-do 중심"이 상호명 나열을 유도해
  한 자료에서 **16개**를 `… 체크해 두세요` 로 묶었다.
- ❌ **작성자 계정명이 남았다.** `Instagram의 먹구리의 먹스타그램님이 …` — "감상·배경 제외"로는
  안 걸러졌고, 011 에서는 오히려 **문장 맨 앞으로 올라왔다.**
- ❌ **어투가 갈렸다.** 001 은 `방문하세요`·`체크해 두세요`(존댓말 명령), 011·015 는 평서. v1 은 전부 평서였다.

### v3 이 고친 것

v2 의 세 실패에 각각 규칙을 대응시켰다 — 추상적인 "제외해라"가 아니라 **구체적인 이름으로** 지시한다.

| v2 의 실패 | v3 의 규칙 |
|---|---|
| 어투가 갈림 | `200자 이내의 평서문(~한다, ~다)으로` |
| 계정명이 남음 | `제외: 작성자 계정명(인스타그램 등), 출처, 인사말, …` |
| 16개 나열로 231자 | `고유명사 제어: … 200자를 초과하지 않도록 핵심 3~4개만 남길 것` |

결과: **3건 모두 200자 이내**(157·88·117), 계정명 0건, 날짜·시간 0건, 어투는 평서로 수렴.
프롬프트가 v2 보다 **짧아졌는데** 결과는 나아졌다 — 규칙을 늘린 게 아니라 **구체적으로 바꾼 것이 효과**였다.

고유명사는 여전히 여유 있게 남는다(001 에서 `최일순 짬뽕순두부`·`강문어화횟집`·`꾸옥 카페툇마루`·
`346커피스토리` 등 9개). "핵심 3~4개"를 문자 그대로는 안 지켰지만 **200자 조건을 만족하는 범위 안**이고,
추천 근거가 많은 쪽이 유리하므로 더 조이지 않았다.

**한계**: 픽스처 3건·각 1회. `temperature` 를 고정하지 않았다 — 같은 프롬프트로 다시 돌리면 문장이
달라질 수 있다. 그래서 **위 표의 자릿수를 품질 지표로 쓰면 안 되고**, "200자를 넘겼는가 / 계정명이
남았는가" 같은 **이진 관측**만 근거로 쓴다. 011 요약이 여전히 후기 서술(`합격한 후기이며`)인 것은
원문 자체가 132자 후기 캡션이라 뽑을 행동이 없는 탓으로 본다 — 프롬프트 문제로 단정하지 않았다.

> 각 규칙이 프롬프트에 실제로 살아 있는지 `OpenAiSummaryClientTest.promptCarriesEveryRuleThatAMeasurementJustified()`
> 가 지킨다. 규칙을 지우면 그 규칙이 막고 있던 문제가 되살아나므로, 지울 때는 위 표를 먼저 볼 것.

## 16. 요약을 트리 구조로 뽑아보기 — **재봤고 채택하지 않았다** (2026-07-30)

> **결과: 미채택.** 프롬프트는 v3(산문)을 유지한다(사용자 결정). 수치를 남기는 이유는 **다시 재지
> 않아도 되게** 하기 위해서다 — 이 형식을 또 고민하게 되면 아래를 먼저 볼 것.

**목적**: "산문 3문장 말고 트리로 뽑고 싶다"는 요청이 있었다. 요약은 추천의 입력이므로 형식이
바뀌면 추천 근거의 밀도가 바뀐다 — 컬럼 폭에 들어가는지, 토큰이 얼마나 늘어나는지 재야 한다.

**형식**: `■ 대분류` + `항목: 핵심` 한 줄. 대분류 3~4개 · 항목 2~4개 · 총 450자 이내.
`gpt-5.4-nano` 고정 · 픽스처 3건 · 각 1회. 프롬프트 복사본과 Java 상수의 문자 단위 일치를 먼저 단언했다.

| 픽스처(본문) | v3 산문 | **v4 트리** |
|---|---|---|
| 001 (553자) | 157자 · completion 133 | **294자 · completion 250** |
| 011 (132자) | 88자 · completion 57 | **153자 · completion 100** |
| 015 (532자) | 117자 · completion 78 | **420자 · completion 367** |

**결론 1 — `VARCHAR(500)` 안에 들어온다. 마이그레이션이 필요 없다.** 최대가 420자였다.
처음에는 사용자가 붙여준 예시(약 600자)를 보고 `V6` 로 컬럼을 넓혀야 한다고 판단했으나, 그건 **형식의
성질이 아니라 그 예시의 길이** 였다. 대분류·항목 수와 총 길이를 프롬프트에서 묶으면 500자에 들어온다.

**결론 2 — 추천 근거가 실제로 촘촘해졌다.** 015 에서 v3 는 `맛집과 카페, 디저트, 소품샵…을 각각 여러 곳`
으로 뭉갰는데 v4 는 `을지면옥`·`대림창고`·`오브젝트`·`몽탄` 처럼 상호를 분류별로 남긴다. 이 요약이
추천 후보의 근거이므로 이쪽이 목적에 맞다.

**결론 3 — 토큰이 2~4.7배 늘어 압축비가 떨어진다.** 이 티켓의 근거인 "자료 20건 117,000 → 2,600 tok,
**45배**"는 자료당 약 130 tok 기준이다. 트리는 자료당 약 150~210 tok 이므로 20건이면 약 3,000~4,200
tok = **약 28~39배**로 내려간다. 여전히 큰 절감이지만 문서에 박힌 "45배"를 12곳에서 고쳐야 한다.

### 채택하지 않은 이유

**결론 2(근거가 촘촘해진다)와 결론 3(압축비가 떨어진다)이 정면으로 부딧친다.** 이 기능의 목적은
화면이 아니라 **추천 프롬프트 비용 절감**이므로 압축비가 주 지표다. 트리가 주는 이득(추천 근거의
밀도)이 그 30% 손실을 정당화하는지는 **추천 출력을 실제로 비교해봐야** 알 수 있고, 그건
[#13](EXPERIMENTS.md) 동결 스냅샷과의 전/후 비교(요약 15 + 추천 15 = 30회)를 먼저 돌린 뒤에 할 판단이다.
그 비교 없이 형식을 바꾸는 것은 이 문서가 반복해서 경계해온 "눈으로 좋아 보인다는 이유로 프롬프트를
바꾸는 것"에 해당한다.

→ **다시 볼 때 필요한 것**: 트리는 컬럼 폭 안에 들어오므로(결론 1) 스키마 변경 없이 전환 가능하다.
막는 것은 압축비 하나뿐이고, 그걸 판단할 재료가 위 전/후 비교다.

**한계**: 픽스처 3건·각 1회, `temperature` 미고정. 본문이 132~553자인데 실사용은 자료당 약 6.8k
tok(#11)·최대 20,000자다 — **풍부한 본문에서는 450자를 넘길 가능성이 남아 있다.** 채택한다면
글자 수로만 자르면 안 된다(마지막 줄이 반토막 나거나 항목 없는 `■` 헤더만 남아 구조가 깨져 보인다).
표의 자릿수를 품질 지표로 쓰지 말고 "500자를 넘겼는가 / 구조가 살았는가" 같은 이진 관측만 근거로 쓴다.

## 17. ★ 후보 의미 중복 임계값 — **실제 후보 24개로 재서 정했다** (2026-07-30)

은 **글자가 같은** 재노출을 막았다. `todo_suggestion_exposures` 에 실제로 쌓인
24개(방 "회화 스터디", 추천 3회 × 8개)를 정규화해보니 **24/24 전부 고유**였는데, 눈으로 보면
같은 할 일이 계속 나왔다:

```
1회차  모바일 유튜브 모의고사를 활용해 주제별 답변 구조 연습하기
2회차  유튜브 모의고사로 주제별 답변 구조 연습하고 표현 정리하기
3회차  유튜브 모의고사로 다양한 주제별 답변 구조 연습하기
```

그래서 임계값을 **정하기 전에** 이 24개로 쌍별 코사인을 쟀다(`evals/calibrate_dedupe.py`,
`text-embedding-3-small`, 1536차원, 배치 1회 **2.73초**). 라벨은 눈으로 붙였다 —
기준은 "같은 **행동**을 다시 시키는가"이고, 같은 주제(오픽)라는 이유만으로는 중복이 아니다.

| 그룹 | n | min | median | max |
|---|---|---|---|---|
| 중복이어야 하는 쌍 | 11 | **0.527** | 0.802 | 0.943 |
| 아니어야 하는 쌍 | 5 | 0.219 | 0.256 | **0.648** |
| 전체 쌍(라벨 무관) | 276 | 0.051 | 0.303 | 0.943 |

### 결론 1 — 단일 임계값으로 라벨 전부를 가르지 못한다

`0.527 ~ 0.648` 에서 두 그룹이 겹친다. 제목이 짧고 전부 같은 도메인이라 코사인이 넓게 퍼지지
않는다. **그래서 "완벽한 분리"를 목표로 삼지 않고 `오탐 0` 을 기준으로 잡았다.**

| 임계값 | 잡음 | 오탐 |
|---|---|---|
| 0.65 | 7/11 | 0/5 |
| **0.70** | **7/11** | **0/5** |
| 0.75 | 6/11 | 0/5 |
| 0.85 | 4/11 | 0/5 |
| 0.90 | 1/11 | 0/5 |

**0.70 채택.** 0.65~0.70 이 재현율이 같은 고원이고, 관측된 비중복 최대(0.648)와 여유를 더
두려고 위쪽을 골랐다.

### 결론 2 — 오탐이 미탐보다 비싸다

이 방향을 고른 이유다. 오탐은 **쓸 만한 새 후보를 조용히 지운다**(사용자는 그게 있었는지 모른다).
미탐은 중복이 한 번 더 보이는 것 = 고치기 전 상태다. 게다가 "회당 8개 vs 제외 창 50개라
6~7번이면 후보가 마른다"가 이미 관측돼 있어(`specs/0001-architecture.md`) 과하게 거르면
빈 화면이 더 빨리 온다.

### 결론 3 — 캘리브레이션 셋에서 잡히는 것

유튜브 모의고사 3쌍 **0.888 / 0.893 / 0.943** · PDF 내려받기 **0.712** ·
서베이 주제 선별 **0.890** · 규정신분증 **0.801** · 스픽 어플 **0.806**.

**놓치는 것(미탐)**: 응시료 대학생 할인 **0.634** · 서베이 주제 선별 일부 **0.602 / 0.620** ·
필러·메인포인트 **0.527**.

⚠️ 처음 이 표를 적을 때 **0.890을 유튜브 쌍으로 잘못 귀속**했다(실제로는 서베이 쌍이다).
리뷰에서 재실행으로 잡혔다. 자릿수를 인용할 때는 러너를 다시 돌려 확인할 것.

### ⚠️ 결론 4 — **라이브에서 다시 재보니 0.70은 아무것도 잡지 못했다**

위 표만 보고 0.70으로 배선한 뒤 실제로 추천을 6회 눌러 봤다(방 "회화 스터디", 누적 29개).
**의미 중복 탈락은 0건**이었다. 생존자 중 이전 회차와의 최대 유사도가 **0.698** — 임계값에
0.002 못 미친다. 그 쌍이 하필 이 티켓의 존재 이유였다:

```
0.698  유튜브 모의고사 활용해 주제별 답변 구조 반복 연습하기
     | 유튜브 오픽 모의고사로 감정표현 포함 답변 연습하기
```

라이브 분포는 캘리브레이션 셋보다 **훨씬 좁은 띠에 몰린다**:

| 유사도 | 쌍 | 판정 |
|---|---|---|
| 0.698 | 유튜브 모의고사 답변 구조 | 중복 |
| 0.693 | 서베이 주제 선정 | 중복 |
| 0.658 | 공식 사이트 PDF 내려받기 | 중복 |
| 0.649 | 서베이 감정표현 | 애매 |
| 0.647 | 스픽 어플 | 중복 |
| 0.631 | 유튜브 채널 강의 시청 | 중복 |
| 0.630 | 문제 두 번 듣고 두괄식 | 중복 |
| 0.605 | 난이도 6-6 | 중복 |
| **0.604** | **접수·납부 확인 ↔ 환불·할인 정책** | **비중복** |
| 0.578 | 롤플레이 연습 | 중복 |

**진짜 중복이 0.578~0.698, 비중복이 0.604까지 올라와 완전히 겹친다.** 캘리브레이션 셋에서
`0.802~0.943` 같은 높은 값이 나온 것은 그 24개가 어휘를 많이 공유했기 때문이고, 일반적인
분포가 아니었다.

→ **0.65로 내렸다.** `오탐 0`(비중복 최대 0.604와 여유 0.046)을 지키면서 잡을 수 있는 최대다.
**라이브 중복 8건 중 3건만 잡는다** — 이 층은 문제를 절반도 해결하지 못한다. 더 내리면 0.604를
건드려 오탐이 시작된다.

### 결론 5 — 바이그램 Jaccard는 **더 낫지 않고 다른 것을 잡는다**

리뷰에서 "무료 어휘 기법이 캘리브레이션 셋에서 9/11로 더 잘 잡는다"는 지적을 받아 라이브
29개로도 재봤다. 뒤집힌다:

| 쌍 | 코사인 | Jaccard |
|---|---|---|
| 유튜브 모의고사 (중복) | **0.698** | 0.265 |
| 서베이 주제 선정 (중복) | **0.693** | 0.114 ← 놓침 |
| 자주 쓰는 표현 (중복) | 0.506 ← 놓침 | **0.464** |
| 접수·납부 ↔ 환불 (비중복) | 0.604 | 0.167 |

코사인은 **단어가 다른 패러프레이즈**를, Jaccard는 **글자를 공유하는 재표현**을 잡는다.
캘리브레이션 셋에서 Jaccard가 이긴 것은 그 24개가 후자에 치우쳐서다. **어느 쪽도 단독으로는
못 가른다.** 둘을 합치는 안(OR 조건 + 두 임계값)은 아직 재보지 않았다 — 임계값이 둘로 늘어
근거 없는 숫자가 배가 되므로 신중해야 한다.

### 다음에 이걸 다시 볼 사람에게

- **자릿수를 절대 기준으로 쓰지 말 것.** 라벨은 내가 눈으로 붙였고, 캘리브레이션과 라이브의
  분포가 이미 서로 다르다. 특히 "시험장 변경 확인" ↔ "준비물 확인"(0.648)을 비중복으로 본
  판정은 논쟁 가능하다 — 중복으로 보면 캘리브레이션의 겹침 구간이 사라진다.
- **단일 코사인 임계값이 이 문제에 맞는 도구가 아닐 가능성이 크다.** 남은 후보: ① 코사인+어휘
  OR 결합 ② 제목+카테고리를 함께 임베딩 ③ LLM에 중복 판정을 맡기기. 단 ③은 프롬프트 규칙 3이
  이미 "이미 제안했던 후보와 의미가 겹치는 것은 내지 않는다"라고 지시하는데 **모델이 지키지
  않아서** 이 층이 필요해졌다는 점을 감안해야 한다.

## 19. 자료 임베딩 저장 — 게이트웨이 실측, 자르는 지점 역산, `real[]` 왕복 (2026-08-01)

**목적**: 착수 전 세 가지를 확인해야 했다. ① 게이트웨이가 임베딩을 **Spring AI 경로로** 받는가
② 본문을 어디서 잘라야 모델 상한을 넘지 않는가 ③ Hibernate `float[]` ↔ Postgres `real[]`가 맞는가.
셋 중 하나라도 안 되면 티켓 나머지가 무의미해서 코드보다 먼저 쟀다.

### ① 게이트웨이 `/v1/embeddings` — 된다 (두 단계로 확인)

| 확인 | 방법 | 결과 |
|---|---|---|
| 게이트웨이가 경로를 받는가 | `curl` 직접 호출 | **http 200** · `text-embedding-3-small` · **1536차원** · 1.76초 · 7 tok |
| **Spring AI가 그 경로를 만드는가** | 실서버 백필 12건 | **12/12 성공** · 16.79초 (건당 **1.40초**) |

두 번째가 진짜 확인이다. 파이썬(`langchain-openai`)에서만 검증돼 있었고,
`OpenAiApi.builder().embeddingsPath("embeddings")`가 게이트웨이 프록시와 맞는지는 **부른 적이 없었다.**
`baseUrl`이 `.../v1/`로 끝나 `chat/completions`와 같은 방식으로 붙는다 — 결합 규칙이 채팅과 같다는 뜻이다.

### ② 자르는 지점 6,000자 — 한국어 토큰/문자 비를 재서 역산했다

`text-embedding-3-small`의 입력 상한은 **8,191 토큰**이고 넘으면 400이 온다. 문자 수로 환산해야 하는데
"한국어는 대충 1자 1토큰"으로 넘겨짚으면 상한을 넘겨 임베딩이 통째로 `NULL`이 되거나, 반대로 과하게 잘라
본문을 버린다. **실제 아카이브 본문 2건**으로 쟀다:

| 본문 | 1,000자 | 4,000자 | 8,000자 |
|---|---|---|---|
| id=12 (블로그) | 976 tok · 0.976 | 3,952 tok · 0.988 | 7,860 tok · 0.983 |
| id=2 (블로그) | 930 tok · 0.930 | 3,692 tok · 0.923 | 7,277 tok · 0.910 |

관측 범위 **0.910~0.988 tok/char**. 8,000자가 아슬아슬하게 들어가지만(7,860 / 8,191) 여유가 2.4%뿐이라
측정하지 않은 종류의 텍스트(기호·이모지가 많은 본문)에서 넘길 수 있다.
관측 최대에 여유를 얹어 **1.3 tok/char**로 잡고 `8,191 ÷ 1.3 ≈ 6,300` → **6,000자**.

> ⚠️ 이 상한은 **요약이 없는 자료에서만** 쓰인다. 임베딩 입력은 요약 우선이고 요약은 500자가 상한이다.

### ③ `float[]` ↔ `real[]` — 우회 없이 통과했다

이 티켓의 최대 리스크였다(`@JdbcTypeCode(SqlTypes.ARRAY)`나 `@Array`가 필요할 줄 알았다).

- `SchemaValidationTest`(Testcontainers `postgres:16-alpine` + Flyway + `ddl-auto=validate`) **통과**
- 값 왕복도 확인 — `ArchiveItemServiceTest`가 1536개짜리 벡터를 쓰고 되읽어 원소를 대조한다
- 실 DB 저장 크기 **6,164 bytes/행** (1536 × 4 + 배열 헤더 20). 12건 = 약 74KB

### ④ 무엇이 임베딩됐는지 실증 — 요약이 입력이 맞다

저장된 벡터(id=12)와 그 자료의 **요약을 새로 임베딩한 벡터**의 코사인 = **1.000000**.
요약이 있는 자료는 요약이, 없는 자료(id 1~4, `V5` 이전 등록분)는 본문이 입력이 됐다.

### 백필 실측

`ARCHIVE_BACKFILL_EMBEDDINGS=true`로 한 번 기동: **대상 12건 → 채움 12건 · 건너뜀 0건, 16.79초.**
기동을 막지 않고(`ApplicationRunner`) 한 건씩 커밋한다. 플래그를 빼면 빈 자체가 안 생긴다.

**남은 개수를 확인하는 쿼리** — 임베딩 실패는 화면에 아무것도 안 나오므로(태그·요약과 다르다)
게이트웨이가 죽어 있어도 다음 티켓 전까지 아무도 모른다. 백필 로그의 "건너뜀 N건" 말고는 이게 유일한 탐지 수단이다:

```sql
select count(*) filter (where embedding is null and crawl_status <> 'PENDING') as 임베딩없음,
       count(*)                                                                as 전체
from archive_items;
```

⚠️ 백필에는 **레이트리밋도 건수 상한도 재시도도 없다.** 12건이면 무해하지만 수천 건이면 순차 호출로 몇 시간이 걸리고,
429가 나면 전건이 조용히 "건너뜀"으로 끝난다. 자료가 크게 늘면 그때 `LIMIT` + 백오프를 붙일 것.

### 등록 1건당 늘어나는 비용 — **동기 2경로는 사용자가 기다린다**

LLM 호출이 **태깅 1 + 요약 1 + 임베딩 1 = 3회**가 됐다(임베딩이 +1). 건당 약 **1.4초**.

> ⚠️ 이 절의 초안에 "세 경로 모두 백그라운드라 체감 지연은 없다"고 적었는데 **틀렸다**(리뷰 지적).
> 백그라운드인 것은 셋 중 **하나**뿐이다.

| 등록 경로 | 임베딩 호출 위치 | 사용자 체감 |
|---|---|---|
| S-25-D 외부 공유 **URL** (`ArchiveCrawlProcessor`, `@Async`) | HTTP 응답 **뒤** | 없음 |
| S-25-C 자료 등록 (`createItem`) | HTTP 응답 **전** | **+1.4초** |
| S-25-D 외부 공유 **텍스트** (`createSharedItem`) | HTTP 응답 **전** | **+1.4초** |

동기 두 경로는 원래도 요약(1.3~2.8초)을 응답 전에 부르고 있었으므로 **없던 대기가 생긴 게 아니라 25~50% 늘었다.**
앱에는 스피너가 있고 클라이언트 타임아웃은 없어 깨지지는 않는다.

**텍스트 공유 경로가 더 아프다.** URL 분기를 굳이 `PENDING` + `@Async`로 뺀 이유가
"네이티브 공유 시트가 등록 확인만 받고 바로 닫혀야 한다"(`specs/0014`)인데, 텍스트 분기는 같은 시트를 1.4초 더 붙잡는다.

**그래도 이번 티켓에서 비동기로 빼지 않았다** — `ArchiveItemDetailResponse.summary`가 생성 응답에 실려 나가므로
파생 데이터 전체를 뒤로 미루면 **응답 계약이 바뀐다**(요약이 항상 `null`인 응답이 된다). 그건 앱까지 걸리는 별도 작업이다.
**여기가 공짜라고 믿고 네 번째 호출을 얹지 말 것** — 이 표가 그 경고다.

⚠️ **크레딧 축은 재지 않았다** — 게이트웨이 대시보드 차감으로만 확인 가능하다([#7](#7)과 같은 한계).

### ⚠️ 남은 문제: 임베딩의 **기준이 자료마다 다르다**

요약이 있는 자료는 요약(115~236자)이, 없는 자료는 본문(최대 6,000자)이 벡터가 된다.
그런데 긴 본문 벡터는 평균화돼 짧은 방 목표와의 코사인이 **구조적으로 낮게** 나온다 — 그게 애초에 요약을 고른 이유다.
즉 **요약 없는 자료는 `NULL`이 아닌데도 유사도 축에서 불리하다.**

실서버 12건 중 **4건**(id 1~4, `V5` 이전 등록분)이 정확히 그 경우이고, 백필이 그 상태를 그대로 굳혔다.
읽는 쪽(다음 티켓)이 이걸 모르면 "왜 옛날 자료는 안 뽑히지"를 처음부터 다시 파게 된다.

**대응은 정하지 않았다** — 선택지는 셋이고 다음 티켓에서 결정한다:
① 백필 때 요약부터 만들어 기준을 통일한다(크레딧 2배) ② 읽는 쪽이 기준을 구분한다 ③ 감수한다.

`suggest_eval_export.json` 은 `.gitignore` 라 나중에 확인할 수 없기 때문이다(#13 이 실제로 겪은 사고이고,
**이번에도 초안에서 같은 실수가 나 리뷰에서 잡혔다**). 9회 중 1회가 스냅샷에 없는 이유는 바로 아래에 적었다.

### ⚠️ 먼저: 잡음 바닥 — **후보 개수와 제목 길이는 근거로 쓸 수 없다**

같은 조건을 두 번씩 돌렸다. temperature 0.0 인데도 갈린다:

| 조건 | 실행 A | 실행 B | |
|---|---|---|---|
| `할 일` · 규칙4 있음 | 후보 **31** · 20자초과 74% | 후보 **35** · 20자초과 71% | Δ4 |
| `공부` · 규칙4 있음 | 후보 **28** · 20자초과 71% | 후보 **25** · 20자초과 64% | Δ3 |

("1회차/2회차" 로 적지 않는다 — 기본 키가 한 번 덮어써져 **순서를 재구성할 수 없다.**)

**조건당 표본이 2개뿐이라 이건 잡음 "바닥"이지 범위가 아니다.** 같은 `할 일` 조건을 한 번 더 돌렸을 때
후보가 **40개**까지 나왔는데, 그 실행은 `--label` 없이 돌려 export 에서 덮어써졌다 — 내 실수다
(반복 실행은 반드시 `--label` 을 붙일 것). **그 40 은 어떤 커밋 파일에도 없으므로 근거로 쓰지 않는다.**
커밋된 값만으로 말하면 폭은 Δ3~4 이고, 실제로는 그보다 넓을 수 있다.

**그러니 조건 간 후보 개수 차이(예: 규칙4 있음 28 vs 없음 36)를 결론으로 쓰지 말 것.**
아래 결론은 `new_categories` 하나에만 기댄다 — 8개 스냅샷에서 재현 가능하고, 계수기의 감도는
`TestCountNewCategories` 가 양성 대조로 따로 확인한다(항상 0인 값의 분산이 0인 것은 "잡음 없음" 과
"감도 없음" 을 구분하지 못하기 때문이다 — 리뷰 지적).

### ① 규칙 4는 원인이 아니다 — 그리고 **1차 A/B 는 반쪽이었다**

[DECISIONS](DECISIONS.md) 미확정 "추천이 새 카테고리를 만들지 않는 편향"의 원인 후보가 프롬프트
규칙 4("기존 카테고리를 우선한다")였다. 기존 카테고리를 `공부` 로 바꿔(여행·맛집 자료 10건이
명백히 안 맞게) 다시 쟀다 — #13 의 1차 측정이 `["할 일"]` 고정 때문에 판별 불가였던 것을 고친 것이다.

| # | 기존 카테고리 | 규칙4 | 스키마 힌트 | 새 카테고리 |
|---|---|---|---|---|
| 1·2 | `할 일` | 있음 | 있음 | **0** |
| 3·4 | `공부` | 있음 | 있음 | **0** |
| 5 | `공부` | **없음** | 있음 | **0** |
| 6 | `공부` | **없음** | **없음** | **0** |
| 7 | **(없음)** | 있음 | 있음 | **0** |
| 8 | **(없음)** | **없음** | **없음** | **15** ← |

**규칙 4 를 빼도 0개다.** 여행·맛집·패션·플레이리스트 자료가 전부 `[공부]` 로 들어갔다
(`강릉에서 식사 3번·카페 3곳·디저트 6곳 일정대로 이동` → `[공부]`).

**그리고 규칙 4 만 빼는 A/B 는 애초에 성립하지 않았다.** 같은 지시가 **프롬프트와 구조화 출력
스키마 두 군데**에 있다 — `TodoCandidate.category` 의 description 이
`"기존 카테고리명 중 하나. 어디에도 맞지 않으면 새 카테고리명(20자 이내)"` 이고, 이게
`with_structured_output` 의 JSON 스키마로 모델에 그대로 간다. 그래서 `--no-schema-hint` 를
새로 만들어 **둘 다** 뺀 조건(#6)을 돌렸고, 그래도 0개였다.

> 러너 설계 결함이 이걸로 **두 번째**다(1차는 `["할 일"]` 고정). 조건을 바꾸는 플래그를 만들 때는
> **그 조건이 프롬프트 말고 다른 데도 적혀 있지 않은지** 먼저 확인할 것.

### ② 모델은 카테고리를 **지어낼 수 있다** — 안 하는 게 아니라 못 하게 막혀 있다

> ⚠️ **이 절의 초안은 정반대로 적혀 있었고 틀렸다.** "모델이 새 카테고리명을 만드는 행동 자체를
> 하지 않는다" 고 썼는데, 그 근거였던 #7 은 **규칙4·스키마 힌트가 켜진 채**였다. 리뷰에서
> "(카테고리 없음 × 규칙4 없음 × 힌트 없음) 셀이 비어 있다" 를 지적받아 #8 을 돌렸고 **결론이 뒤집혔다.**
> 빠진 셀 하나가 결론을 뒤집을 수 있으면, 그 셀을 안 돌린 결론은 결론이 아니다.

세 조건이 갈라 준다:

| 기존 카테고리 | 힌트(규칙4+스키마) | 결과 |
|---|---|---|
| `공부` 있음 | 있든 없든 | 여행·맛집까지 **전부 `공부` 로** 밀어넣음 |
| 없음 | 있음 | 후보 40개 **전부 `None`** |
| 없음 | **없음** | **새로 지어냄** — 42개 중 15개 |

#8 에서 실제로 나온 이름:

```
[여행/식도락] 강릉 맛집 투어 루트대로 일정 수행하기
[여행/교통]   KTX로 청량리 출발-강릉 도착 동선대로 이동하기
[장소 방문]   모치플레지르 방문 일정 추가하기
[맛집 방문]   별미청 돼지국밥 들르기
[여행 일정]   부산 1박 2일 코스 동선표 만들기
```

**즉 능력의 문제가 아니라 지시의 문제다.** 다만 자유롭게 풀어줘도 **15건 중 3건(여행 자료)에서만**
카테고리를 지었고 나머지는 여전히 `None` 이다 — `category` 가 `Optional`(`default=None`)이라
"모르겠으면 비운다" 가 항상 열린 탈출구인 것은 그대로다.

→ 지금 안 되는 것은 **"기존 것에 안 맞으면 새로 만든다" 는 판단**이다. 목록이 있으면 무조건 거기 넣는다.
얄궂게도 규칙 4 문구는 이미 *"어느 쪽에도 맞지 않을 때만 새 카테고리명을 지어낸다"* 라고 적고 있다 —
모델이 앞의 "우선한다" 만 듣고 뒷문장을 무시한다.

→ 그래서 고칠 방향은 규칙을 **빼는 것이 아니라** ① "안 맞으면 만들어라" 에 **판단 기준을 주거나**
② `category` 를 필수로 만들거나 ③ 앱이 `None` 후보를 받아 사용자가 정하게 하는 것이다.
**이 티켓에서는 하지 않았다** — 프롬프트/스키마/앱 변경은 근거를 들고 오는 다음 티켓이다
(`full_spec.md` §S-16-B 가 요구하는 "새로 카테고리 + 투두" 가 지금 안 나오는 것은 그대로 스펙 위반이다).

### ③ 제목 품질 — #13 의 예측은 **절반만 맞았다**

#13 은 제목이 긴 원인이 "원문에 병기된 주소·날짜·기관명을 그대로 베끼는 것"이라 보고
**"요약이 들어가면 그 원인 자체가 사라진다"** 고 예측했다.

| | #13 (본문 · `gpt-4.1-mini`) | 지금 (요약 · `gpt-5.4-nano`, 8회) |
|---|---|---|
| 최대 길이 | **40자** | **30~40자** (아티팩트 1건 빼면 30~35) |
| 최소 길이 | 8자 | **12~16자** |
| 20자 초과 비율 | 60% (30/50) | **58.3~74.2%** |

- **맞은 것**: `부산 부산진구 히떼 로스터리 …` 같은 **주소 병기가 사라졌다.** 요약이 주소를 걸러낸 결과다.
- **틀린 것**: **길이 자체는 나아지지 않았다.** 20자 초과 비율은 같은 대역이고, 최대 길이도 한 실행이 #13과 똑같이 40자를 찍었다. 오히려 짧은 제목(8자)이 사라져 **분포가 가운데로 몰렸을 뿐**이다.
- 40자 1건은 **러너 아티팩트**다: `아카이브 ‘009_fashion_promtome’ 기반 옷 정보 요청하기` — 픽스처는 크롤링을 안 거쳐 `og:title` 이 없고 `EvalCase.title` 이 **파일 이름**을 넘긴다(`dataset.py`). 실사용에서는 안 나오는 형태이니 길이 비교에서 빼고 볼 것.
- 어미 이탈은 여전히 실행당 **3~5건**(`… 반복학습`, `… 오답노트 작성` — 명사형 종결). 판정 기준은 "제목이 `기` 로 끝나지 않는다" 로 셌다 — 눈 관측이라도 기준을 적어야 다시 셀 수 있다.
- 새 형태의 반복이 생겼다: `을지로·성수 맛집 …` / `을지로·성수 카페 …` / `을지로·성수 디저트 …`
  처럼 **한 자료에서 접두어가 반복**된다. 요약이 지역명을 앞에 모아둔 결과다.

**두 스냅샷의 차이는 2변수다**(입력 본문→요약 **과** 모델 `gpt-4.1-mini`→`gpt-5.4-nano`).
어느 쪽 때문인지 이 데이터로는 가를 수 없다 — 그렇게 읽지 말 것.

### ④ 원문 충실도(고유명사) — 눈으로 대조했고 **손상 없음**

[DECISIONS](DECISIONS.md) 미확정 "추천 생성 모델 ② 고유명사 원문 충실도"가 이걸 기다리고 있었다.
장소·상호명이 많은 6건(001 강릉, 003~006 부산, 015 서울)의 후보를 요약·원문과 대조했다.

`모치플레지르` · `밤산책방` · `히떼 로스터리` · `별미청 돼지국밥` · `공원 6ongone` · `광안역` ·
`을지로3가역` · `퀴즐렛` · `이기적 스터디 카페` — **전부 원문 표기 그대로**다.
`nano` 계열이 제목을 중간에서 잘라내던 전례([#7](EXPERIMENTS.md))는 재현되지 않았다.
`source_item_id` 위반·필터 탈락도 8회 전부 **0개**.

> **한계**: 요약이 이미 고유명사를 3~4개로 줄인 뒤라, 이 측정이 보는 것은 **"요약→후보" 구간의
> 충실도**다. "원문→요약" 구간에서 버려진 상호명은 여기서 안 잡힌다.

### ⑤ 응답 시간 — 동기 유지 결정을 **뒤집을 이유가 없다**

자료 1건당 **1.1~2.8초** — 스냅샷에 남은 **120회 중 117회**가 그 안이다(나머지 15회는 덮어써진 실행이라
per-case 값이 없다). 3초를 넘긴 것은 **2건**(3.32초·6.1초)이고 최댓값은 6.1초다.
둘 다 같은 자료(001)인데 다른 실행에서는 1.57~2.77초에 냈으므로 자료 탓이 아니라 게이트웨이 흔들림으로 본다.
**"항상 3초 안"으로 읽지 말 것.**

> ⚠️ **이 135회가 동기 유지 결정의 근거는 아니다.** 여기는 자료 **1건**짜리 호출(≈900 tok)이고 운영은
> 8~12건(2,400~2,900 tok)이다 — 바로 아래 ⑥이 그 차이를 계산한다. 결정을 실제로 떠받치는 것은
> [#18](EXPERIMENTS.md)의 **실사용 트레이스 3.13초**이고, 이 절은 그것과 모순되지 않는다는 확인이다.

### ⑥ 덤으로 나온 것 — **자료를 걸러내도 토큰이 별로 안 준다**

자료 1건짜리 프롬프트가 **869~948 tok** 인데, 그 안의 요약은 59~167자(≈100 tok)다.
즉 **고정 비용(시스템 프롬프트 + 방 정보 + JSON 스키마)이 약 800 tok** 으로 대부분이다.

스키마 힌트를 뺀 순수 효과는 **155 tok**(규칙4를 고정하고 힌트만 뺀 15케이스 전부 정확히 155).
초안이 `913→713` 이라고 적었던 것은 **rule4·카테고리 이름까지 같이 바뀐 3변수 차이**였다 — 이 문서가
다른 절에서 스스로 경계하는 실수를 여기서 저질렀다(리뷰 지적).

→ **자료 하이브리드 선별(RRF) 티켓에 직접 걸린다.** 자료를 절반으로 줄여도 고정비가 그대로라
전체의 25% 남짓밖에 못 줄인다.

> **다만 이 모형은 운영을 과소추정한다.** 운영 실측은 자료 **8건**에 2,398~2,923 tok인데
> 같은 모형은 800 + 8×100 = **1,600 tok** 을 준다. 추천 요청에는 `excluded_todos`(방별 최근 50개)와
> `existing_todos` 가 더 실리기 때문이다(`build_payload`). **운영 고정비는 여기서 잰 것보다 크다** —
> 그래서 결론("선별의 이득을 토큰에서 찾지 마라")은 오히려 더 강해진다.

선별의 이득은 토큰이 아니라 "관련 없는 자료가 후보를 흐리는 것"에서 찾아야 한다.

### 동결 (커밋된 것 = 근거)

`evals/data/snapshots/2026-08-01_gpt-5.4-nano_summary_*.json` **8개** — 위 표의 모든 조건을 하나씩 얼렸다.
`evals/freeze_snapshot.py`(크레딧 0)로 만들었고, 조건 필드(`input`/`categories`/`rule4`/`schema_category_hint`)와
per-case 관측값(`prompt_tokens`/`seconds`)까지 파일에 함께 적었다 — 조건 없는 숫자는 근거가 못 되고,
문서가 인용하는 값이 커밋 밖에 있으면 나중에 확인할 방법이 없기 때문이다.

**`tests/test_snapshot_2026_08_01.py` 가 이 절의 수치를 크레딧 0으로 단언한다.** 그 파일이 없어서
초안에 `47.5%`(어떤 파일에도 없는 값)와 `30~34`(34인 실행 없음)가 나갔고 리뷰에서 잡혔다.
**숫자가 바뀌면 문서와 스냅샷을 함께 다시 만든다 — 테스트를 고쳐 통과시키지 않는다.**

> ⚠️ 스냅샷 3·4·5행의 `schema_category_hint` 는 `null` 로 얼려져 있다 — `--no-schema-hint` 플래그를
> 만들기 **전** 실행이라 러너가 그 필드를 안 남겼다. 조건은 "있음"이 맞지만(그 플래그의 기본값이 곧
> 당시 동작이다) **파일만 보고는 확인할 수 없다.**

요약 픽스처 15건은 `evals/data/summaries/` 에 커밋했다 — 이게 안 고정되면 조건 간 비교가 성립하지 않는다.

**[#13](EXPERIMENTS.md)의 `2026-07-30_gpt-4.1-mini_baseline.json` 과 짝을 이룬다**(요약 도입 전/후).
다만 그 사이 모델도 바뀌어 **2변수 비교**라는 것을 잊지 말 것.

## 21. ★ 카테고리 편향을 **실제로 고쳤다** — 프롬프트로는 안 됐고, 판단을 코드로 옮겼다 (2026-08-01)

**목적**: [#20](EXPERIMENTS.md)이 밝힌 편향("기존 카테고리가 있으면 안 맞는 자료까지 전부 거기 넣는다")을
고치는 것. `full_spec.md` §S-16-B 가 요구하는 **"새로 카테고리 + 투두"** 가 안 나오던 스펙 위반이다.

사용자가 원한 동작은 한 문장이었다 — *"유사도가 높으면 그 카테고리에 맞게, 아니면 새로 만들면 되잖아."*

**방법**: 기존 카테고리 `공부` 하나(여행·맛집·패션 자료 10건이 명백히 안 맞음), 입력 요약,
`gpt-5.4-nano`, temperature 0.0, 자료 15건씩. 수치는 커밋된 `data/snapshots/2026-08-01_*.json` 에서 뽑았다.

### ① 프롬프트로는 안 된다 — 문구 4가지가 **전부 0개**

| 조건 | 새 카테고리 | 후보 |
|---|---|---|
| v1 (커밋된 규칙 4) | **0** | 28·25 |
| **v2** — "우선한다"를 빼고 판정 기준을 줌 | **0** | 38 |
| **스키마 힌트 v2** — 같은 취지를 description 에 | **0** | 33 |
| **v2 + 스키마 v2** | **0** | 33 |
| **v3** — 구체적 예시까지 추가(`운동` 뿐인데 독서 자료면 `독서`) | **0** | 29 |

**후보의 100%가 `공부` 였다.** 모델이 전혀 흔들리지 않는다. 강릉 맛집 투어도, 부산 여행도,
패션 자료도 `[공부]` 로 들어간다.

> v3 의 예시 도메인(`운동`/`독서`)은 **평가셋에 없는 것**으로 골랐다. `공부`/`여행` 을 예로 들면
> 시험 문제를 알려주고 채점하는 셈이다.

`ai/CLAUDE.md` 는 "프롬프트 변경은 평가셋으로 검증한다"고 적어뒀는데, 이번엔 그 규칙이 **채택을
막는 쪽으로** 작동했다. 눈으로는 v3 이 훨씬 그럴듯해 보였다.

### ② 그래서 판단을 코드로 옮겼다

바뀐 것은 셋이고, **모델에게 매칭을 시키지 않는다**는 한 가지 생각에서 나왔다.

1. **규칙 4** — "기존 카테고리 중에서 고르라" → **"이 후보가 속할 분야를 한두 단어로 쓰라"**
2. **`build_payload` 에서 기존 카테고리 목록을 뺐다** — 목록을 보여주면 거기 맞추려 한다.
   ①의 실패가 그 증거다(문구를 뭐라고 쓰든 목록이 이기더라).
3. **`suggest.map_categories`** — 모델이 쓴 주제를 임베딩해 기존 카테고리와 코사인을 재고,
   임계값 이상이면 기존 이름으로 바꾼다. 이미 있던 `Embedder`·`_cosine` 을 그대로 쓴다.

## 22. ★ 자료 선별 — **확정 설계였던 가중 RRF 를 실측으로 기각했다** (2026-08-02)

`DECISIONS.md` 에 2026-07-29부터 "융합은 RRF(k=60)"가 확정으로 박혀 있었고, 2026-08-01에
사용자가 축별 가중치를 **좋아요 3.0 > 핀 2.5 > 유사도 2.0 > 최근성 1.0** 으로 정했다.
구현 중에 재보니 **그 가중치 순서가 정반대로 뒤집혀 있었다.**

### ① 실서버 분포로 재기

방 "회화 스터디" 자료 17건 기준(당시), **핀 0건 · 좋아요 1건**. 즉 좋아요·핀 축은 사실상
**2단계(1/0)** 이고 유사도·최근성은 **17단계**다.

> 질문: **가장 오래된 자료에 좋아요를 하나 누르면 몇 등이 되나?**

| 융합 | 좋아요를 눌렀을 때 | 핀을 꽂았을 때 |
|---|---|---|
| **RRF k=60** (확정안) | **16등** ← 17등에서 한 칸 | **16등** |
| RRF k=30 | 15등 | 16등 |
| RRF k=10 | 13등 | 14등 |
| RRF k=1 | 4등 | 5등 |
| **순위 정규화** | **2등** | 4등 |

### ② 원인은 k 가 아니라 구조다

축별 **변별력**(그 축이 1등과 꼴찌에 주는 점수 차이 = 그 축이 순서를 좌우하는 힘):

| 융합 | 좋아요(2단계) | 핀(2단계) | 유사도(17단계) | 최근성(17단계) | 의도대로? |
|---|---|---|---|---|---|
| RRF k=60 | 0.0008 | 0.0007 | **0.0068** | 0.0034 | ❌ 유사도가 좋아요의 **8.6배** |
| RRF k=10 | 0.0227 | 0.0189 | **0.1077** | 0.0539 | ❌ |
| RRF k=1 | 0.5000 | 0.4167 | **0.8889** | 0.4444 | ❌ |
| RRF k=0 | 1.5000 | 1.2500 | **1.8824** | 0.9412 | ❌ |
| **순위 정규화** | **3.0** | **2.5** | **2.0** | **1.0** | ✅ |

RRF 의 변별력은 `w × [1/(k+1) − 1/(k+n)]` 이라 **가중치뿐 아니라 그 축의 단계 수 `n` 에
비례한다.** 2단계 축은 `1/(k+1) − 1/(k+2)` 밖에 못 벌어서, 17단계 축을 **k 를 0까지 낮춰도
못 이긴다.** 대수적으로도 좋아요가 최근성을 이기려면 `k < 1.46` 이어야 하고, 그래도 유사도는
못 이긴다. **튜닝으로 고칠 수 있는 문제가 아니다.**

### ③ 대신 쓴 것 — 순위 정규화

등수를 축마다 관측된 범위로 `1등 = 1.0 · 꼴찌 = 0.0` 으로 편 뒤 가중합한다.

    점수 = Σ wᵢ × (꼴찌등수ᵢ − 등수ᵢ) / (꼴찌등수ᵢ − 1등수ᵢ)

**변별력이 곧 가중치**가 된다. RRF 를 골랐던 원래 근거("코사인 0~1 · 경과일수 · 정수 카운트는
스케일이 달라 정규화 상수가 근거 없이 코드에 남는다")는 그대로 지켜진다 — **등수만 쓰고, 나누는
값은 임의 상수가 아니라 그 축에서 관측된 등수 범위**다. 전원 동점이면 축이 통째로 빠지는 성질도
동일하다(핀 0건 → 자동으로 빠짐). **2026-08-02 사용자 확정.**

### ⑤ 예산은 발동하지 않는다 (미결 #4 를 닫은 값의 근거)

자료 18건의 렌더 합계 **3,709자**(평균 206자/건). 예산 12,000자는 **약 58건 · 지금의 3.2배**다.
실제 HTTP 호출에서 `archive=18 items` 가 그대로 로깅됐다 — 하나도 안 잘렸다.

### ⑥ 함께 잰 것

| 항목 | 값 |
|---|---|
| 요청 페이로드 | **390,110 바이트** (자료 18건 × 1536차원 벡터) |
| 응답 시간 | **9.1초** (HTTP 200, 후보 8개) |
| LLM 토큰 | input **2,982** · output 275 |
| 임베딩 호출 | **2회** — LLM 전(목표 벡터) + LLM 후(후보 제목 배치) |
| LangSmith 스팬 | 루트 `LangGraph` 6.52초 · `select` **0.9초** · `generate` 3.76초 · `dedupe` 1.71초 |

**임베딩 왕복이 하나 늘어난 것은 구조상 불가피하다** — 목표 벡터는 LLM **전에** 필요한데 뒤의
배치는 후보 제목을 담아 LLM **후에**만 만들 수 있다. 최악 지연은 10초 × 2회(재시도) × 2군데
= 40초 + LLM 8~11초로 Spring read timeout 60초 안이지만 **여유가 9초뿐**이다.

> **벡터를 통째로 보내는 비용(390KB)** 은 내부망 1회 호출이고 LLM 9.1초 대비 무시할 수준이라
> 그대로 둔다. 대안(Spring 이 코사인까지 계산)은 "선별 주체는 FastAPI" 확정을 어긴다.
> ⚠️ **다만 이 기각 사유는 절차 논거이지 기술 논거가 아니다**(리뷰 지적). 코사인 계산은 선별이
> 아니라 **피처 산출**이고, 선별(가중합·동점 처리·예산)은 Spring 으로 옮겨도 FastAPI 에 남는다.
> Spring 이 계산하면 390KB·왕복 0.9초·차원 불일치 처리가 한꺼번에 사라지고 **방 목표 벡터를
> 캐시할 수도 있다**(이 서버는 아무것도 저장하지 않으므로 요청마다 새로 만든다). 지금 9.1초 중
> 0.9초라 급하지 않아 두는 것이고, 필요해지면 RRF 를 뒤집은 것과 같은 기준으로 다시 물으면 된다.

### ⑦ 리뷰에서 잡힌 것 — **값이 없는 축을 "꼴찌"로 두면 같은 실패가 재발한다**

처음 구현은 임베딩이 없는 자료에 유사도 축 **꼴찌**를 줬다. `DECISIONS.md`·`V7` 은 *"유사도
축에서**만** 빠진다"* 라고 약속했는데 **꼴찌는 중립이 아니라 가중치 2.0 만큼의 감점**이다.

벡터는 `V7`(2026-08-01) 이후 등록분에만 있고 **백필은 기본 꺼짐**(`ARCHIVE_BACKFILL_EMBEDDINGS`)
이라 혼합 방이 기본 상태다. 그러면 **"벡터가 있다" ≈ "최근에 등록됐다"** 이므로 유사도 축이
최근성의 복사본이 되고, **실효 최근성 3.0 이 핀 2.5 를 넘는다** — 가중치 순서가 다시 뒤집힌다.

실서버 자료 18건에서 **최신 5건만 벡터를 남기고** 재현했다(= 백필 안 돌린 방):

| 처리 | 상위 5위 |
|---|---|
| 꼴찌(처음 구현) | 벡터를 가진 5건이 독점 — 목표와의 코사인이 0.196(거의 무관)이어도 |
| **중립(고침)** | **`[18, 20, 15, 11, 9]` = 좋아요가 눌린 5건.** 그중 벡터 보유는 0건 |

고친 방식: 값이 없으면 그 축에서 **한가운데(`NEUTRAL` = 0.5)** 를 준다. 모르는 것에 상도 벌도
주지 않는다. 덕분에 **"코사인이 낮다고 알려진 자료"가 "모르는 자료"보다 아래로** 간다.

함께 고친 것 둘:
- **예산 컷이 `break` 라 거대한 자료 1건이 나머지를 전부 지웠다.** 요약이 없는 자료는 본문
  전체가 실리므로(`pickContent` — 요약 `null` 이 정상인 경우가 셋) 실제로 가능한 경로다.
  이제 안 들어가는 것만 건너뛰고, **하나도 안 들어갈 때만** 1등 하나를 남긴다.
- **`NaN` 벡터가 유사도 1등을 먹었다.** `real[]` 는 `'NaN'::real` 을 저장할 수 있고 NaN 은
  내림차순 정렬에서 맨 앞으로 간다. `math.isfinite` 로 "값 없음" 처리한다.

## 23. 예산이 실제로는 안 지켜지고 있었다 — **고치다가 같은 버그를 다른 문으로 되살렸다** (2026-08-02)

[#22](#22) 직후 코드 전체를 리뷰하다 발견했다. 자료 절 예산(12,000자)에 우회 경로가 둘이었다.

1. `_select_archive` 의 `len(archive) < 2` 단축이 노드를 통째로 빠져나가 **예산이 안 돈다.**
   그 docstring 은 "결과가 완전히 같아서 왕복만 아낀다"고 적고 있었다 — 거짓이었다.
2. `select_archive` 의 "최소 1건은 남긴다" 폴백이 거대한 것 하나를 **자르지 않고** 통과시킨다.

### ① 실측 — 셋 다 같은 값에서 멈춘다

DB 상한(`ArchiveTextLimits.MAX_BODY_TEXT = 20,000자`)까지 채운 자료로 쟀다.

| 자료 수 | 프롬프트 | 예산 대비 |
|---|---|---|
| 1건 | 20,369자 | 1.70배 |
| 2건 | 20,369자 | 1.70배 |
| 18건 | 20,369자 | 1.70배 |

같은 값인 이유가 곧 두 경로다 — 1건은 ①로, 2건 이상은 ②로 새어 나간다.

> **"컨텍스트 초과 → 영구 500" 은 기각했다.** 리뷰는 40만 자로 33배 초과를 보였지만, 본문을
> 쓰는 **세 경로가 전부 20,000자로 자른다**(`ArchiveCrawlProcessor:74`,
> `ArchiveItemService:145`·`:200`). 천장이 "DB 상한 자료 1건"으로 유계이고 약 20k 토큰이라
> 컨텍스트가 안 넘친다. **운영 사고가 아니라 문서가 거짓인 문제였다.**

### ② ⚠️ 첫 수정이 [#22](#22)에서 고친 버그를 되살렸다

`render_archive_item` 에 상한을 **예산값 그대로** 넣었다. 그러자 거대한 자료의 렌더가 **정확히
12,000자**가 되어 `used(0) + 12000 > 12000` 이 거짓이 됐고, 그 한 건이 예산을 통째로 먹었다.

| | 프롬프트 자료 수 |
|---|---|
| 상한 전 | **17건** (거대한 1건은 `continue` 로 건너뜀) |
| 상한 후 | **1건** ← 나머지 17건이 사라졌다 |

[#22](#22)에서 `break` → `continue` 로 고친 "거대한 1건이 나머지를 지운다"가 **다른 문으로**
돌아온 것이다. 그때 만든 가드 `test_one_huge_item_does_not_silence_everything_after_it` 이
못 잡은 이유는 **가짜 render 를 주입**하기 때문이다 — 진짜 렌더로는 그 성질이 거짓이 돼 있었다.

→ **교훈: 렌더에 상한을 두면 안 된다.** 자르는 일은 **남은 예산을 아는 쪽**이 해야 한다.
최종 형태는 (a) `< 2` 단축을 없애 예산을 항상 태우고(임베딩 왕복만 계속 아낀다),
(b) 폴백 안에서만 본문을 깎는다. 깎는 양은 렌더 초과분 그대로다 — 본문에서 N자를 빼면 렌더도
정확히 N자 준다. **머리(`## id=`)는 남긴다**: 그게 깨지면 모델이 근거 id 를 인용할 수 없어
`filter_candidates` 가 후보를 전부 버리고 **추천이 조용히 빈 목록**이 된다(예산 9자에서 재현 —
모델은 `id=12` 만 보는데 유효 id 는 `123` 이었다).

### ③ 최종 결과

| 상황 | 프롬프트 | 예산 대비 |
|---|---|---|
| DB 상한 자료 1건 | 12,102자 | 1.01배 |
| DB 상한 자료 18건 | 12,102자 | 1.01배 |
| 거대 1건(좋아요 1등) + 평범 17건 | 3,329자 · **17건 전부** | 0.28배 |

초과분 102자는 자료 절 **밖**의 고정 헤더다. 평가 픽스처는 최대 1,126자라 영향이 없다
(기준선 불변).

### ④ 함께 잡은 것 — 테스트가 지키는 척만 하던 자리들

변형을 넣어 테스트가 잡는지 셌다. `ranking.py` 는 8개 중 **7개**를 잡았고, 못 잡은 하나가
하필 [#22](#22) 리뷰에서 고친 `NEUTRAL`(값 없는 축 = 중립)이었다. 게다가 `_similarity`
docstring 은 여전히 "꼴찌 동점"이라고 적고 있었다 — **주석을 읽고 코드를 되돌리면 테스트가
전부 초록인 채로 버그가 복귀**하는 상태였다.

원인은 단언이 **순서**였기 때문이다: `NEUTRAL = 0.0` 이면 unknown 과 worst 가 동점(0.0)이 되고
안정 정렬이 입력 순서를 지켜 같은 결과가 나온다. **점수 부등식**으로 바꾸니 잡힌다
(`[2.0, 0.0, 0.0]`).

같은 방식으로 확인한 나머지: 임베딩 응답 길이 불일치 시 `dict.update(zip(..., strict=True))` 가
**소비하면서 넣어** 버린 벡터가 캐시에 남던 것(응답이 길면 재시도 0회로 그대로 사용),
`/v1/health` 가 추천과 스레드풀을 공유하던 것, 폴백 `except Exception` 이 게이트웨이 장애와
우리 코드 버그를 같은 로그로 수렴시키던 것.

## 24. ★ 후보가 마르는 것을 **실측으로 잡았다** — 제외 창 50 → 16 (2026-08-03)

사용자가 "초반엔 여러 개 떴는데 지금 3개 정도만 뜬다"고 관측했고, LangSmith 로 확인하니
사실이었다.

### ① 관측 — 후보가 8개에서 1~2개로

| 시각 | 입력 토큰 | 후보 |
|---|---|---|
| 11:45 | 2,982 | **8** |
| 13:05 | 2,982 | **8** |
| 21:58 | 4,219 | 5 |
| 21:59 | 4,305 | **1** |
| 22:00 | 4,327 | 4 |
| 22:14 | 4,395 | **1** |
| 22:15 | 4,446 | **2** |

**비용은 오히려 올랐는데 후보는 줄었다.** 후보 1개당 비용이 $0.00011 → $0.00056~0.00116 으로
**5~10배**가 됐다.

### ② 원인은 역할 중복이었다

제외 목록(`excluded_todos`)이 50칸을 채우면서 입력 토큰의 33%(약 1,464 tok)를 먹고, 모델이
피해야 할 제목이 50개라 새로 낼 것이 없어졌다.

**그런데 채택한 후보는 이미 `existing_todos` 로 영구 제외되고 있었다** —
`TodoSuggestionPayloadLoader` 가 방의 투두를 **상한 없이 전부** 싣고 `filter_candidates` 가
그것과 겹치는 후보를 버린다. 노출 기록이 같은 일을 한 번 더 하면서, **채택하지 않은 후보까지
영구히 막고 있었다.**

관측된 방의 숫자가 그것을 보여준다: **채택 2개 vs 제외 50개(채택률 4%).**

### ③ 창 크기 실측 — 같은 방 진짜 데이터, 각 3회

방 "회화 스터디"(자료 18건·벡터 18건·투두 2개·노출 50개)를 DB 에서 그대로 읽어 AI 서버에
보냈다. 바꾼 것은 `excluded_todos` 길이 **하나뿐**이다.

| 제외 창 | 후보 (3회) | 평균 |
|---|---|---|
| **50 (당시)** | 3, 1, 2 | **2.0** |
| 24 | 5, 5, 6 | 5.3 |
| **16 (채택)** | 5, 6, 7 | **6.0** |
| 8 | 8, 7, 7 | 7.3 |
| 0 | 7 | 7.0 |

편차 ±1 인데 효과가 2.0~7.3 이라 **관계가 편차보다 훨씬 크다.** #20 에서 "31↔35 로 갈려
이 표본으로는 못 잰다"고 접었던 것과 대조적이다 — 이번엔 효과가 잡음보다 크다.

**16 = 회당 상한 8개(규칙 6) × 직전 2회차.** 8이 후보 수는 더 낫지만 반복 방지가 한 회차뿐이라,
이 기능을 만든 이유에 너무 가까워진다.

### ④ 함께 확인한 것 — LangSmith 목록 화면의 토큰은 **정확히 6배**다

서버 로그와 1:1 대조했다.

| LangSmith 목록 | 실제(서버 로그) | 배수 |
|---|---|---|
| 6,504 | 1,084 | **6.00** |
| 26,724 | 4,454 | **6.00** |
| 26,442 | 4,407 | **6.00** |
| 27,114 | 4,519 | **6.00** |

트레이스의 중첩 런 여러 층에 같은 사용량이 중복 집계된다. **상세 화면을 열면 맞는 값이 나온다**
(위 27,114 건의 상세는 `4.5K`). **비용은 정확하다** — 4,519 토큰에 $0.0012 가 맞는 값이다.

> 발표·보고에 목록 화면 숫자를 쓰지 말 것. 상세 화면이나 서버 로그를 쓴다.

### ⑤ 노드별 시간 분해 (실측 5.14초)

| 노드 | 시간 | 무엇을 증명하나 |

### ⑥ 응답 시간이 #22 보다 빨라졌다

지금 **3.6~5.6초**다. [#22](#22) 에 적은 9.1~9.4초를 갱신한다. 같은 자료 18건 기준이다.

## 25. ★ 요약 없는 자료가 프롬프트의 98%였다 — 백필로 후보가 살아났다 (2026-08-03)

사용자가 "부산 여행 방 추천이 맘에 안 든다"고 해서 들여다보다 발견했다. 불만은 셋이었다 —
**할 일 내용이 별로 · 카테고리 난립 · 후보가 금방 마름.**

### ① 원인 — 절반이 요약 없이 본문째로 실리고 있었다

`TodoSuggestionPayloadLoader.pickContent` 는 요약·본문 중 **짧은 쪽**을 고른다. 요약이 없으면
본문 전체가 간다. 부산 방 자료 8건을 재보니:

| | 건수 | 프롬프트에 실리는 길이 |
|---|---|---|
| 요약 있음 | 4건 | 529자 (2%) |

### ① 조건

운영이 실제로 보낸 요청을 **캡처 프록시로 그대로 받아 적어** 얼렸다(`evals/data/rooms/`).

`gpt-5.4-nano` · **2방 × 3라운드 × 5반복 = 30회** · temperature 운영 기본값(고정 안 함) ·
1회차는 제외 목록을 비우고 시작(`--start-excluded fresh`).
부산 여행 자료 13건 · 회화 스터디 자료 21건.

> ⚠️ **캡처에서 두 번 걸렸다.**
> ① Spring `RestClient` 는 `Content-Length` 없이 **`Transfer-Encoding: chunked`** 로 보낸다 —
>   그것만 읽는 프록시는 본문을 **0바이트**로 받는다.
> ② 제외 창의 **회차 내부 순서를 서버와 반대로** 짰다(리뷰 지적). 서버는 후보 순서대로
>   `saveAll` 하고 `order by createdAt desc, id desc` 로 읽으므로 **그 회차의 마지막 후보가
>   맨 앞**이다. 회당 8개 상한 아래에서는 남는 집합이 같지만 `build_payload` 가 순서 그대로
>   렌더하므로 프롬프트 문자열이 운영과 달랐다. 고치고 다시 쟀다.

### ③ ★ 여행 방에서만 "실제로 하는 일"이 안 나온다 — **재현됐다**

> ⚠️ **이 지표는 [#28](EXPERIMENTS.md) 에서 무너졌다 — 조건을 비교하는 데 쓰지 말 것.**
> `DOING_VERBS` 는 **이 기준선 출력에서만** 뽑은 목록이라, 조건이 바뀌어 새 동사가 나오면
> (검수를 켜니 `탐방하기`·`체험하기`·`방문해보기` 가 나왔다) 그걸 전부 "계획·확인"으로
> 센다. 아래 14% / 44% 는 **이 기준선을 서술하는 값**으로만 유효하다.
> 조건 비교는 #28 의 **메타 행위 비율**(나쁜 모양을 센다)을 쓴다.

> 본문 길이 분포가 임계값을 쉽게 만든다 — **43자 3건, 그다음이 1,728자**(10 퍼센타일).
> 사이에 아무것도 없어 100~1,000 어디를 잡아도 같은 결과다.

### ⑦ 표본의 한계

**방 2개다.** 3·4번 방은 자료가 0건이라 쓸 수 없었다. 한 방에서 좋아 보인 규칙이 다른 방에서
반증된 전례가 이미 있으므로(2026-08-02, "제목에 자료 이름을 넣지 마라"), 여기서 나온 결론도
세 번째 방에서 뒤집힐 수 있다. ③의 여행/학습 대비는 **정확히 그 위험을 보여주는 결과**이기도
하다 — 방 성격이 결과를 가른다.

측정 전에 테스트용 쓰레기(`ㄹㄹㄹㄹ` 카테고리 · `ㄴㄴㄴ` 투두 · `(없음)` 카테고리)를 DB 에서
지웠다. 안 지웠으면 앞으로 모든 카테고리 측정의 분모에 영원히 꼈을 것이다.

## 27. ★ 카테고리 접기를 **만들고 나서 실측으로 기각했다** (2026-08-03)

`map_categories` 가 제안을 **방의 기존 카테고리하고만** 비교하고 후보끼리는 안 보니까
저것들이 나란히 남는 것이라고 진단했다. 글자 정규화로 접는 층(`_fold_name_variants`)을
만들고 테스트 11개까지 붙였다. **그리고 재보니 전부 틀렸다.**

### ① 변이는 한 회차 안에서 나온 적이 없다

    부산 15라운드 + 오픽 15라운드 = 30라운드   회차내 표기 변이 **0건**

`서베이 전략` 과 `서베이전략` 은 **서로 다른 회차**의 산물이다. `map_categories` 는 한 번의

### ② 임베딩이 이미 접는다 — 글자 층은 중복이다

전부 임계값을 한참 넘는다. 사용자가 한쪽을 채택해 방 카테고리가 되는 순간, 다음 회차의
변이는 임베딩이 알아서 접는다. **마지막 줄이 특히 아프다** — 기획 단계에서 *"`말하기` /
`말하기전략` 처럼 뜻만 가까운 것은 임베딩이 못 잡으니 이 티켓 밖"* 이라고 적었는데
**그것도 틀렸다.** 0.677 로 접힌다.

### ③ `specs/OPEN.md` 대안 (a)"후보끼리 먼저 군집화"도 같은 데이터로 반증된다

    임계값 0.50 에서 회차내 접을 쌍 — 부산 **0쌍** · 오픽 15라운드에 7쌍(라운드당 0.5)

한 시트의 `카페투어`·`해산물`·`여행코스` 는 **진짜로 다른 주제**다. 묶을 게 없다.
임계값을 0.60·0.70 으로 올리면 각각 2쌍·0쌍으로 더 줄어든다.

### ④ 그래서 진짜 숫자는 이것이다

| | 한 시트당 후보 | 한 시트당 카테고리 | 최악 |
|---|---|---|---|
| 부산 여행 | 5.1개 | **3.1종** | 후보 7개에 6종 |
| 회화 스터디 | 4.9개 | **4.1종** | 후보 8개에 7종 |

**거의 후보마다 카테고리가 하나씩이다**(후보당 0.62 / 0.85종). 프롬프트 규칙 4 는
*"개별 행동이 아니라 여러 투두를 묶을 수 있는 이름"* 을 요구하는데 모델이 안 지킨다.

즉 카테고리 난립은 **매칭 문제가 아니라 생성 문제**다. 접는 층을 어떻게 만들어도 안 줄어든다.
고치려면 후보를 낸 뒤 카테고리를 다시 배정하는 층이 필요하고, 그건 LLM 패스를 한 번 더 도는
자리(의 critique 노드)와 같다.

### ⑤ 교훈

**집계된 목록을 보고 원인을 단정했다.** 15라운드를 합친 카테고리 목록에 변이 쌍이 보였고,
그것이 "한 번에 같이 나온다"는 뜻이라고 읽었다. 라운드별로 갈라보는 데 5분이면 됐고
코사인 6쌍을 재는 데 1분이면 됐다 — **구현 전에 그걸 했으면 티켓이 필요 없었다.**

같은 실수를 [#22](EXPERIMENTS.md)에서 반대 방향으로 겪었다(확정 설계였던 RRF 를 실측으로
기각). 그때 얻은 규칙이 여기서도 그대로다 — **고치기 전에, 고치려는 것이 실제로 그 모양인지
먼저 잰다.**

되돌린 구현은 커밋하지 않았다. 다시 필요해지는 조건은 위 테스트가 지킨다 — 임계값이나
임베딩 모델이 바뀌어 변이 쌍이 안 접히게 되면 그 테스트가 깨진다.

## 28. ★ 후보 자기 검수 — **효과는 있는데, 내가 만든 지표가 그걸 못 봤다** (2026-08-03)

> 근거 파일: `evals/data/snapshots/2026-08-03_room_ab*.json` 5개 ·
> `tests/test_snapshot_critique_ab.py` 가 크레딧 0으로 단언한다.

[#26 ③](EXPERIMENTS.md)이 잡은 문제 — 여행 방 후보가 `동선 짜기`·`코스로 묶기`·`10곳 중
1곳 고르기` 로 빠진다 — 을 고치려고 **검수 노드**를 넣었다. 생성 뒤에 LLM 을 한 번 더 불러
"바로 실행할 수 없는 후보"를 반려한다. 프롬프트 규칙을 늘리지 않은 이유는 [#6](EXPERIMENTS.md)
(규칙 하나 추가 → 14/15 에서 10/15 로 후퇴)과 [#21](EXPERIMENTS.md)(문구 네 가지 전부 0개)이다.

`gpt-5.4-nano` · 2방 × 3라운드 × 5반복 = 30회 · `critique_max_attempts` **0/1/2** ·
**1과 2는 두 번씩** 돌렸다.

### ① 첫 결론은 틀렸다 — 한 번씩만 재고 좋아했다

처음 한 번씩 재고 이렇게 적을 뻔했다: *"부산 실제행동 12% → 22%, 오픽 35% → 50%, 카테고리
22종 → 10종."* **재현이 안 됐다.**

| #26 지표(좋은 동사 비율) | 부산 | 오픽 |
|---|---|---|
| 0 (검수 없음) | 12% | 35% |
| 1 — 1차 | 22% | 50% |
| 1 — **2차** | **9%** | **36%** |

**2차는 기준선보다도 낮다.** 흔들림이 효과보다 컸다. [#26 ②](EXPERIMENTS.md)가 "회차 평균이
실행마다 ±0.7 움직인다"고 적어뒀는데 그걸 알고도 n=1 로 결론을 냈다.

카테고리 감소도 이득이 아니었다 — **후보가 줄어서 생긴 부산물**이다.

    카테고리 ÷ 고유 후보 :  0 → 0.53 · 1(1차) → 0.54 · 1(2차) → 0.51   (오픽, 사실상 동일)

### ② 눈으로 보니 검수는 확실히 작동하고 있었다

지표를 믿지 못하게 됐으니 출력을 나란히 놓고 봤다(부산, 반복 1~2).

    검수 없음 (35개)                         검수 켬 (13개)
    KTX 이동 동선 중심으로 코스 재정리하기        감천문화마을 골목 탐방하기
    감천문화마을-남포동-흰여울 동선 다시 짜기       고래사어묵해운대점 어묵 맛보기
    개미집·18번완당집 위치/동선 확인해서 묶기      런닝맨 부산점 실내 액티비티 체험하기
    대저생태공원-을숙도 코스 경로 짜기            부네치아 방문해보기
    모모스커피 영도 미피카페 일정에 묶기           부산역 초량해 칼국수 점심 가기
    영도 미피카페·모모스커피 방문 후보로 정하기     해운대 씨라이프 부산아쿠아리움 방문하기
    부네치아 등 가볼만한 곳 목록에 추가하기        해운대블루라인파크 이용해보기

**계획 행위가 통째로 사라졌다.** 남은 `확인하기` 도 전부 대상이 특정돼 있다
(`더웨이브펜션 체크인 3시/체크아웃 11시 확인하기`).

### ③ ★ 지표가 틀린 이유 — 좋은 동사를 **열거**하려 한 것

#26 의 `DOING_VERBS` 는 **검수 없는 출력에서만** 뽑은 목록이다. 검수를 켜니 `탐방하기` ·
`체험하기` · `방문해보기` · `가기` · `이용해보기` 가 새로 나왔는데 목록에 없어서 전부
"계획·확인"으로 세어졌다. **좋은 동사는 열린 집합이라 열거할 수 없다.**

반대로 **사용자가 지목한 나쁜 모양은 닫힌 집합**이다. 그걸 세니 재현됐다.

| 메타 행위 비율 (`짜기`·`묶기`·`넣기`·`고르기`·`정하기`…) | 부산 | 오픽 |
|---|---|---|
| **0 (검수 없음)** | **40%** (33/82) | 12% |
| **1 (검수만)** | **0%** · **6%** | 8% · 7% |
| 2 (재생성 1회) | 22% · 3% | 5% · 3% |

**40% → 0~6%.** 두 실행의 차이(6%p)가 효과(34%p)보다 훨씬 작다 — 이번엔 결론이 선다.

> ⚠️ **지표를 데이터에 맞춘 것 아닌가?** 순서는 이랬다 — 재현 실패 → 출력을 눈으로 대조 →
> 무엇이 사라졌는지 확인 → 그걸 셈. `ai/CLAUDE.md` 가 정한 순서 그대로다. 동사 목록은
> 사용자가 든 불만 예시(`코스로 묶기`·`10곳 중 1곳 체크하기`)에서 나왔다. 목록을 늘려 결과를
> 바꾸지 못하게 테스트에 `frozenset` 으로 박아뒀다.

### ④ `critique_max_attempts = 1` — **2가 나빠서가 아니라, 구분이 안 돼서**

착수 계획은 2(최초 1회 + 재생성 1회)였다. 처음엔 *"2 는 일관성이 없고 지연만 더 든다"* 고
적었는데 **그건 틀렸다**(2026-08-03 리뷰). 실제 4개 축은 이렇다.

| | 부산 메타 | 오픽 메타 | 지연 평균 | 후보 수 |
|---|---|---|---|---|
| 1 | 0% · 5.9% | 7.7% · 6.6% | 6.29 · 5.48초 | 41 · 42개 |
| 2 | 22.4% · 3.0% | **5.5% · 3.2%** | **6.00 · 5.43초** | **52 · 43개** |

**3개 축에서 2 가 같거나 낫다.** "지연만 더 든다"는 정반대였다 — 2 가 오히려 빠르다.
"2 기각"은 사실상 **부산 1차의 22% 하나**에 걸려 있었고 2차는 3.0%다.

그리고 이 절이 ①에서 세운 기준(*"두 실행의 차이가 효과보다 훨씬 작아야 결론이 선다"*)을
1 vs 2 는 **통과하지 못한다** — 군간 차 9.7%p < 조건 2 자신의 군내 흔들림 19.4%p.

**그래서 근거를 바꿔 적는다: 데이터로는 둘을 구분할 수 없다. 그래서 싼 쪽인 1 을 쓴다**
(라운드당 LLM 호출이 정확히 2회 · 2 는 최악 4회). 재생성이 왜 안 통하는지에 대한 설명은
없다 — 있는 척하지 않는다.

⚠️ **이건 ① 에서 고백한 n=1 오류와 같은 종류다.** ① 에서는 조건당 1회로 결론을 냈고,
④ 에서는 n=2 의 spread 를 통계처럼 썼다. n=2 의 폭은 통계가 아니다.

⚠️ **그래서 `critique → generate` 되돌아가는 엣지는 운영에서 안 탄다.** 이 티켓의 명분이
그 루프였는데 결과가 이렇다. 코드는 남긴다 — 설정 하나로 다시 잴 수 있어야 하기 때문이다.

### ④-1 ★ **LangGraph 는 이 티켓 뒤에도 기능 이득이 없다** — 과장을 한 번 썼다가 지웠다

이 절의 초안에 *"그 A/B 를 싸게 만든 것이 그래프의 값"* 이라고 적었다. **그것도 과장이다.**
설정으로 갈래를 나누는 것은 함수에 `if` 하나 넣어도 똑같이 된다.

냉정하게 하나씩 따지면 이렇다.

| | LangGraph 여야 했나 |
|---|---|
| `critique` 노드 | ❌ 함수 하나 더 부르는 것과 같다 |
| `critique → END`(전부 반려 → 빈 목록) | ❌ `if not candidates: return []` |
| `attempts`·`rejected` 상태 전달 | ❌ 지역변수로 충분 |
| `--critique 0/1/2` A/B | ❌ `if` 하나면 된다 |
| `critique → generate` 되돌아가기 | ✅ **그런데 안 쓴다** |
| Studio 시각화 | ✅ 개발 도구, 사용자에게 가는 값은 아니다 |

**품질을 올린 것은 "검수"라는 아이디어이지 그래프가 아니다.** 발표·문서에서
"LangGraph 덕분에 좋아졌다"고 말하면 거짓이다. 사실은 *"루프를 만들고, 재보고, 데이터가
아니라고 해서 껐다"* 이고, 그쪽이 더 정확하며 더 나은 이야기이기도 하다.

### ⑤ 대가 — 후보가 절반 이하로 준다

| 부산 | 1회차 | 2회차 | 3회차 | 총 후보 |
|---|---|---|---|---|
| 0 | 7.00 | 5.20 | 5.40 | 88개 |
| 1 | 3.20 · 3.20 | 3.00 · 3.60 | 2.00 · 1.60 | 41 · 42개 |

**3회차는 최소 0 이 실제로 나왔다.** 빈 목록을 허용한 결과다(2026-08-03 사용자 확정 —
나쁜 후보를 보여주느니 안 보여준다). 사용자가 이 거래를 알고 받았다.

토큰은 46,082 → 64,795(부산 15라운드 합)다.

**지연은 상한을 가끔 깬다** — 초안에 "3.9 → 5.8초로 7초 상한 안"이라고 적었는데 **평균만
본 것이었다**(2026-08-03 리뷰).

| | 라운드 평균 범위 | **7초 이상** | 최악 |
|---|---|---|---|
| 0 (검수 없음) | 3.58~3.87초 | **0 / 30** | 5.05초 |
| **1 (채택)** | 5.30~**6.79**초 | **8 / 60 (13%)** | **10.88초** |

**검수가 최악을 두 배로 만든다**(5.05 → 10.88초). 평균 +1.8초만 보면 안 보이는 사실이다.
사용자가 처음 받은 거래에는 이게 없었다 — 알리고 **다시 확정받았다**(2026-08-03, 검수 유지).

검수 호출 자체는 **+1,247 prompt tok · +165 completion tok · +1.82초**다. 토큰이 적은데도
1.8초인 것은 게이트웨이 왕복의 고정 비용이고, **더 빠른 모델이 없다** — 우리가 재본 셋 중
`gpt-5.4-nano`(3.13초)가 이미 제일 빠르다(`gpt-4.1-mini` 10.94초 [#18], `gpt-5-nano`
12.9~23.9초 [#14]).

### ⑥ 학습 방은 안 망가졌다

회화 스터디는 원래 메타 행위가 12% 로 적어서 개선 여지가 작았고, 검수 후 7~8% 다.

## 29. 부분 반려분 재생성 — **품질은 올랐는데 지연이 못 버틴다. 기각** (2026-08-03)

> **결론: 기각.** 코드는 남기고 스위치(`regenerate_on_partial_reject`)를 **끈 채로** 둔다 —
> 조건 하나로 다시 잴 수 있게. 수치는 커밋된 스냅샷
> `evals/data/snapshots/2026-08-03_room_partial_run{1,2}.json` 에서 나오고
> `tests/test_snapshot_partial_retry.py` 가 단언한다.

### 왜 했나

[#28](#28) ⑤ 가 남긴 대가다. 검수를 켜니 부산 총 후보가 88 → 41개로 줄었고 3회차는 0이
나왔다. 원인은 **반려분을 그냥 버리기 때문**이다 — -235 의 되돌아가는 엣지는 "전부 반려"일
때만 도는데 그게 거의 없어서 운영에서 안 탔다. 흔한 것은 "3개 통과 · 4개 반려"이고 그 4개가
아무것도 안 남긴다.

**조건**: `critique_max_attempts=2` + `regenerate_on_partial_reject=True`. 기준선은 #28 의
`critique=1` 스냅샷 두 개를 **재실행 없이 재사용**했다(그 동일성은 `tests/test_partial_retry.py`
가 고정한다). 처치군은 두 번 돌렸다 — #28 ① 에서 한 번 데였기 때문이다.

### ① 후보는 확실히 회복했다 — 목적 자체는 달성

| 총 후보 | 기준선 ×2 | 처치 ×2 |
|---|---|---|
| 부산 여행 | 41 · 42개 | **109 · 88개** |
| 회화 스터디 | 55 · 63개 | **93 · 103개** |

### ② 그런데 방마다 **방향이 반대**다 — 이게 이 실험의 핵심 관측

| 메타 행위 비율 | 기준선 ×2 | 처치 ×2 | |
|---|---|---|---|
| 부산 여행 | 0.0% · 5.9% | **7.6% · 12.7%** | ❌ 나빠졌다 |
| 회화 스터디 | 7.7% · 6.6% | **4.3% · 3.0%** | ✅ 좋아졌다 |

**하필 부산이 사용자가 불만을 제기한 방이다.**

⚠️ **다만 "부산이 나빠졌다"는 이 실험이 스스로 세운 기준을 통과하지 못한다**(2026-08-03 리뷰).
지연에서는 "군내 흔들림 3%p 대 효과 34%p" 라고 대비를 명시했는데, 메타 비율에는 그 대비를
안 했다. 같은 잣대를 대면 이렇다.

| | 군내 흔들림(기준선 두 실행 차) | 군간 차 | 배수 |
|---|---|---|---|
| 부산 | 5.9%p (0.0 ↔ 5.9) | 7.2%p | **1.2배** |
| 오픽 | 1.4%p (7.7 ↔ 6.6) | 3.5%p | **2.5배** |

즉 **오픽 개선은 견고하고, 부산 악화는 흔들림과 크기가 비슷하다.** 정확한 서술은 "부산이
기준선 두 실행을 모두 넘었지만 그 차가 기준선 자체의 흔들림만 하다"이고, **왜 그런지는 모른다.**

초안에는 "fail-open 오염 탓"이라고 적었다가 → "오염 탓이 아니다(2차는 fail-open 이 더 적은데
메타는 더 나빴다)"로 물렀다가 → 지금 문면으로 두 번 고쳤다. **두 번째 정정의 근거였던
`4회 vs 6회` 는 n=2 상관이고 그 수치 자체가 아래 ④ 처럼 커밋된 근거가 없다.** 어느 쪽도
단정할 데이터가 아니다.

**기각 사유는 ③(지연) 하나로 이미 충분히 선다.** 이 관측은 기각 근거가 아니라 후속을 위한
기록이다.

### ③ 기각 사유는 지연이다 — 두 실행이 거의 붙는다

| | 평균 | **10초 이상** | 최악 |
|---|---|---|---|
| 기준선 ×2 | 5.54 · 6.22초 | **0/30 · 1/30 (0% · 3%)** | 7.82 · 10.88초 |
| 처치 ×2 | 9.63 · 9.54초 | **11/30 · 12/30 (37% · 40%)** | **13.78 · 15.46초** |

37% 와 40% 차이는 3%p 인데 효과는 34%p 다 — **변동이 아니라 구조다.** 라운드당 LLM 호출이
2회에서 4회가 되고, 착수 전 산수(약 10.6초)가 그대로 나왔다.

⚠️ **이 수치는 오히려 관대하다.** fail-open 라운드는 반려가 없어 재생성을 안 하므로 LLM 2회로
끝난다 — 즉 싸다. 237 이 실제로 발동한 라운드만 세면 지연은 이보다 나쁘다.

**상한 10초는 사용자가 이 티켓 착수 시점에 7초에서 올려준 값이다.** 올려주고도 깨졌다.

### ④ 🔴 곁가지로 **-235 의 결함**을 발견했다 — 검수가 조용히 우회된다

측정 중 로그에 이게 반복됐다.

    ERROR 검수 판정 개수가 안 맞는다(후보 8개, 판정 7개) — 전부 통과시킨다
    ERROR 검수 판정 개수가 안 맞는다(후보 6개, 판정 5개) — 전부 통과시킨다
    ERROR 검수 판정 개수가 안 맞는다(후보 7개, 판정 6개) — 전부 통과시킨다

**부산 방에서 반복됐고 회화 스터디에서는 한 번도 안 봤다.** 콘솔에 센 것은 15라운드 중
6회(1차)·4회(2차)다.

🔴 **그 횟수에는 커밋된 근거가 없다**(2026-08-03 리뷰 P1-1). 라운드 레코드에 fail-open 필드가

확실한 것은 이것뿐이다 — **판정 개수가 후보보다 정확히 하나씩 모자란 응답이 부산 방에서

**-237 이 만든 것은 아니다** — `_critique` 는 -235 이후 이 티켓에서 한 글자도 안 바뀌었다.

## 30. ★ 검수가 조용히 우회되던 원인 — **번호를 `0` 부터 매긴 것** (2026-08-03)

[#29](#29) ④ 가 남긴 🔴 항목을 닫는다. 근거는 `data/snapshots/2026-08-03_critique_index_probe.json`
과 `2026-08-03_room_index1_run{1,2}.json`, 단언은 `tests/test_snapshot_critique_index.py`.

### ① 무엇이 문제였나

`_critique` 는 후보에 번호를 붙여 보내고 **판정 개수가 후보 수와 다르면 배치 전체를 통과**
시킨다(fail-open, 의도된 정책). 그런데 그게 반복해서 걸렸고 로그가 전부 `후보 N개, 판정 N-1개`
였다. 그 라운드는 **검수를 안 한 것과 같다.**

### ② 검수만 떼어내 쟀다 — 방 평가의 1/13 값

방 평가는 한 실행에 프롬프트 13만 토큰이다(실측: 부산 15라운드 64,996 + 오픽 78,752). 검수는
**제목만** 보내므로 훨씬 싸다 — ⚠️ **다만 프로브는 토큰을 안 모은다**(`run_room_eval.py` 는
`UsageCollector` 로 모은다). "호출당 1천 토큰 수준"은 **추정이지 실측이 아니다.** 입력은 새로
생성하지 않고 [#28](#28) 의 `critique0` 스냅샷에 있는 **실제 후보 묶음**을 썼다.

| 첫 번호 | 판정 개수가 맞은 라운드 | 응답 모양 |
|---|---|---|
| `0` (당시 운영) | 20/30 — **10회(33%)가 하나 모자람** | 번호가 `0..n-2` 로 연속 |
| `1` | **30/30** | — |

프롬프트(`CRITIQUE_PROMPT`)와 스키마 설명은 **그대로 두고 번호만** 바꿨다. 그래야 [#6](#6)
전례대로 "재지 않은 것을 배포"하지 않는다.

### ③ 개수가 아니라 **짝**이 문제였다

개수만 모자란 게 아니었다 — **판정이 엉뚱한 후보에 붙었다.** 반려 사유를 후보 제목과 대조해
세면(글자 2-gram 겹침, `tests/test_snapshot_critique_index.py::shifted_rejections`):

| 첫 번호 | 사유가 **바로 다음 후보**를 설명한 반려 |
|---|---|
| `0` | **12건** |
| `1` | **0건** |

예: `opic_8` 의 `index=6` 사유가 7번 후보(`시험 40분 동안 12~15개 콤보 …`)를 설명했다. 즉
**개수가 우연히 맞았다면 fail-open 이 안 걸리고 엉뚱한 후보가 반려됐을 것**이다 — `_critique`
docstring 이 "조용해서 알아챌 방법이 없다"고 경고한 그 시나리오가 실재한다. 지금까지 그걸
막아준 것은 개수 검사뿐이었다. **이 처방이 고친 것은 개수가 아니라 짝이다.**

### ③-1 ⚠️ "꼬리가 빠진다"는 틀렸다 — 그리고 가설도 기각 못 한다

**초안에 *"빠지는 것은 첫 번호가 아니라 꼬리다"* 라고 쓰고 `OPEN.md` 의 가설(*"모델이 0번을
빼고 답한다"*)을 기각했는데, 둘 다 데이터가 뒷받침하지 않는다**(2026-08-03 리뷰 P0-1).

- 응답은 항상 `0..n-2` 로 **연속**이다. 개수 검사를 통과한 뒤라면 빠진 번호는 **반드시**
  `n-1` 이 된다 — **관측이 아니라 산수다.** 그걸 "꼬리 후보가 빠졌다"로 읽은 것이 오독이고,
  그 근거라며 걸어둔 테스트는 **어떤 가설에서도 참인 항진명제**였다.
- **빠진 번호 라벨 ≠ 판정을 못 받은 후보.** `opic_8` 에서 꼬리 후보는 **판정을 받았다** —
  라벨 `6` 을 달고서.
- **밀림 시작점이 묶음마다 다르다.** `opic_8` 은 `index=1`·`5` 가 라벨과 정확히 맞고 `6`
  부터 밀린다. `busan_8c` 는 `index=4` 에서 이미 밀렸다.
- 따라서 **어느 후보가 건너뛰어졌는지는 확정할 수 없다** — 통과 판정에는 사유가 없어서 그
  구간을 대조할 방법이 없다.
- `OPEN.md` 의 가설은 `opic_8` 에서 **반증된다**(`index=1` 이 라벨과 맞으니 0번이 빠진 게
  아니다). `busan_8c` 는 그 가설과 모순되지 않지만 확정도 안 된다.

**왜 0-based 일 때만 이러는지는 모른다.** 아는 것은 `1` 부터면 30/30 이고 밀림이 0건이라는
것뿐이다.

### ④ 방마다가 아니라 **묶음마다** 결정적이다

6개 묶음 중 `busan_8c`·`opic_8` 만 걸렸고, 걸린 묶음은 **5/5**, 안 걸린 묶음은 **0/5** 였다.
무작위가 아니라 입력에 달렸다. #29 에서 부산 방에만 몰려 보인 것은 그 방의 후보 묶음 탓이고,
**다른 방이 안전하다는 뜻이 아니다** — 오픽 묶음도 걸렸다.

가설 B(뜻이 겹치는 제목을 모델이 하나로 합친다)는 **기각**이다. `near_dup` 묶음은 두 조건 모두
0/5 였다. 강한 형태(글자가 같은 제목)는 애초에 불가능하다 — `filter_candidates` 가 `_normalize`
기준 중복을 검수 **전에** 버린다.

### ⑤ 방 평가 — 목적은 달성, 품질은 **구분되지 않는다**

| 실행 | fail-open | 부산 메타 | 오픽 메타 | 부산 후보 | 오픽 후보 | 10초 초과 | 최악 |
|---|---|---|---|---|---|---|---|
| 기준선 `critique1` #1 (0-based) | 기록 없음 | 0.0% | 7.7% | 41 | 55 | 0/30 | 7.82s |
| 기준선 `critique1` #2 (0-based) | 기록 없음 | 5.9% | 6.6% | 42 | 63 | 1/30 | 10.88s |
| **1-based #1** | **0/30** | 6.1% | 1.8% | 41 | 58 | 1/30 | 10.10s |
| **1-based #2** | **0/30** | 3.0% | 7.9% | 38 | 64 | 1/30 | 14.31s |

- **fail-open 0/30 · 0/30.** 이 값이 파일에 남은 것은 처음이다(계수기는 -237 에서 붙였다).
- ⚠️ **"0 → 0" 이라고 쓰면 안 된다.** 기준선에는 그 필드가 **없다** — 비교 대상이 아니라
  "이제부터 보인다"가 맞는 서술이다. `test_snapshot_critique_index.py` 가 그걸 단언한다.
- ⚠️ **품질이 좋아졌다고 말할 수 없다.** 방마다 기준선의 최선보다 나쁜 실행이 하나씩 있다
  (부산 6.1% > 0.0%, 오픽 7.9% > 6.6%). 두 실행의 폭이 기준선의 폭만큼 넓다. 실측이 말하는
  것은 **"구분되지 않는다"**까지다.
- **후보 수는 그대로다**(41·38 / 58·64 vs 41·42 / 55·63). 검수가 실제로 걸리기 시작했는데도
  안 줄었다.
- ⚠️ **최악 지연은 커졌다**(10.88 → **14.31초**, 네 실행 통틀어 최댓값). 같은 실행의 차순위가
  7.09초라 **단발 스파이크로 보이지만 확인한 것은 아니다.** 상한 초과 횟수는 1/30 으로
  **기준선의 나쁜 쪽과 같다**(기준선은 0/30·1/30).
- ⚠️ **초안에 "중앙값·평균이 기준선보다 빠르다"고 썼는데 틀렸다**(2026-08-03 리뷰 P1-3).
  실제로는 기준선의 폭과 겹친다 — 처치군 평균 하나(6.387초)는 기준선 최댓값(6.221초)보다
  **높다.** `test_snapshot_critique_index.py` 가 이제 이 값들을 단언한다.

  | | 기준선 #1 | 기준선 #2 | 1-based #1 | 1-based #2 |
  |---|---|---|---|---|
  | 평균 | 5.541 | 6.221 | **6.387** | 5.848 |
  | 중앙값 | 5.465 | 5.925 | 5.920 | 5.635 |

### ⑥ 남은 한계

- **기전을 모른다.** 증상을 없앤 것이지 왜 그런지 안 것이 아니다. 모델이 바뀌면 다시 나올 수
  있고, 그때 알아채는 유일한 수단이 러너 계수기다.
- **묶음 6개다.** 그중 2개가 걸렸다는 33% 는 이 6개에 대한 값이지 모집단 비율이 아니다.
- **"후보 8개일 때만 생기는가"는 가르지 못했다.** 불일치 10건이 전부 `n=8` 이지만 `n=8` 묶음
  다섯 중 셋은 깨끗했다 — 크기만으로는 불충분하다는 것까지다. `n=7` 표본이 `busan_7` 하나뿐이라
  크기가 **필요조건**인지는 이 데이터로 못 말한다.
- **밀림 판별기는 휴리스틱이다.** 글자 2-gram 겹침이라 사유가 짧고 일반적이면 틀린다 —
  `one_based` 에서 2건이 그렇고, 눈으로 확인해보니 둘 다 정상이었다(`TestTheShiftDetectorIsHonest`
  가 이름을 대고 남겨둔다). 동결 데이터라 결과는 결정적이지만 정밀한 도구는 아니다.
- **`0` 이 왜 나빴는지 모르므로 `2` 부터·문자 라벨 같은 다른 안은 재보지 않았다.** 필요가 없다.
- **A/B 가 시간에 교락돼 있다**(리뷰 P2-4). 루프가 `조건 → 묶음 → 반복` 순서라 앞 30회가 전부
  `zero_based`, 뒤 30회가 전부 `one_based` 다. 게이트웨이 상태가 그 사이에 변했다면 구분할
  방법이 없다 — 라운드별 타임스탬프도 안 남겼다. 다시 잰다면 루프 순서를 뒤집을 것.
- **[#28](#28) 의 대표 수치(`메타 행위 40% → 0~6%`)는 여전히 "검수가 매번 걸렸다"는 전제 위에
  있다.** 다만 그 스냅샷의 부산 방 후보 수에 8이 하나도 없어(최대 5·6) 오염 가능성은 낮다.
  **대리지표이므로 단정하지 않는다** — 되재려면 그 조건을 다시 돌려야 한다.

## 31. ★ 카테고리 배정을 **세 번 시도하고 세 번 실패해서, 기능을 걷어냈다** (2026-08-04·243)

AI 가 카테고리를 정하는 기능을 **제거했다.** 후보는 카테고리 없이 나가고(= 기타/미분류)
사용자가 투두 탭에서 직접 분류한다. 되살리는 법은
[`RESTORE-category-assignment.md`](RESTORE-category-assignment.md).

### ① 임베딩으로는 못 한다 — 두 방향 다 재봤다 (크레딧 0)

`map_categories`(코사인 0.50)가 실사용에서 **10/10 실패**한다는 것은 [#25](#25) ⑤ 에 있다.
남은 물음은 "임계값이 문제인가, 방법이 문제인가"였다.

**접기 방향** — 이름끼리 비교. `부산 맛집 ~ 요리 0.348` · `미식여행 ~ 카페 0.146`.
0.35 까지 내려야 접히는데 그러면 무관한 것도 접힌다.

**떼어내기 방향** — 게이트를 뒤집어 "제목이 그 카테고리에 안 맞으면 새로 만든다"로. 제목이
10~30자라 신호가 더 많을 것으로 봤다. 커밋된 스냅샷의 (제목, 카테고리) 쌍 1,140건을 임베딩해
쟀다.

| 방의 어휘 크기 | 부산 중앙값 차 | 오픽 중앙값 차 |
|---|---|---|
| 4종 | −0.013 | +0.026 |
| 6종 | −0.030 | +0.015 |
| 8종 | −0.030 | −0.001 |

어휘에 **속하는** 제목과 **속하지 않는** 제목이 그 어휘에 대해 같은 점수를 낸다(차이 ±0.03).
임계값을 어디에 둬도 안 갈린다. 뿌리는 [#17](#17) 과 같다 — **한 방 안의 텍스트가 전부 같은
도메인이라 코사인이 좁은 띠에 몰린다.**

⚠️ 곁가지: 오픽 어휘 4종에서 자기 카테고리를 68.7% 집어내는데 6종으로 늘리면 **45%로
무너진다.** 늘어난 둘이 `모의고사`·`시험 준비`로 `시험준비`와 거의 같은 말이다 —
**난립이 스스로를 악화시킨다.**

### ② LLM 별도 호출 — 프로브는 좋았는데 방 평가가 뒤집었다

`critique` 와 같은 구조로 분류 전용 호출을 뒀다. [#21](#21) 이 실패한 이유가 "생성 프롬프트
안에서 시켜서"라고 보고, 판단만 하는 호출로 떼면 풀릴 것으로 봤다(검수가 그렇게 성공했다).

**프로브(96회)는 통과였다.** 지연 1.87초(중앙) · **전부한곳 0건**([#21] 미재현) · 어휘가
크면 새 카테고리 77% → 5%.

**모델 선택은 실측이 뒤집었다.** `gpt-5-nano` 로 가려 했으나 **지연 중앙 19.65초**(최악
40.97초)였다 — completion 2,813 tok 인데 실제 답은 136 tok 이고 나머지가 숨은 추론 토큰이다.
[#14](#14) 가 요약에서 본 현상이 출력이 짧아도 그대로 났다. 상한 10초라 쓸 수 없다.
`gpt-5.4-nano` 는 1.87초.

**그런데 방 평가에서 뒤집혔다.** 지표는 [#27](#27) 이 정한 **후보당 카테고리 종수**다.

| 실행 | 부산 | 오픽 | 후보 수 | 10초 초과 |
|---|---|---|---|---|
| 임베딩 채택끔 #1 | **0.82** | **0.90** | 41 / 58 | 1/30 |
| 임베딩 채택끔 #2 | **0.80** | **0.88** | 38 / 64 | 1/30 |
| 임베딩 채택켬 | **0.89** | **0.87** | 33 / 50 | 0/30 |
| LLM 채택끔 | 0.96 | 0.97 | 37 / 55 | 0/30 |
| LLM 채택켬 | 0.91 | 0.97 | 44 / 62 | 0/30 |

**5/5 비교에서 전부 LLM 쪽이 나쁘다** — 방향은 일관된다.
**0.97 은 후보 하나당 카테고리 하나**라는 뜻 — 고치려던 문제가 심해졌다.

⚠️ **크기는 방마다 다르게 말해야 한다**(2026-08-04 리뷰 P1-1 에서 정정).

| 방 | 쌍별 차이 | 기준선 편차 | 말할 수 있는 것 |
|---|---|---|---|
| 오픽 | 0.067~0.102 | 0.033 | **편차를 넘는다** — 확실하다 |
| 부산 | 0.016~0.160 | **0.094** | 방향만. 짝맞춘 비교(채택켬끼리)가 **0.0155** 로 편차 안이다 |

초안에 *"조건 안 편차가 0.02 인데 차이는 0.08~0.16"* 이라고 적었는데 **틀렸다.** 0.02 는
`index1_run{1,2}` 둘만 센 값이고, 조건을 맞춘 대조군(`embed_adopt` 0.89)을 빼고 센 것이었다.

원인은 프로브가 이미 보여줬다: **새 이름의 46%가 투두 제목을 거의 그대로 베낀다**
(`해운대 블루라인파크 이용시간` · `씨라이프 부산아쿠아리움 관람`). 이름 길이 규칙을 8자로
조여 중앙 11자 → 5자가 됐는데도 그 비율은 **47%로 안 변했다.**

⚠️ **지연은 문제가 아니었다.** LLM 호출이 3회가 됐는데도 10초 초과 0/30(기준선 1/30).
`match` 노드가 임베딩을 안 부르게 되면서 상쇄됐다. **비싸서 기각이 아니라 효과가 없어서다** —
[#29](#29) 와 기각 사유가 다르다.

### ③ ⚠️ 측정 과정에서 같은 오독을 두 번 했다

**"부산 카테고리가 14종 → 28종, 2배 악화"라고 보고했는데 틀렸다.** 그 숫자는 **5개 반복을
합집합**한 값이다. 반복은 서로 독립된 세션(제외 목록을 비우고 3번 누르기)이라 **사용자가
겪을 수 없는 수**다. 세션 하나 기준으로는 4.7 → 6.4종이다.

[#30](#30) 에서도 스냅샷 10개를 합쳐 "131종"이라고 적었다. **합집합을 사용자 경험처럼
읽는 것이 반복되는 실수다.** 카테고리를 잴 때는 **후보당 종수**를 쓴다.

### ④ 그래서 기능을 걷어냈다

세 방법이 다 실패했고, 제품 쪽에서 **"후보를 전부 기타로 내보내고 사용자가 직접 분류"**
로 결정했다.

⚠️ **오늘 실제로 있는 경로는 드래그가 아니다** — 채택하면 기타로 들어가고, 편집 시트에서
카테고리를 고른다(`todo_form_sheet.dart`). 드래그 UI 는 앱 어디에도 없다(2026-08-04 리뷰
P1-7 에서 잡혔다. 초안이 열 곳에 "드래그로 분류한다"를 현재형으로 적었다). AI 가 풀지 못한 문제를 UI 로 우회한 것이고, 그게 가장 싼 해법이다.

받는 쪽은 한 줄도 안 고쳤다 — Spring 의 `AiCandidate` 는 record 라 키가 없으면 `null` 이고,
앱 `_resolveCategoryId` 는 빈 이름을 기타로 해석한다. **양쪽 다 이미 null 을 정상 경로로
처리하고 있었다.** 그 전제는 `HttpTodoSuggestionClientTest.aResponseWithoutCategoryStillParses`
가 지킨다 — 전역 Jackson 설정이 바뀌면 거기서 깨진다.

**되살리는 것은 커밋 두 개를 함께 revert 하는 것이다**(`Feat!` + 그 위의 `Fix`). 하나만
되돌리면 4개 파일에서 충돌한다. 절차와 주의는 `RESTORE-category-assignment.md`.

### ⑤ 남은 한계

- **`run_room_eval` 은 후보를 채택하지 않는다.** 그래서 방의 카테고리가 회차를 거쳐도 안
  자란다 — 실사용과 다르다. `--adopt-categories`(전부 채택 = 상한)를 만들어 양쪽을 다 쟀고,
  결론은 두 조건에서 같았다. ⚠️ **그 플래그(`--adopt-categories`)는 mainline 에 올라간 적이

## 32. 요약 분량을 "두 배"로 못 늘렸다 — 1.43배가 한계였고, 하한은 규칙을 깬다 (2026-08-04)

**요청**: "AI 요약 분량을 지금의 두 배 정도로." 목표 200자 → 300자.

**방법**: 픽스처 15건(`evals/data/summaries/`)을 프롬프트 네 조합으로 각각 다시 얼려 길이 분포와
[#15](#15) 의 이진 관측(계정명·날짜·어투·따옴표·목록 기호)을 함께 봤다. `summarize_fixtures --force`.
크레딧: 15건 × 4판 = 60회(`gpt-5.4-nano`).

| 프롬프트 | min | 중앙값 | max | 평균 | 기준선 대비 | 계정명 |
|---|---|---|---|---|---|---|
| `2~3문장, 200자 이내` (기준선) | 59 | 112 | 167 | 107.0 | — | 0건 |
| `3~5문장, 300자 이내` | 66 | 153 | 247 | 147.5 | 1.38배 | 0건 |
| `4~6문장, 300자` + **조건부 250자 하한** | 80 | 150 | 336 | 181.0 | 1.69배 | 🔴 **1건** |
| ↑ + "분량 채우려 제외 항목 넣지 마라" | 85 | 177 | 336 | 183.1 | 1.71배 | 🔴 **1건** |
| **`4~6문장, 300자 이내` (채택)** | 59 | **159** | 231 | **152.9** | **1.43배** | **0건** |

### ① 상한을 올려도 안 늘어난다 — 원래 안 걸리고 있었다

기준선의 **최대가 167자**로 200자 상한에 닿은 자료가 하나도 없었다. 즉 길이를 정하던 것은 상한이
아니라 **문장 수**다. 그래서 상한만 200→300 으로 올리는 것은 거의 무효이고, 문장 수를 2~3 → 4~6
으로 올린 것이 실제 증가분의 대부분이다.

**교훈: 안 걸리는 상한을 올려서 분량을 늘릴 수는 없다.** 늘리려면 하한이나 문장 수처럼 **실제로
바인딩되는 축**을 건드려야 한다.

### ② 🔴 하한은 두 배를 만들지만 `제외` 규칙을 깬다

`원문에 담을 내용이 충분하다면 250자 이상` 을 넣으니 평균이 1.69배로 올랐다. 그런데 **원문이 얇은
자료에서 모델이 분량을 채우려고 계정명을 집어넣었다** — `제외` 규칙 1번이자 #15 가 가장 먼저 잡은
문제다.

```
기준선(200자) 009 : 옷 잘 아는 사람들이 요즘 이렇게 입는다고 한다. …          ← 깨끗
하한 추가    009 : 인스타그램의 '프롬투미'가 옷 잘 입는 방법을 알려주고 있다  ← 🔴 유출
```

`분량을 채우려고 아래 '제외' 항목이나 원문에 없는 내용을 넣지 마라 — 짧은 요약이 규칙 위반보다
낫다` 를 **명시해도 그대로 유출했다**(`인스타그램에서 '프롬투미'가`). 하한을 걷어내니 같은 자료가
59자로 깨끗해졌다.

**교훈: 분량 하한과 "제외" 규칙은 얇은 원문에서 정면으로 충돌하고, 말로 우선순위를 정해도 안
먹는다.** [#15](#15) 의 "규칙을 늘리는 게 아니라 구체적으로 쓰는 것이 효과였다"가 여기서는 안
통한 셈이다.

### ③ 그래서 1.43배에서 멈췄다

알려진 회귀를 안고 숫자를 맞추지 않았다. 채택안은 **계정명·날짜·어투·따옴표·목록 기호 전부 0건**,
300자 초과 0건, 최대 231자(컬럼 `VARCHAR(500)` 에 두 배 이상 여유).

### ④ 아직 안 재본 지렛대

**고유명사 상한 `핵심 3~4개`** — 이 숫자는 200자 기준으로 정해졌다(#15: 16개 나열로 231자). 300자
면 여유가 있으므로 이걸 늘리면 **`제외` 규칙을 안 건드리고** 상호가 많은 자료만 길어질 수 있다.
더 늘려야 하면 여기가 다음 후보다.

### ⑤ 남은 한계

- **추천 품질로는 안 쟀다.** 요약은 추천 프롬프트의 입력인데 이 실험은 요약 자체만 봤다. 방 평가를
  안 돌렸으므로 후보 품질이 나아졌는지 나빠졌는지 **모른다.**
- **파급 둘이 미측정이다.** ① 추천 프롬프트 예산(12,000자)에서 자료당 비용이 약 1.4배 —
  자료 27건은 안 걸리지만 50건쯤에서 뒤쪽이 버려지기 시작한다. ② 임베딩 입력이 길어지는데 기존
  자료는 200자 요약으로 만든 벡터를 그대로 갖고 있어 **같은 방에서 길이가 섞인다**(재요약 안 하기로
  확정).
- **`temperature` 를 고정하지 않았다**(운영과 같게 두려고 — #15 와 같은 이유). 위 자릿수는 한 번
  뽑은 값이므로 **재현하면 ±로 흔들린다.** 품질 판단은 자릿수가 아니라 이진 관측으로 했다.
- **n=15 다.** 계정명 유출이 1건이라 "하한이 유출을 만든다"는 관측은 **자료 하나에 걸려 있다.**
  다만 하한을 넣은 두 판에서 같은 자료가 두 번 유출하고 빼면 사라졌으므로 우연으로 보지 않았다.

## 33. ★ 요약 서식(줄바꿈·강조)을 프롬프트로 받으려다 **기각했다** — 앱 렌더링으로 갔다 (2026-08-08)

**요청**: 자료 상세(S-25-B)의 AI 요약이 4~6문장 통짜라 읽기 어렵다는 QA. 디자이너 표현은 *"굵기·크기
변화 없는 통짜 텍스트라 너무 지저분하다"*(`docs/backend/archive-summary-formatting-handoff.md`).
받은 선택지는 ① 문장/문단 `\n` ② 마크다운 `**강조**` ③ 둘 다 불필요.

**방법**: v4 에 규칙을 **골라 얹어** 픽스처 15건을 조건별로 재봤다(`evals/probe_summary_format.py`,
`--condition`). 기존 네 규칙(평서문·제외·고유명사 제어·출력)은 한 글자도 안 건드렸다. 크레딧 45회
(`gpt-5.4-nano`). 300자 규칙은 유지.

| 조건 | 개행=문장 | 평서문 이탈 | 강조 3~4개 | 평균 보이는 글자 | 300 초과 | strip 후 v4 유사도 |
|---|---|---|---|---|---|---|
| **v4 동결(기준선)** | — | **0/15** | — | **152.9** | 0건 | 1.000 |
| `줄바꿈` 1차 | **7/15** | (미계측) | — | 151.9 | 0건 | 0.623 |
| `줄바꿈` 2차 | **8/15** | 1/15 (2회) | — | 159.9 | 🔴 **1건 (310자)** | 0.605 |
| `줄바꿈+강조` | 10/15 | 다수 | 🔴 **2/15** | 160.4 | 0건 | 0.540 |

> 개행 준수율 세 값은 **⑤의 계수기를 두 번 고친 뒤 저장해 둔 원출력으로 다시 센 것이다**(LLM 재호출
> 0회). 처음 적었던 `8/15 · 8/15 · 10/15` 중 1차가 `7/15` 로 내려갔고 나머지 둘은 같았다.

### ① 모델이 줄바꿈 규칙을 절반만 지킨다 — 두 번 재현됐다

`7/15`, `8/15`. 그리고 **어길 때의 모양이 한결같다** — 실패한 15건 전부가 `줄 1`, 즉 **부분적으로
지키는 경우가 없다.** 3~5문장을 통째로 한 줄에 쓰거나 문장마다 나누거나 둘 중 하나다.

자료마다 어떤 건 여러 줄, 어떤 건 통짜가 되므로 **QA 문제가 절반만 해결된다.** 규칙을 더 강하게
쓰는 것은 안 해봤지만, 준수율이 100%가 되지 않는 한 "자료마다 다르게 보인다"는 성질은 남는다.

### ② 🔴 강조 규칙이 `고유명사 제어`·`제외` 두 규칙과 정면으로 싸운다

`핵심 3~4개` 범위를 지킨 것이 **2/15** 뿐이다. `015_seoul_extreme` 은 **11개**, `001` 은 8개를
감쌌고 반대로 4건은 0개였다. 그리고 **계정명을 강조까지 했다**(둘 다 `줄바꿈+강조` 조건):

```
003 : **COMBINE**님의 안내를 따라 …    ← 원문 계정명 `컴바인 COMBINE`
010 : **꿈꾸는라이언** 실기 요약노트    ← 원문 계정명 `꿈꾸는라이언`
```

> ⚠️ **처음엔 `012 : **드.디.어.**` 도 계정명 유출로 적었는데 틀렸다**(리뷰 지적). 원문
> (`data/archives/012_jeongcheogi_potato.txt`)을 열어보면 그건 게시물 첫 줄의 감탄사
> (`드.디.어. 왔습니다`)이고 012 의 계정명은 `정처기 감자`다. **증거 3개 중 1개가 무효**이나
> 나머지 2개로 결론은 그대로다. 같은 변경 안에서 앱 코드 주석은 같은 문자열을 "게시물 감탄사"로
> 옳게 적어 놓고 이 문서만 틀렸었다 — **한 사실을 두 곳에 쓰면 갈린다.**

v4 동결본은 계정명 **0건**이다. #15 가 가장 먼저 잡은 문제가 되살아났고, [#32 ②](#32) 의 교훈
("분량 하한과 제외 규칙은 정면 충돌하고 말로 우선순위를 정해도 안 먹는다")가 **다른 규칙에서 다시
관측된 것**이다. 강조할 대상을 고르는 일이 "무엇을 남길지"를 다시 판단하게 만들어, 이미 걸러낸
계정명을 되불러온다.

### ③ 🔴 어투가 무너진다 — 규칙을 얹은 대가

v4 는 `기록한다 / 방문한다 / 진행한다` 인데 후보에서는:

```
[줄바꿈+강조] 003 : … 만들 수 있습니다. / … 가져보세요.   ← 존댓말 명령 (#15 가 잡은 그 문제)
[줄바꿈+강조] 015 : … 따라가라. / … 공유하라.             ← 명령형
[줄바꿈+강조] 011 : … 확인하라.
[줄바꿈]      003 : … 습니다.                             ← 단독 조건에서도 1/15 는 났다
```

`평서문(~한다, ~다)` 규칙 자체는 그대로 뒀는데도 이렇게 됐다. 기준선은 **0/15**다.

⚠️ **조건 라벨을 붙여 둔다** — 위 인용 대부분이 `줄바꿈+강조` 에서 나왔다. 어투 이탈은 두 조건
모두에서 관측됐지만 **빈도가 다르다**(단독 1/15 vs 조합 다수). "줄바꿈 규칙이 계정명을 유출시켰다"
처럼 뭉뚱그리지 말 것 — 계정명 유출은 **강조 조건에서만** 나왔다.

### ④ 새 위험 하나는 실제로 발현했다 — 300자 초과

`002_sqld_review` 가 **310자**. `출력:` 줄에 "줄바꿈과 별표는 300자에 포함하지 않는다"를 넣은 것이
빌미가 된 것으로 보인다(확증 못 함). 컬럼은 `VARCHAR(500)` 이라 저장은 되지만 프롬프트가 스스로
요구한 상한을 깼다.

### ⑤ ⚠️ 계수기를 **두 번** 고쳤다 — 둘 다 결과를 실제보다 좋게 보이게 하는 방향이었다

**1차 오류: 어투를 전제로 문장을 셌다.** 처음엔 `~다.` 만 셌다(프롬프트가 평서문을 고정하니
성립한다고 봤다). 그런데 ③ 때문에 모델이 `~하라.` 로 이탈하자 **4문장짜리를 1문장으로 셌고**,
그 결과 `줄 수 == 문장 수` 가 우연히 맞아 **개행을 아예 안 넣은 자료가 "준수"로 집계됐다**
(`002` 가 실제로 그랬다: 줄 1 · 문장 1 로 찍혔지만 실제는 4문장 1줄).

**2차 오류(리뷰에서 잡힘): 종결 부호만 세도록 고쳤더니 `드.디.어.` 의 마지막 마침표를 문장으로
셌다.** `010` 이 4문장인데 5로 나와, **모델이 완벽히 준수해도 비준수로 집계**된다. 게다가 마크업이
붙은 원문에 세고 있어서 종결 마침표 뒤에 `*` 가 오면 문장이 아예 누락됐다 — 1차와 **같은 방향**의
과대 준수 집계다. 지금은 마크업을 뗀 뒤에 세고, 약어·숫자 어절 판정을 **앱 분리기와 같은 규칙**으로
맞춰 뒀다(`_is_sentence_end` ↔ `summary_text.dart::_isNotSentenceEnd`).

**교훈 둘.** ① **측정 대상이 흔들릴 수 있는 축을 계측기의 전제로 쓰지 말 것.** ② **앱이 특별
처리하는 입력은 계측기도 같이 특별 처리할 것** — 아니면 둘이 다른 것을 재게 된다.

### ⑥ 그래서 프롬프트를 안 고치고 앱에서 나눈다

요약 프롬프트가 `~한다/~다` 를 못 박고 있으니 **문장 경계는 이미 문법으로 정해져 있다.** 앱이
그 경계에서 줄을 바꾸면:

| | 프롬프트로 받기 | 앱에서 나누기 |
|---|---|---|
| 개행 준수 | 8/15 (53%) | **15/15 (100%)** |
| 어투·계정명·날짜 규칙 | 깨짐(①②③) | **무변경** |
| 추천·임베딩 입력 | 유사도 0.54~0.62 | **1.000 (같은 값)** |
| 이미 등록된 자료 | 재요약 백필 필요(크레딧) | **즉시, 0원** |
| 300자 초과 | 1건 발생 | 없음 |

구현은 `app/lib/features/archive/summary_text.dart`. **동결 픽스처가 그 분리기의 시험대가 됐다** —
`010` 의 콘텐츠 이름 `드.디.어.` 는 마지막 마침표 뒤에 공백이 와서 단순 분리 시 한 문장이 두 줄로
찢어지고, `008` 에는 `~보자.` 처럼 **`다` 로 끝나지 않는 문장이 1건** 있다. 그래서 종결 어미를
열거하는 대신 "마침표 앞 어절에 다른 마침표가 있으면 약어로 본다"로 판정한다.

### ⑦ 강조(볼드)는 보류다 — 없앤 게 아니다

②가 말하는 것은 "볼드가 나쁘다"가 아니라 **이 프롬프트로는 3~4개 규칙을 못 지킨다**는 것이다.
볼드는 앱이 만들 수 없다(어떤 단어가 핵심 상호명인지는 모델만 안다). 다시 볼 때의 출발점은
[#32 ④](#32) 와 같은 자리 — `고유명사 제어` 의 개수를 강조와 **같은 규칙 안에서** 다루는 것이다.
`specs/OPEN.md` 에 기록했다.

### ⑧ 남은 한계

- **n=15 · 조건당 1~2회다.** `temperature` 를 고정하지 않았으므로(운영과 같게, #15·#32 와 같은
  이유) 자릿수는 재현하면 흔들린다. 판단은 자릿수가 아니라 **이진 관측**(계정명 유출·어투 이탈·
  강조 개수 범위)으로 했고, 줄바꿈 준수율만 두 번 재서 `8/15` 로 일치했다.
- **`강조만` 조건은 안 쟀다.** ②의 원인이 강조 규칙 자체인지 두 규칙의 상호작용인지 갈리지 않는다.
  다만 `줄바꿈` 단독에서도 어투 이탈이 1건 나왔으므로 **강조만의 문제는 아니다.**
- **추천 품질로는 안 쟀다**(#32 와 같은 한계). 다만 채택안은 저장값을 **한 글자도 바꾸지 않으므로**
  추천·임베딩 입력이 그대로다 — 이 실험에서 방 평가가 필요 없는 유일한 이유다.
- 회귀 힌트(계정명·날짜·존댓말)는 **문자열 판정이라 오탐·미탐이 있다.** 그래서 러너가 요약 전문을
  함께 찍고, 위 인용은 전부 눈으로 본 것이다. 덤으로 확인된 것: **날짜 유출은 v4 에도 있었다**
  (`012` 의 `2026년`) — 이번 변경의 회귀가 아니다.
- **표의 `평서문 이탈` 은 하한이다.** `count_imperative` 가 종결 어미 목록 기반이라 `됩니다`·
  `드립니다` 처럼 목록 밖 존댓말은 안 잡힌다. **0 을 "이탈 없음" 의 증거로 쓰지 말 것.**
- 🔴 **원출력을 커밋하지 않았다.** 크레딧 45회짜리 관측인데 `015 가 11개` 같은 숫자를 남이 검증하려면
  또 45회가 든다(개행 준수율 재계산은 마침 로컬에 남아 있던 실행 출력으로 했다). 다음에 이런 측정을
  할 때는 `evals/data/` 에 픽스처처럼 **동결해 커밋할 것** — `summarize_fixtures.py` 가 요약을
  동결하는 것과 같은 이유다.

## 34. ★ 태깅 모델을 `gpt-5.4-nano` 로 바꿨다 — **근거가 사라져서다** (2026-08-13)

태깅만 `gpt-5-nano` 였다. 그걸 정당화한 축은 **딱 하나, 게이트웨이 크레딧 등급**이었다(#7, `DECISIONS.md`).
원 프로젝트가 끝나 **게이트웨이 키가 2026-08-14 에 회수되고 제공사가 OpenAI 직접으로 바뀌면서 그 축이
사라졌다.** 그래서 태깅·요약·추천 셋을 한 모델로 합쳤다.

> **이 실험의 성격**: 새 사실을 찾은 게 아니라 **이미 알던 사실(#2·#14)을 태깅 워크로드에서 확인하고,
> 옛 결정의 전제가 죽었음을 기록한 것**이다. #14 가 "태깅도 `gpt-5.4-nano` 가 나을 수 있다 — 별도 확인
> 대상"으로 남겨둔 항목이 여기서 닫힌다.

**방법**: `evals/measure_tagging_model.py` · 픽스처 3건 × 모델 2종 × **2라운드** · 운영 서버
(`modi-prod`)의 `maramodi-ai` 컨테이너 안 · `api.openai.com` 직접 · `temperature` 미지정.
`SYSTEM_PROMPT` 는 `OpenAiTaggingClient.SYSTEM_PROMPT` 를 **문자 단위로 복사**했고 본문도 운영과 같이
4000자에서 잘랐다. 원출력은 `evals/data/snapshots/2026-08-13_tagging_model_openai_direct.txt`
에 **동결해 커밋했다**(#33 이 남긴 교훈).

| 픽스처 (prompt tok) | `gpt-5-nano` 1R | 2R | `gpt-5.4-nano` 1R | 2R |
|---|---|---|---|---|
| 001 강릉 (541) | 4.18초 · 484 tok (추론 448) | 4.80초 · 670 (640) | **0.81초 · 32 (0)** | **0.73초 · 32 (0)** |
| 002 SQLD (778) | 3.94초 · 478 (448) | 5.74초 · 544 (512) | **1.12초 · 36 (0)** | **0.76초 · 28 (0)** |
| 003 부산 (467) | 4.41초 · 478 (448) | **15.43초 · 1,818 (1,792)** | **0.75초 · 25 (0)** | **1.32초 · 25 (0)** |

같은 픽스처의 prompt 토큰이 두 라운드에서 같은 것이 **입력이 같았다는 증거**다.

**결론 1 — `gpt-5-nano` 는 태깅에서도 completion 의 92.7~98.6% 를 숨은 추론에 쓴다.** 태그 5개(=출력
25~36 tok)를 내려고 추론 토큰 448~1,792개를 태운다. #2(태그 5개에 추론 1,344)·#14(요약에서 94~97%)와
같은 성질이고, **프롬프트가 아니라 모델의 성질**이라는 판단이 태깅에서도 재확인됐다.

**결론 2 — 문제는 평균이 아니라 편차다.** 003 은 **입력이 완전히 같은데** 4.41초 → **15.43초**로 튀었다
(추론 448 → 1,792). `gpt-5.4-nano` 는 6회 전부 0.73~1.32초, 추론 **0/6회**다. 운영 read 타임아웃은
60초(`modi.archive.ai-read-timeout-seconds`)라 이번 최악값도 안에 들지만, **꼬리를 예측할 수 없는
모델을 폴백이 삼켜버리는 경로에 두면 "가끔 태그가 안 달린다"가 원인 없이 남는다.**

**결론 3 — 비용의 방향이 게이트웨이 시절과 반대가 됐다.** OpenAI 직접 과금은 **숨은 추론 토큰까지 출력 토큰
요금으로 청구**한다. 출력 토큰이 픽스처별로 **13~73배** 차이 나므로, 크레딧 등급이라는 방패가 없어진
지금 `gpt-5-nano` 는 느린 쪽이면서 **동시에 비싼 쪽**이다.

**결론 4 — 태그 품질은 눈으로 볼 때 동등하고, 관측된 유일한 회귀는 플랫폼 이름 태그다.**
`gpt-5.4-nano` 가 `먹스타그램`·`인스타그램` 을 **6회 중 3회** 냈고 `gpt-5-nano` 는 한 번도 안 냈다.
- ⚠️ **이건 "품질을 쟀다"가 아니다.** 정답 라벨이 없고(`evals/data/archives_index.md`) 6회를 눈으로 본
  것뿐이다. 태그의 용도가 검색이라 무해하다고 **판단**했지, 측정하지 않았다.
- 고치려면 프롬프트에 "플랫폼·서비스 이름은 태그로 쓰지 말라"를 한 줄 더하면 되겠지만, **이번에는
  프롬프트를 건드리지 않았다** — 모델만 바꾼 상태의 숫자를 남겨야 다음에 프롬프트를 고칠 때 무엇이
  무엇을 바꿨는지 갈라 볼 수 있다.

**⚠️ 안 잰 것**: 실사용 본문 크기(자료당 약 6.8k tok, #11)에서의 거동. 픽스처는 467~778 tok 이라
**운영보다 한 자릿수 작다.** 큰 입력에서 `gpt-5-nano` 의 추론 토큰이 어떻게 늘어나는지는 모른다 —
다만 그 방향은 이 결정을 뒤집는 쪽이 아니다(늘어나면 더 불리해진다).

## pgvector 도입 시 확인된 사실

> ⚠️ **2026-08-01: pgvector를 도입하지 않기로 뒤집혔다**([#19](#19) · `DECISIONS.md`). 저장은 `archive_items.embedding real[]`로

- 공식 `pgvector/pgvector` 이미지는 **debian 베이스만** 제공한다. 현재 `postgres:17-alpine`(운영)·`postgres:16-alpine`(테스트)에서 교체하면 베이스 OS가 바뀐다.
