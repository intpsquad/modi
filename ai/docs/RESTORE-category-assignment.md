# 카테고리 배정을 되살리는 법 (에서 걷어냄)

2026-08-04에 **AI가 카테고리를 정하는 기능을 통째로 제거**했다. 추천 후보는 카테고리 없이
나가고(= 기타/미분류), 사용자가 투두 탭에서 직접 분류한다.

이 문서는 **되살려야 할 때 무엇을 어떻게 되돌리는지**만 적는다. 왜 제거했는지의 근거는
[`EXPERIMENTS.md`](EXPERIMENTS.md) #31에 있다.

---

## 되살리는 방법 — 커밋 **두 개**를 함께 revert 한다

```bash
git log --oneline --all --grep=""
# Feat!: AI 추천에서 카테고리 배정 제거   ← 제거 본체
# Fix:   리뷰 반영 …                      ← 그 위에 얹힌 수정

git revert --no-commit <Fix 해시> <Feat! 해시>   # ⚠️ 최신 → 오래된 순서
```

⚠️ **`Feat!` 하나만 되돌리면 4개 파일에서 충돌한다.** `Fix` 커밋이 같은 자리를 다시 건드렸기
때문이다(`run_suggest_eval.py` · `prompts.py` · `test_runner.py` · 이 문서). 순서를 지켜 둘 다
되돌리면 **충돌 없이** 붙는다 — 실측으로 확인했다(2026-08-04).

`Docs` 커밋(측정 스냅샷 5개 + `EXPERIMENTS` #31)은 **되돌리지 마라.** 왜 지웠는지의 증거이고,
되살린 뒤에도 남아 있어야 한다.

되돌린 뒤 확인:

```bash
cd ai
uv run ruff check . && uv run pytest      # 507개 통과 (제거 전과 같은 수)
```

⚠️ **이 문서도 `Feat!` 커밋에 들어 있어 revert 하면 함께 지워진다.** 먼저 복사해두거나,
되돌린 뒤 `git checkout <Feat! 해시> -- ai/docs/RESTORE-category-assignment.md` 로 꺼내라.

⚠️ **`batch` 노드는 제거 커밋에 포함돼 있다.** 그래서 일부러 안 지웠다 — 같이 지웠으면
revert 가 반쪽이 되어 `match` 노드가 없는 `state["batched"]` 를 참조했을 것이다. 그 뒤에
누군가 `batch` 를 정리했다면(→ `specs/OPEN.md` 후속 항목) revert 가 충돌한다.

## 🔴 되살리기 전에 반드시 읽을 것

세 가지 방식을 다 만들어봤고 **셋 다 실패했다.** 그냥 되돌리면 실패한 상태로 돌아간다.

### ① 프롬프트로 시키기 — 실패 (#21, 2026-08-01)

생성 프롬프트에 "기존 카테고리를 우선하라"를 넣었다. 문구를 네 가지로 바꿔가며 자료 15건에
돌렸다.

> **새 카테고리 0개 · 후보의 100%가 기존 카테고리 하나로 몰림**

기존 카테고리가 `공부` 하나뿐인데 강릉 맛집·부산 여행·패션 자료까지 전부 거기 넣었다.
`full_spec.md` §S-16-B가 "새로 카테고리 + 투두도 추천"을 요구하므로 스펙 위반이다.

### ② 임베딩 코사인으로 접기 — 실패 (#25 ⑤, 실사용 10/10)

판단을 코드로 옮겼다. 모델은 주제만 쓰고 서버가 기존 카테고리와의 코사인이 0.50 이상이면
접는다.

> **실사용에서 10개 중 하나도 안 접혔다.** 추천 4번에 후보 카테고리가 2종 → 12종.

```
부산 맛집 ~ 요리      0.348
부산 맛집 ~ 숙소      0.350
미식여행  ~ 카페      0.146
관광      ~ 여가      0.439      (임계값 0.50)
```

⚠️ **임계값을 내려서는 못 푼다.** 0.35까지 내려야 접히는데 그러면 무관한 것도 접힌다.
뿌리는 #17과 같다 — **한 방 안의 텍스트가 전부 같은 도메인이라 코사인이 좁은 띠에 몰린다.**

**게이트를 뒤집는 안(제목↔카테고리 유사도로 "안 맞으면 떼어내기")도 재봤다**(2026-08-04).
어휘에 속하는 제목과 속하지 않는 제목의 점수 중앙값 차가 **±0.03**이었다 — 못 가른다.

### ③ LLM 별도 호출로 배정 — 실패 (#31, 2026-08-04)

`critique` 노드와 같은 구조로 분류 전용 호출을 뒀다. 방의 카테고리 목록 + 후보 제목을 주고
"몇 번에 넣을지, 아니면 새로 만들지"만 답하게 했다.

프로브(96회)는 좋아 보였다 — 지연 1.87초, [#21] 재현 없음(전부한곳 0건), 어휘가 크면 새
카테고리 77% → 5%. **그런데 방 평가에서 뒤집혔다.**

| | 부산 후보당 종수 | 오픽 후보당 종수 |
|---|---|---|
| 임베딩 채택끔 (2회) | **0.82 · 0.80** | **0.90 · 0.88** |
| 임베딩 채택켬 | **0.89** | **0.87** |
| LLM 채택끔 | 0.96 | 0.97 |
| LLM 채택켬 | 0.91 | 0.97 |

**0.97 = 후보 하나당 카테고리 하나.** 고치려던 문제가 심해졌다.

⚠️ **5/5 비교에서 전부 LLM 쪽이 나쁘지만 크기는 방마다 다르다.** 오픽은 차이 0.067~0.102 로
기준선 편차(0.033)를 넘는다. 부산은 짝맞춘 비교(채택켬끼리)가 **0.0155** 인데 기준선 편차가
**0.094** 라 편차 안이다 — 방향만 말할 수 있다.

원인은 프로브가 이미 보여줬다 — **새 이름의 46%가 투두 제목을 거의 그대로 베낀다.**
이름 길이 규칙을 8자로 조여도(중앙 11자 → 5자) 그 비율은 47%로 안 변했다.

⚠️ **지연은 문제가 아니었다.** LLM 호출이 3회가 됐는데도 10초 초과 0/30(기준선은 1/30).
`match` 노드가 임베딩을 안 부르게 되면서 상쇄됐다. **비싸서 기각이 아니라 효과가 없어서다.**

## 되살린다면 무엇이 달라야 하나

위 셋을 그대로 되돌리는 것은 의미가 없다. 새로 시도한다면 **아직 안 해본 것**은 이쪽이다.

- **생성 단계에서 후보 수 대비 카테고리 수를 제약하기.** #27이 이미 진단했다 —
  *"매칭 문제가 아니라 생성 문제"*. 모델이 후보마다 이름을 하나씩 짓는 성향이 본체이고,
  그건 배정 단계에서 고칠 수 없다. 프롬프트에 "후보 8개에 카테고리 3개 이하" 같은 제약을
  넣는 안은 **아직 안 재봤다.**
- **판정 기준(라벨 세트)을 먼저 만들기.** 지금은 `관광명소`와 `해변관광`이 같은 것인지
  판정할 근거가 없다. ⚠️ 다만 방이 2개뿐이라 표본이 좁고, 그 위에서 임계값을 튜닝하면
  과적합된다(2026-08-04 사용자 지적).

**측정 지표는 `후보당 카테고리 종수`다** — 세션당 종수나 실행 합집합이 아니다.
합집합을 사용자 경험처럼 읽는 오독을 두 번 했다(#30 리뷰 · #31).
