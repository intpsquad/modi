# 0015 — 알림 트리거 7종 (푸시 발송)

> 관련 스펙: `specs/full_spec.md` §10(설정 페이지 알림 항목 원본 목록), `specs/0002-data-model.md`(`notification_settings`, `pokes`, `users.fcm_token`), `specs/0012-설정.md`(수신 설정 화면·개별 on/off — 이 문서는 그 화면이 다루는 채널의 **실제 발송 시점**만 정한다), `specs/0011-멤버-투두-콕찌르기.md`(콕찌르기 트리거 원본, 이 문서의 나머지 5종이 같은 패턴을 따름), `specs/0001-architecture.md`(FCM 파이프라인 자체는 이미 확정).
>
> 2026-08-05 구현 완료(백엔드). 이 문서는 `specs/0012-설정.md`가 "별도 알림 트리거 작업에서 확정한다"고 유보했던 항목을 채운다.

## 목적
`full_spec.md:205`가 나열한 6종 알림 이벤트(콕찌르기, 일정 전날, 일정 디데이, 방 멤버 입장, 방 멤버 퇴장, 내 담당 투두 추가)가 **언제, 누구에게, 무엇을** 발송하는지를 확정한다. 8개 `notification_settings` 채널 중 콕찌르기(`poke_enabled`)만 이미 발송 중이었고, 나머지 5개는 설정 컬럼만 있고 아무도 읽지 않았다.

## 하지 않을 것
- **수신 설정 화면(전체/개별 on/off) 자체** — `specs/0012-설정.md`. 이 문서는 그 설정값을 실제로 "언제 확인해서 쏘는지"만 다룬다.
- **FCM 파이프라인 상세(Firebase 프로젝트 설정, 토큰 등록 흐름)** — `specs/0001-architecture.md`, `docs/fcm-setup.md`.
- **재촉(노크)** — `knock_enabled` 컬럼은 남아 있지만 콕찌르기와 통일돼 실제로는 항상 `POKE`로만 기록된다(2026-07-29 확정, `specs/0011`). 이 문서에서도 건드리지 않는다.
- **"마감임박 알림"** — `specs/OPEN.md`의 **별개의 미해결** 항목(방 `end_date` 기준). 이 문서의 "일정 디데이"는 `schedules.date` 기준이라 다른 개념이다. 혼동 금지.
- **푸시 payload의 `data` 맵/딥링크** — 앱(`fcm_service.dart`)이 `onMessageOpenedApp`/`message.data`를 전혀 읽지 않는다(2026-08-05 확인). title/body만 보낸다.
- **다기기 푸시** — `users.fcm_token` 단일 컬럼(1대만 지원) 유지.

## 액션·전이
| 이벤트 | 트리거 시점 | 대상 | 제외 |
|---|---|---|---|
| 콕찌르기 | `POST .../pokes` 즉시(`PokeService.sendPoke`) | 대상 멤버(`toUser`) | — |
| 일정 디데이 | 매일 08:00 KST 배치(`ScheduleReminderService`), `schedules.date = 오늘` | 그 일정이 속한 방의 멤버 전원 | 방이 이미 끝난 경우(`rooms.end_date < 오늘`) |
| 일정 전날 | 매일 08:00 KST 배치, `schedules.date = 내일` | 그 일정이 속한 방의 멤버 전원 | 위와 동일 |
| 방 멤버 입장 | `POST .../join` 성공 시(신규 참여일 때만, `RoomService.joinRoom`) | 참여 **이전** 시점의 기존 멤버 전원 | 참여자 본인, 이미 멤버인 재참여(no-op) |
| 방 멤버 퇴장 | `DELETE .../members/me` 성공 시(`RoomService.leaveRoom`) | 퇴장 **이후** 남은 멤버 전원 | 나간 사람 본인, 마지막 멤버라 방 자체가 삭제되는 경우(남을 사람이 없음) |
| 내 담당 투두 추가 | 투두 생성/수정 시(`TodoService.createTodo`/`updateTodo`) | **신규로** 배정된 담당자만 | 요청자 본인(자기 자신을 담당자로 추가), 수정으로 유지된 기존 담당자(재알림 없음) |
| 자료 분석 완료·실패 | 마지막 확정 뒤 **1분간 조용하면** 배치가 묶어서(`ArchiveAnalysisNotifier`, 30초 주기) | 그 자료를 **등록한 본인만** | 재시도로 밀린 것(아직 실패가 아니다), 작성자가 탈퇴한 자료, Redis 장애(fail-open) |

공통 게이팅(모든 이벤트 동일, `global.notification.PushNotifier`):
1. `notification_settings.all_enabled = false`면 개별 채널 값과 무관하게 발송 안 함(전체 킬스위치, 0012 확정).
2. 설정 행이 없는 유저는 `NotificationSetting` 기본값(전부 `true`)과 동일하게 발송 허용.
3. `users.fcm_token`이 없으면 발송 스킵.
4. FCM 발송 자체가 실패해도(`PushSender` 예외) 주 액션(콕찌르기 기록, 방 참여, 투두 생성 등)은 그대로 성공한다 — 부가 기능이 핵심 기능을 막지 않는다.

## 데이터 (엔티티 연결)
- 새 테이블/컬럼 없음 — `notification_settings`(전체 8컬럼, `V13`)와 `users.fcm_token`(`V4`)을 그대로 쓴다.
- 발송 자체를 기록하는 로그 테이블은 없다(콕찌르기의 `pokes` 행처럼 "발송 대상 이벤트"의 흔적이 남는 것은 콕찌르기·투두·방 입퇴장뿐이고, 일정 리마인더는 Redis에만 짧게 흔적이 남는다 — 아래 엣지케이스 참고).
- 문구(title/body)는 코드에만 있다(콕찌르기 선례와 동일, 별도 i18n/카피 테이블 없음):
  - 콕찌르기: `"{닉네임}님의 콕찌르기"` / `"{방이름} 방에서 투두를 확인해보세요"` (기존, 변경 없음)
  - 방 입장: `"{닉네임}님이 방에 들어왔어요"` / `"{방이름}"`
  - 방 퇴장: `"{닉네임}님이 방에서 나갔어요"` / `"{방이름}"`
  - 담당 투두 추가: `"{닉네임}님이 담당 투두를 추가했어요"` / `"{방이름} · {투두제목}"`
  - 일정 디데이: `"오늘 일정: {일정제목}"` / `"{방이름}"`
  - 일정 전날: `"내일 일정: {일정제목}"` / `"{방이름}"`

## 성공(인수) 기준
- [x] 콕찌르기를 받으면 대상자에게만 푸시가 간다(기존 동작 유지, 리팩터링만 함).
- [x] 오늘 날짜가 시작일인 일정이 있는 방의 멤버 전원이 08:00 KST에 "오늘 일정" 푸시를 받는다.
- [x] 내일 날짜가 시작일인 일정이 있는 방의 멤버 전원이 08:00 KST에 "내일 일정" 푸시를 받는다.
- [x] 같은 일정에 대해 배치가 같은 날 두 번 돌아도(재기동·수동 재실행) 푸시는 한 번만 나간다.
- [x] 방에 새 멤버가 들어오면 참여자 본인을 제외한 기존 멤버 전원이 알림을 받는다. 이미 멤버인 사람이 다시 참여를 시도해도(멱등) 알림은 안 간다.
- [x] 방에서 멤버가 나가면 나간 사람을 제외한 남은 멤버 전원이 알림을 받는다. 마지막 멤버가 나가 방이 삭제되는 경우는 알림이 없다.
- [x] 투두 생성 시 배정된 담당자(본인 제외)에게 알림이 간다.
- [x] 투두 수정으로 담당자가 갈아엎어져도, 새로 추가된 담당자에게만 알림이 가고 기존부터 담당자였던 사람은 재알림받지 않는다.
- [x] 각 채널의 개별 토글(`*_enabled`)을 끄면 그 채널만 발송이 스킵되고, `all_enabled`를 끄면 전부 스킵된다.

## 상태 (로딩·빈·에러)
서버 트리거 로직이라 화면 상태는 없다. 배치 실행 자체의 예외는 로그(`log.warn`)로만 남고 다음 실행에 영향을 주지 않는다.

## 엣지케이스
- **타임존**: 배포 컨테이너에 `TZ`가 설정돼 있지 않아 JVM은 UTC로 돈다(`server/Dockerfile`, `deploy/docker-compose.app.yml` 확인, 2026-08-05). 배치 cron과 날짜 계산 모두 `Asia/Seoul`을 코드에 명시해 UTC 여부와 무관하게 08:00 KST에 정확히 돌게 했다. (기존 `RoomService.refreshStatus` 등 무인자 `LocalDate.now()`는 같은 이유로 UTC 기준이라 KST와 최대 9시간 어긋날 수 있음 — 이 문서의 범위는 아니고 `specs/OPEN.md`에 별도 기록.)
- **일정 디데이 판단 기준**: 다중일 일정(`endDate` 있음)이어도 시작일(`date`)만 본다. `endDate`는 안 본다(2026-08-05 확정) — 여러 날 걸친 일정의 "끝나는 날 디데이"는 이번 범위 밖.
- **방 활성 여부 판단**: `rooms.status`(ACTIVE/ENDED)가 아니라 `rooms.end_date`를 직접 비교한다. `status`는 `RoomService.refreshStatus`가 요청 시점에만 lazy 갱신하므로, 아무도 열어보지 않은 종료된 방은 DB엔 여전히 ACTIVE로 남아 있을 수 있어 이 값만 믿으면 종료된 방에도 리마인더가 나간다.
- **일정 리마인더 중복 방지**: Redis `SETNX` 키 `schedule:reminder:{dday|day-before}:{scheduleId}:{기준일}`, TTL 2일. 08:00 직후 서버가 재기동하거나 배치를 수동으로 다시 돌려도 같은 일정·같은 날엔 한 번만 나간다.
- **일정이 여러 건**: 한 방에 그날 일정이 여러 개면 일정당 각각 별도 푸시가 나간다(묶어서 요약하지 않음, 2026-08-05 확정).
- **방 입장/퇴장에는 레이트리밋이 없다**: 콕찌르기(30초당 10회, Redis)와 달리 입장/퇴장은 반복 유인이 없는 이벤트라 별도 제한을 두지 않았다(2026-08-05 확정).
- **자기 자신을 담당자로 추가**: 투두 담당자 알림·방 입장/퇴장 알림 모두 "행위자 본인"은 항상 대상에서 제외한다 — 본인 행동에 본인이 알림받을 이유가 없다.

## 자료 분석 완료·실패 (2026-08-06 추가)

등록이 양쪽 경로(인앱 S-25-C · 공유 S-25-D) 모두 비동기가 되면서 "언제 분석이 끝났는지"를 알 방법이
앱을 다시 여는 것뿐이 됐다. 등록 직후 신호(「분석 중」 배지 · 목록 상단 "분석 중 N건")는 **등록됐다는
것만** 말해 준다. (등록 직후 스낵바도 있었지만 2026-08-06 에 뺐다 — `specs/0010` 참고.)

- **왜 묶는가**: 공유로 5건을 연달아 넣으면 알림도 5개가 된다. `ArchiveAnalysisNotificationBuffer`가
  사람별로 Redis 에 모으고, 마지막 확정 뒤 1분간 조용하면 그때 한 번만 보낸다.
- **왜 본인만**: 방 전체에 보내면 남이 올린 링크의 분석 알림까지 온다.
- 🔴 **실패는 자동 재시도가 끝난 뒤에만 보낸다.** 재시도로 밀린 것을 실패로 세면 20분 뒤 성공할 것에
  대해 "가져오지 못했어요"를 먼저 보내게 된다 — 알림이 틀린 말을 하는 것이라 안 보내느니만 못하다.
  세는 지점은 `markCrawlFailed()`를 부르는 자리뿐이다(`specs/0014`의 재시도 절 참고).
- **문구**(2026-08-09 후속 확정 — 1건 성공 케이스 변경): 1건 성공이면 제목은 **고정 문구**
  "AI로 자료 분석이 끝났어요", 본문에 어떤 자료·어느 방인지를 담아 "{자료 제목}의 내용을 {방 이름}
  모아보기에서 확인해보세요"로 안내한다(방 이름은 `ArchiveCrawlProcessor`가 크롤링 완료 시점의
  `item.getRoom().getName()`을 버퍼에 함께 실어 보낸다 — `ArchiveAnalysisNotificationBuffer`).
  1건 실패는 그대로 제목에 자료 제목을 담아 알린다("「강릉 여행 코스」 내용을 가져오지 못했어요").
  여러 건이면 개수로 묶고(방 이름은 안 쓴다 — 여러 방에 걸칠 수 있어 단일 방을 못 정한다),
  성공·실패가 섞이면 둘 다 적는다. 전부 실패면 본문에 "링크는 저장돼 있어요"를 넣는다 —
  실패 알림이 "다 날아갔다"로 읽히면 안 된다.
- **설정**: `notification_settings.archive_analysis_done_enabled`(`V17`, 기본 켜짐). 이 알림이 없으면
  완료 시점을 알 방법이 없으므로 받기 싫은 사람이 끄는 쪽으로 잡았다.
- ⚠️ **단일 인스턴스 전제**다. 여럿이면 같은 사람 몫을 둘이 집어 두 번 갈 수 있다.
- ⚠️ 조용 대기 1분은 **추정값**이다(실측 아님). 실제 사용 패턴을 보고 고칠 것.
