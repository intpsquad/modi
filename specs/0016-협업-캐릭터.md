# 0016 — 협업 캐릭터 (마이 탭)

> 관련 스펙: `specs/0002-data-model.md`(`user_activity` 테이블), `specs/0006-투두-탭.md`(투두 `due_date`, 이미 `V16`으로 구현돼 있어 이번 스코프가 아님), `specs/OPEN.md`(90일 보존·완주 판정 한계·타이밍 정규화 단순화·CHEERLEADER 고정 임계값·취향 태그 제외 근거).
>
> 2026-08-07 **서버** 구현 완료(백엔드 핸드오프). 프론트/디자인이 전달한 "MODI 협업 캐릭터" 핸드오프 문서 1~4장을 스펙 형식으로 정리한다.
> 2026-08-07 **프론트 카드 연동**: 마이 탭 `MyActivityCard`(`features/settings/my_activity_card.dart`)가 캐릭터를 표시한다. 서버는 URL이 아니라 `characterId`만 주므로 앱이 `characterId → assets/images/characters/{파일}.png`로 매핑해 로컬 일러스트를 그린다(파일명 오타 `procrasinator.png` 우회, `SPRINTER`는 전용 아트 없어 `steady`로 임시 대체). **실제 `GET /me/character` 연결 완료**(`SettingsApi.fetchCharacter`가 인증 호출 → `MyActivitySummary.fromJson`으로 파싱, 실서버 데이터 표시). 진화 바(`evolveProgress`/`evolveHint`)는 이번 카드에 미표시.

## 목적
방을 넘나들며 누적되는 사용자의 협업 행동(투두 완료 타이밍·완료율·꾸준함, 자료에 준 좋아요, 접속·조회 빈도)을 바탕으로 10종의 "협업 캐릭터" 중 하나를 서버가 판정해 마이 탭에 보여준다. 재미 요소(갓생 게이미피케이션)이자, 진화 사다리로 "다음 단계"를 은근히 유도하는 것이 목적이다.

## 핵심 설계 결정
1. **캐릭터는 전역(방 무관)이다.** 핸드오프 문서가 "프로젝트를 넘나들며 누적되는 개인 정체성"이라고 명시해, `GET /me/character`는 사용자의 **모든 방**을 합산해 계산한다. `GET /rooms/{roomId}/members/{userId}/character`도 같은 전역 캐릭터를 반환하며 방마다 다시 계산하지 않는다 — 그 방 멤버십은 오직 **접근 권한 확인**에만 쓰인다(호출자·대상 둘 다 그 방 멤버여야 함, `NotRoomMemberException`).
2. **결과는 저장하지 않는다.** 매 요청마다 기존 도메인 데이터(`todos`, `archive_likes`, `user_activity`)로 즉석에서 계산한다 — "이번 시즌" 개념이라 가변적이고, 캐시나 배치가 필요 없다.
3. **접속·조회 로그 3종은 기존 엔드포인트에 자동으로 얹는다.** 프론트 변경 없이: `ROOM_VIEW`는 `GET /rooms/{roomId}/dashboard`, `ARCHIVE_ITEM_VIEW`는 `GET .../archive/items/{itemId}`, `TODO_VIEW`는 `GET /rooms/{roomId}/todos/{todoId}`(2026-08-06 신설) 호출 시 기록한다. `APP_OPEN`만 대응하는 기존 엔드포인트가 없어 전용 `POST /me/activity/app-open`을 새로 만들었지만, 이 커밋 시점엔 앱이 아직 호출하지 않는다(폴더 미지정 등록 엔드포인트와 같은 선례 — 백엔드만 준비해 둔다).
4. **로그 보존은 90일.** 매일 새벽 배치(`UserActivityRetentionScheduler`)가 90일 지난 `user_activity` 원본 행을 삭제한다(개인 행동 로그라 저장 기간을 짧게 잡음, 사용자 확정 2026-08-07).
5. **마감 없는 투두의 "타이밍" 정규화.** 문서는 "그 방/사용자 분포로 정규화"라고만 하고 방법을 정하지 않았다. 교차 사용자 분포 계산을 피하려고 **사용자 자신의 리드타임(생성→완료 소요시간) 중앙값 대비 이르면(−)/늦으면(+)**으로 단순화했다.
6. **완주(생존) 신호는 넣지 않았다.** 문서 3-3절이 "다른 축"으로 완주율을 언급하지만, `room_members`는 방을 나가면 행이 **하드 삭제**된다(`RoomService.leaveRoom`). 그래서 "종료 전에 나간 방"은 데이터에 흔적이 안 남고, 남아 있는 행은 전부 "현재도 멤버"라 완주 여부를 구분할 수 없다(끝난 방에 아직 멤버로 남아 있으면 자동으로 "완주"가 되는 것과 같아, 실제보다 낙관적으로 나올 수밖에 없다). 스키마 변경(예: 탈퇴 이력 별도 보관) 없이는 정확한 판정이 불가능해 이번 스코프에서 제외했다 — `RoomMemberRepository.countByUserId`/`countByUserIdAndRoomStatus`는 이 목적으로 추가했다가 판정 로직에서는 빼서, 현재 `CharacterService`가 쓰지 않는 채로 리포지토리에만 남아 있다.
7. **스트릭 = 현재 연속일수**(최장 기록이 아니다). KST 달력 날짜 기준으로 오늘 또는 어제부터 거슬러 연속으로 완료가 있는 날 수를 센다 — 진화 힌트("N일 연속 완료하면 진화해요")가 현재진행형이라 "지금 몇 일째인지"가 맞는 개념이다.
8. **CHEERLEADER는 고정 임계값**(좋아요 준 횟수 ≥ 20)으로 판정한다. 문서는 "최상위"(percentile)를 암시하지만, 전체 사용자 순위를 매기는 쿼리는 무겁고 보조 캐릭터에 그 비용을 들일 이유가 없다고 판단했다.
9. **취향 태그(🍜)는 이번 스코프 제외.** 문서 "요약" 절이 "① 마감일 ② 로그 ③ 캐릭터 판정·API — 딱 3개"로 범위를 좁혔고, ①(투두 마감일)은 2026-08-06에 이미 구현돼 있었다(`todos.due_date`, `V16`) — 이번에 새로 만든 것은 ②③뿐이다.

## 판정 로직 (`CharacterService.getCharacter`)
1. **데이터 희박 가드**: 완료한 투두가 5개 미만이면 즉시 `WARMING_UP`(캐릭터 미정) 반환.
2. 아래 순서의 결정 트리(먼저 맞는 조건이 이긴다):
   - **최근 30일 조회 ≥10건 & 완료 ≤1건 → `LURKER`**(둘러보기만 하고 완료는 뜸함).
   - **완료일 사이 최대 공백 ≥7일 & 최근 7일 내 완료 없음 → `GHOST`**(한동안 조용하다 몰아서 완료).
   - **타이밍 점수 > +0.3(늦음 쪽)** → 완료율 ≥0.7이면 `SPRINTER`(막판 스퍼트해도 결국 해냄), 아니면 `PROCRASTINATOR`(미루기 장인).
   - **타이밍 점수 < −0.3(이른 쪽)** → 완료율 ≥0.85 & 스트릭 ≥7일 & 마감 준수율 ≥0.85 전부 만족하면 `THE_J`(완벽주의), 아니면 `EARLYBIRD`(미리미리단).
   - 그 외(중립 타이밍) → 스트릭 ≥7일이면 `STEADY`(꾸준 적립가), 아니면 `TURTLE`(마이 페이스).
3. **CHEERLEADER 오버라이드**: 위에서 무엇으로 판정됐든, 좋아요 준 횟수가 20 이상이면 최종적으로 `CHEERLEADER`로 덮어쓴다(보조 캐릭터, 문서 명시).
4. **`confidence`**: 완료 수 <10 이거나 마감일이 있는 완료가 0건이면 `LOW`, 아니면 `HIGH`.
5. **진화(`evolveTo`/`evolveProgress`/`evolveHint`)**: 문서 2장 화살표 그대로 — `PROCRASTINATOR→SPRINTER`, `GHOST/LURKER/TURTLE→STEADY`, `SPRINTER/STEADY→EARLYBIRD`, `EARLYBIRD→THE_J`. `THE_J`/`CHEERLEADER`/`WARMING_UP`은 더 이상 진화 경로가 없다(`evolveTo=null`).

**타이밍 점수**(−1=이름, +1=늦음): 마감 있는 완료는 `(완료일 − 마감일) / 3일`을 [−1,1]로 클램프해 가중치 1.0, 마감 없는 완료는 `(리드타임 − 본인 중앙값) / max(중앙값, 1시간)`을 클램프해 가중치 0.5로 가중평균한다.

## API
| 엔드포인트 | 설명 | 인가 |
|---|---|---|
| `GET /me/character` | 내 캐릭터(전역) 조회 | 로그인 |
| `GET /rooms/{roomId}/members/{userId}/character` | 다른 멤버의 캐릭터(전역, 방은 접근 권한만) 조회 | 호출자·대상 둘 다 그 방 멤버(`NotRoomMemberException`, 403) |
| `POST /me/activity/app-open` | 앱 진입 로그 기록 (`204`, 준비만 — 앱 미호출) | 로그인 |

**응답(`CharacterResponse`)**: `characterId`, `name`, `copy`, `why`(판정 근거 한 줄), `evolveTo`(nullable), `evolveProgress`(0~1, nullable), `evolveHint`(nullable), `confidence`(`LOW`/`HIGH`), `activityStats`(`completed`, `streak`, `deadlineKeptRate`, `helpGiven`(=좋아요 준 횟수), `shared`(=내가 등록한 자료 수), `dueDateCompletedCount`(마감일 있는 완료 투두 수, 2026-08-09 추가)). 취향 태그 필드는 없다(위 결정 9). `emoji` 필드는 앱이 쓰지 않아 2026-08-08 제거(로컬 일러스트를 `characterId`로 매핑해 표시).

**2026-08-09 수정**: `dueDateCompletedCount`가 0이면 `deadlineKeptRate`는 항상 0.0으로 나가는데, 이걸 "마감을 전혀 안 지킴"으로 오해할 수 있다 — 프론트는 `dueDateCompletedCount == 0`이면 마감 준수 지표를 아예 숨긴다(`app/lib/features/settings/my_activity_card.dart`).

## 데이터
- `user_activity`(`V21`, `specs/0002-data-model.md` 참고): `id`, `user_id`, `room_id`(nullable), `kind`(`APP_OPEN`/`ROOM_VIEW`/`ARCHIVE_ITEM_VIEW`/`TODO_VIEW`), `target_id`(nullable), `created_at`. 인덱스 `(user_id, created_at DESC)`.
- 새 컬럼은 이것뿐이다 — 캐릭터 판정에 쓰는 나머지 신호(투두 완료 타이밍, 좋아요 준 횟수, 등록한 자료 수)는 기존 `todos`/`todo_assignees`/`archive_likes`/`archive_items`를 전역(방 무관) 집계 쿼리로 새로 추가해 읽는다.
- `UserActivityRecorder.record(...)`는 실패해도 본 요청을 막지 않는다(예외를 삼키고 `log.warn`만 남김) — 그리고 **반드시 `REQUIRES_NEW` 트랜잭션**이어야 한다. 읽기 전용(`readOnly = true`)인 호출자 트랜잭션(대시보드·아카이브 상세·투두 상세 조회는 전부 읽기 전용이다)에 그대로 얹으면, 내부 INSERT가 읽기 전용 위반으로 실패하고 그 순간 트랜잭션 전체가 rollback-only로 마킹돼 이후 같은 트랜잭션의 모든 조회가 "current transaction is aborted"로 깨진다(2026-08-07 실제로 겪고 `REQUIRES_NEW`로 고침).

## 하지 않은 것
- 캐릭터 결과 저장·캐싱 — 매 요청 즉석 계산.
- 방 단위 캐릭터 — 항상 전역.
- 완주(생존) 신호 — 위 결정 6.
- 취향 태그 — 위 결정 9.
- 전체 사용자 순위 기반 CHEERLEADER(percentile) — 고정 임계값으로 근사.
- 프론트 UI(마이 탭 화면) — 서버 스코프에서는 제외했으나, **2026-08-07 카드 연동 완료(실제 `GET /me/character` 호출, 위 헤더 참고)**.
- 프론트 UI(멤버 투두 화면) — **2026-08-07 멤버 캐릭터 카드 연동**: `MemberTodosApi.fetchCharacter`가 `GET /rooms/{roomId}/members/{userId}/character`를 호출해 `MyActivityCard`를 그대로 재사용한다.
- `SPRINTER` 전용 일러스트 — 아직 없어 앱이 `steady`로 임시 대체(디자인 후속).
- 진화 바 UI(`evolveProgress`/`evolveHint`) — API는 주지만 카드에는 아직 미표시.

## 엣지케이스
- **동시에 여러 조건을 만족**: 결정 트리는 순서대로 첫 매치를 채택한다(예: LURKER·GHOST 조건이 겹치면 LURKER가 먼저 걸린다). CHEERLEADER만 예외로 트리 결과 전체를 마지막에 덮어쓴다.
- **마감 있는 완료가 0건**: `confidence`가 자동으로 `LOW`가 된다 — 타이밍 신호의 절반(마감 기반)이 아예 없다는 뜻이라서다.
- **완료 후 트랜잭션 실패로 조회 로그가 안 남아도**: 캐릭터 판정 자체(투두·좋아요 기반)엔 영향 없다. `user_activity`는 LURKER/GHOST 판정에만 쓰이는 보조 신호다.
- **로그 기록 실패**: 조회 API 자체는 정상 응답한다(위 데이터 절 참고).
