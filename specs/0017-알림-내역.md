# 0017 — 알림 내역 (S-41)

> 관련 스펙: `specs/0012-설정.md`(마이페이지 진입·디자인 톤), `specs/0015-알림-트리거.md`(발송 트리거 7종·문구·게이팅), `specs/0003-navigation.md`(라우트), `specs/0002-data-model.md`(엔티티), `specs/design.md`(토큰).
> 관련 핸드오프: `docs/backend/notification-deeplink-handoff.md`(같은 `type`/`roomId` 계약을 이 화면의 탭 이동에도 재사용).
>
> 2026-08-09 신설(사용자 확정) — 홈 상단 알림 벨이 지금은 알림 **설정**(`/mypage/notifications`)으로 직행하는데, 실제 발송 이력을 보여주는 화면이 없다. 이 문서가 그 화면(알림 내역)을 새로 정의한다.

## 목적
사용자가 그동안 받은 알림 7종(콕 찌르기·일정 전날·일정 당일·방 멤버 입장·방 멤버 퇴장·담당 투두 추가·자료 분석 결과)을 시간순 목록으로 보여주고, 항목을 탭하면 관련 화면으로 이동하게 한다. 안읽은 알림은 배지로 표시한다.

## 하지 않을 것
- **알림 수신 설정(on/off)** — 여전히 `specs/0012-설정.md`(`/mypage/notifications`)가 다룬다. 이 문서는 "받은 알림의 기록"만 다룬다. 두 화면은 별개이고, 마이페이지 [계정] 그룹의 "알림 설정" 메뉴는 그대로 유지된다(진입 경로만 유지, 변경 없음).
- **실시간 인앱 토스트/배너** — 앱을 켜 놓은 상태에서 알림이 오는 순간 화면에 뜨는 연출은 다루지 않는다(FCM 포그라운드 처리는 기존 `fcm_service.dart` 영역).
- **알림별 삭제/전체 지우기** — 이번 범위는 조회·읽음 처리까지만. 삭제 UI가 필요해지면 별도 확정.
- **푸시 `data` 페이로드 자체의 구현** — `docs/backend/notification-deeplink-handoff.md`(서버 C항목, 아직 미반영)와는 별개다. 이 화면의 탭 이동은 **DB에 저장된 `type`/`roomId`를 그대로 써서** 이동하므로, 푸시 `data`가 아직 없어도(=탭 시 앱만 열리는 상태여도) 이 화면 안에서의 탭 이동은 정상 동작한다.
- **알림 종류 확장(마감임박 등)** — 지금 발송되는 7종만 기록한다. 새 알림 종류가 생기면 그때 이 문서를 갱신한다.

**`type` → 이동 매핑**(`notification_router.dart`와 완전히 동일, 신규 매핑 없음):
- `POKE`, `ASSIGNED_TODO_ADDED` → 투두 탭(`/todos`)
- `SCHEDULE_DAY_BEFORE`, `SCHEDULE_DDAY` → 일정 탭(`/schedule`)
- `ROOM_MEMBER_JOINED`, `ROOM_MEMBER_LEFT` → 멤버·초대(`/mypage/members`)
- `ARCHIVE_ANALYSIS_DONE` → 모아보기 탭(`/archive`)

## 데이터 (엔티티 연결)

### 신규 테이블 `notifications` (`V24`)
발송 시점에 실제로 쓰인 제목·본문 문자열을 **그대로 스냅샷 저장**한다 — 나중에 `docs/backend/notification-handoff.md`(B. 문구 교체)가 반영돼도 과거 기록은 그때 실제로 보낸 문구를 유지해야 하므로(문구 재구성이 아니라 사실 기록), 구조화된 필드 대신 완성된 title/body를 그대로 저장한다.

```
notifications
  id            BIGSERIAL PK
  user_id       VARCHAR(128) NOT NULL REFERENCES users(id) ON DELETE CASCADE   -- 수신자(개인 기록이라 탈퇴 시 함께 삭제, V9 계정 삭제 cascade 패턴과 동일)
  type          VARCHAR(32)  NOT NULL   -- PushType 이름 그대로(POKE, SCHEDULE_DAY_BEFORE, ...) — 딥링크 계약과 값 공유
  room_id       BIGINT       NULL REFERENCES rooms(id) ON DELETE SET NULL      -- 방이 나중에 삭제돼도 알림 기록 자체는 남긴다(SET NULL)
  title         VARCHAR(255) NOT NULL
  body          VARCHAR(255) NOT NULL
  read_at       TIMESTAMP    NULL       -- null = 안읽음
  created_at    TIMESTAMP    NOT NULL DEFAULT now()

INDEX (user_id, created_at DESC)              -- 목록 조회
INDEX (user_id) WHERE read_at IS NULL         -- 안읽음 배지 카운트
```

**기록 지점**: `global.notification.PushNotifier`의 `notify`/`notifyEach` 딱 한 곳 — 개별 채널 게이트(`isEnabled`)를 통과한 시점에 이 테이블에도 행을 쓴다. **FCM 발송 성공 여부와 무관하게 기록한다**(토큰이 없거나 FCM 호출이 실패해도 기록은 남는다) — 앱 내 알림 내역은 "그 이벤트가 나에게 알림 대상이었다"는 기록이지 "기기에 실제로 푸시가 도착했다"는 기록이 아니다. 이렇게 하면 부수 효과로 **FCM 자체가 실패해도 사용자는 앱 안에서는 그 알림을 확인할 수 있다**(현재 "자료 분석 알림이 안 온다"는 QA 이슈의 우회 확인 경로도 된다 — 근본 원인은 별도 조사 대상).

### API
| 엔드포인트 | 설명 |
|---|---|
| `GET /me/notifications?limit=100` | 최신순 목록. 응답 `[{id, type, title, body, roomId, read, createdAt}]`. 페이지네이션 없음(다른 목록 API들과 동일하게 상한 개수만 — `home-activity-feed.md`의 20건 캡과 같은 패턴), 90일 보존이라 무한정 쌓이지 않는다. |
| `GET /me/notifications/unread-count` | `{count}` — 홈 벨 배지 전용, 목록 전체를 안 불러오고 가볍게 조회. |
| `POST /me/notifications/read-all` | 204. 안읽은 행 전부 `read_at = now()`. S-41 진입 시 호출. |

### 보존 정책
90일 지난 행은 매일 배치로 삭제(`character-handoff.md`의 `UserActivityRetentionScheduler`와 동일 패턴 — `NotificationRetentionScheduler` 신설, 04:00 KST 등 기존 배치와 겹치지 않는 시간대 권장). 알림은 "그때 놓친 걸 확인하는 용도"라 무한 보관할 이유가 적고, 협업 캐릭터 활동 로그와 같은 근거로 기간을 맞춘다.

## 성공(인수) 기준
- [ ] 홈 상단 알림 벨을 탭하면 알림 내역(S-41)이 열린다(알림 설정이 아니라).
- [ ] 알림 내역에는 그동안 발송 대상이었던 알림 7종이 최신순으로 보인다.
- [ ] 안읽은 알림이 있으면 홈 벨에 배지가 보이고, 알림 내역 화면에 진입하는 순간 배지가 사라진다(전부 읽음 처리).
- [ ] 항목을 탭하면 그 알림 종류에 맞는 화면(투두/일정/멤버/모아보기)으로 이동하고, 알림이 속한 방과 현재 방이 다르면 먼저 그 방으로 전환한다.
- [ ] 알림이 하나도 없으면 빈 상태 문구가 보인다.
- [ ] 마이페이지 [계정] 그룹의 "알림 설정" 메뉴는 그대로 알림 설정 화면으로 간다(회귀 없음).

## 상태 (로딩·빈·에러)
- **로딩**: 마이페이지 하위 화면들과 동일하게 중앙 스피너(`PastRoomsScreen` 패턴).
- **빈 상태**: "아직 받은 알림이 없어요" — 아이콘 없이 텍스트만(다른 빈 상태들과 톤 통일).
- **에러**: 목록 로드 실패 시 재시도 버튼(`_ErrorState` 공유 위젯 재사용).
- **당겨서 새로고침**: 마이페이지·프로필과 동일하게 `RefreshIndicator` 지원.

## 엣지케이스
- **연결된 방이 이미 없어짐(나감·삭제)**: `roomId`가 null이거나(방이 삭제돼 `SET NULL`된 경우) 현재 세션의 방 목록에 없으면, 탭해도 이동하지 않고 "이미 없어진 방이에요" 스낵바만 띄운다 — 없는 방으로 전환을 시도해 에러 화면으로 빠지는 것을 막는다.
- **알림 설정을 꺼둔 채널의 과거 기록**: 나중에 채널을 꺼도 그 전에 쌓인 기록은 그대로 보인다(껐다고 과거 기록을 지우지 않음) — 게이트는 "새로 기록할지"만 결정한다.
- **90일 넘은 기록**: 배치가 삭제한 뒤에는 목록에서 사라진다. 사용자가 삭제를 요청한 게 아니라 자동 정책이므로 별도 안내 없음(다른 자동 보존 정책과 동일 — 예: `character-handoff.md`의 `user_activity`).
- **FCM 발송은 실패했지만 기록은 있는 경우**: 위 "기록 지점" 절 참고 — 정상 동작이다(기록≠발송 성공). 사용자가 "푸시는 못 받았는데 내역엔 있다"고 느낄 수 있어, 이 화면이 "알림 설정 검토용 대체 확인 채널"로도 기능한다는 점을 QA 시 참고.
- **탈퇴 유저가 남긴 알림의 표시**: 알림 자체는 수신자(`user_id`) 기준이라 발신자가 누군지 별도로 저장하지 않는다(문구 스냅샷에 닉네임이 이미 문자열로 박혀 있다) — 발신자 탈퇴 여부와 무관하게 문구는 그대로 보인다.
