# 0014 — 외부 공유 등록 (S-25-D, 네이티브)

> 관련 스펙: `specs/0010-아카이브-탭.md`(S-25-C 인앱 등록 — 이 문서는 그 병렬 진입 경로), `specs/0001-architecture.md`(공유 익스텐션 컴포넌트·인증 흐름), `specs/0002-data-model.md`(`archive_items` — 이 기능으로 `crawl_status` 컬럼 추가 및 `body_text` nullable 완화됨), `specs/0003-navigation.md`(go_router 라우트 트리 밖의 네이티브 화면).
>
> 2026-07-27: `full_spec.md` §7(아카이브 탭) 작성 시점에는 없던 신규 요구사항 — 원본 IA에 이 진입 경로 언급이 없으므로 이 문서가 처음으로 정의한다. 사용자 확정(2026-07-27): 인증은 앱과 공유 화면이 토큰을 공유, 공유 시트에서 방부터 선택 가능, 콘텐츠는 URL/텍스트만, 크롤링·AI 태깅은 등록 후 백그라운드 처리(공유 화면은 등록 확인 즉시 닫힘).
>
> **구현 범위(2026-07-31 갱신)**: Android 네이티브(Kotlin `ShareActivity`)와 iOS 네이티브 Share Extension(Swift)을 모두 구현했다. iOS는 `app/ios/ShareExtension` 별도 타깃으로 URL/텍스트 수신·방/폴더 선택·등록 API 호출을 처리하고, 메인 Flutter 앱과 `App Group` Keychain을 통해 Firebase ID 토큰을 공유한다. Xcode 시뮬레이터 빌드·Swift XCTest까지 검증했으며, Apple Developer 프로비저닝이 필요한 실기기 공유 시트 E2E는 아직 남아 있다.

## 목적
외부 앱·브라우저의 OS 공유 기능("공유하기")으로 전달된 링크/텍스트를 앱을 열지 않고 네이티브 공유 익스텐션에서 방·폴더를 선택해 바로 아카이브에 등록한다. 크롤링과 AI 자동 태깅은 서버가 등록 이후 비동기로 처리하고, 결과는 아카이브 탭에서 기존 폴링 정책(`specs/0001-architecture.md` "실시간 = 폴링")으로 확인한다.

## 하지 않을 것
- **이미지 등 파일 공유 수용** — URL/텍스트만 받는다(`specs/0010-아카이브-탭.md`의 "파일 업로드 범위 밖" 결정과 동일 선상, 2026-07-27 재확인).
- **크롤링·AI 태깅 완료까지 익스텐션이 대기** — 등록(서버에 PENDING 레코드 생성) 확인 즉시 닫힌다. S-25-C의 "태깅 로딩 스피너"는 이 화면엔 없다.
- **공유 시트에서 방 신규 생성** — 방은 기존 ACTIVE 방 중 선택만 가능(방 생성은 앱에서). ⚠️ **폴더는 예외로 공유 시트에서 바로 만들 수 있다**(2026-08-04 개정 QA — 기존 "폴더도 신규 생성 안 함, 없으면 종료" 결정을 뒤집음). 폴더가 0개면 종료하지 않고 새 폴더 이름을 입력받아 만들고, 폴더가 있어도 선택지에 "＋ 새 폴더 만들기"를 함께 준다. 서버는 기존 `POST /rooms/{roomId}/archive/folders`(`{name}`, 최대 20자) 재사용 — 서버 변경 없음.
- **로그인/회원가입** — 이미 로그인된 세션의 토큰만 재사용한다. 미로그인·토큰 갱신 실패는 엣지케이스로 안내 후 종료.
- **Android에서 Flutter 엔진 재사용** — iOS는 익스텐션 메모리 제한(약 120MB) 때문에 네이티브가 필수이고, Android도 플랫폼 일관성을 위해 동일하게 순수 네이티브(Kotlin) Activity로 구현한다(iOS만 네이티브로 하고 Android는 Flutter로 하는 비대칭 구성은 채택하지 않음).
- **크롤링 실패 시 재시도 UI** — `specs/OPEN.md`에 기록, 이번 범위 밖.
- **유튜브·인스타 링크도 이 경로로 들어온다** *(2026-08-03)* — 두 앱의 공유 시트가 넘기는 URL에는 추적 파라미터가 붙지만(`?igsh=…`·`?si=…`) 크롤러가 경로만 보므로 그대로 등록된다. 사이트별 처리 상세는 `specs/0010-아카이브-탭.md`. ⚠️ **인스타는 여기(비동기)에서 외부 호출이 최대 4회**라 `ArchiveCrawlProcessor`의 기존 트랜잭션 부채가 커졌다 — `specs/OPEN.md`의 해당 항목 참고.

## 진입·화면 (S-xx 연결)
| 화면 | 형태 | 진입 경로 | 비고 |
|---|---|---|---|
| S-25-D 외부 공유 등록 | 네이티브 공유 익스텐션(iOS Share Extension) / 네이티브 Activity(Android `ACTION_SEND` intent-filter) | OS 공유 시트에서 앱 선택 | `specs/0003-navigation.md`의 go_router 트리 밖 — Flutter `Navigator`가 아닌 별도 네이티브 타깃/화면 |

내부 단계(별도 S-xx 없이 이 문서 안에서만 관리되는 하위 스텝):
1. **공유 수신** — URL 또는 텍스트 1건을 OS로부터 받는다.
2. **방 선택** — 로그인 세션으로 `GET /rooms`(기존 엔드포인트 재사용)를 호출해 ACTIVE 방 목록을 보여준다. 방이 1개뿐이면 자동 선택하고 이 단계를 건너뛴다.
3. **폴더 선택/생성 → 즉시 등록** *(2026-08-09 개정, 사용자 확정)*: 선택된 방의 폴더 목록(`GET /rooms/{roomId}/archive/folders` — 0010에서 신설된 폴더 목록 API 재사용)을 보여준다. 목록에는 항상 **"＋ 새 폴더 만들기"** 선택지가 함께 있다. **기존 폴더를 고르거나 새 폴더를 만드는 그 순간, 공유된 값(URL 또는 텍스트)을 제목으로 그대로 써서 즉시 서버에 `PENDING` 레코드를 생성한다** — 별도 제목 입력·확인 단계가 없다(기존 4단계 "등록 확인" 폐지). 새 폴더는 이름 입력 화면에서 만든 뒤(`POST .../archive/folders`) 곧바로 같은 방식으로 등록된다. **폴더가 0개면 종료하지 않고 곧장 새 폴더 이름 입력 화면**을 띄운다(2026-08-04 개정 QA). 이름은 최대 20자(서버 검증과 동일). ⚠️ 새 폴더 선택지를 항상 노출하기 위해 폴더가 1개여도 자동 선택하지 않고 목록을 보여준다(기존 "1개면 자동 스킵" 동작 변경). 등록 성공 시 토스트 후 화면이 닫히고, 실패하면 인라인 에러 + "다시 시도"(같은 방·폴더로 재호출)만 보여준다(제목 재입력 없음).

> **Android 구현 노트(2026-07-27, 2026-08-09 갱신)**: 위 단계들은 화면을 여러 개 쌓는 대신 **단일 `ShareActivity` 안에서 `AlertDialog`를 순차적으로 띄우는 방식**으로 구현했다(방 선택 → 폴더 선택 → [폴더 확정 시 자동 등록]). 공유 타겟 액티비티의 경량 패턴이며, 아래 "액션·전이"의 "네이티브 push"는 Android에서는 이 다이얼로그 시퀀스를 의미한다. **2026-08-09**: 각 다이얼로그가 기본 `setItems`/`AlertDialog` 대신 `ShareTokens`(design.md·tokens.dart 미러링)로 스타일링한 커스텀 뷰(surfaceSoft 리스트 행, primary 강조 버튼)를 쓴다 — 제목 입력 다이얼로그(구 `showRegisterDialog`)는 제거됐다.
>
> **iOS 구현 노트(2026-07-31, 2026-08-09 갱신)**: `ShareViewController`가 프로그래매틱 UIKit 화면으로 동일한 단계를 처리한다. 메인 앱의 Dart `ShareAuthSync`가 `idTokenChanges()` 때마다 네이티브 MethodChannel로 최신 Firebase ID 토큰을 전달하고, `AppDelegate`가 `$(AppIdentifierPrefix)group.com.nomara.modi` Keychain access group에 저장한다. 확장은 Flutter 엔진을 띄우지 않고 Keychain 토큰과 App Group UserDefaults의 API 주소만 읽는다. UI 색·간격·라운드는 `specs/design.md`/`tokens.dart` 값을 현재 수동 미러링한다(`UIConstants`). **2026-08-09**: 방·폴더 선택과 새 폴더 이름 입력을 시스템 `UIAlertController` 대신 커스텀 `contentStack` 리스트 화면으로 교체했고, 폴더 확정 즉시 등록하도록 제목 입력 폼(구 `showRegisterForm`)을 제거했다.

## 공유 값에서 URL 뽑기 — 양 네이티브 공통 규칙 (2026-08-05 신설)

🔴 **여기가 이 규칙의 단일 진실이다.** 네이티브가 2종이라 공유 코드가 없어 Android(`SharedTextUrl.kt`)와 iOS(`ShareContent.swift`)에 **각각** 구현돼 있다. 한쪽을 고치면 다른 쪽과 이 문서를 함께 고친다.

**왜 필요한가**: 앱들은 URL 만 보내지 않는다. 네이버 지도 공유 버튼이 보내는 값은 이렇다 —

```
[네이버지도] 돼지통 역삼2호점 서울 강남구 역삼로 123 https://naver.me/52aGF4S5
```

원래 두 플랫폼 모두 **문자열 전체가 URL 인지**를 봤다(Android `Patterns.WEB_URL…matches()`, iOS `URL(string:)?.host`). 위 값은 거짓이라 링크가 아니라 **텍스트로 등록됐고 크롤링이 아예 안 일어났다** — 2026-08-05 실측(로컬 DB id 60): `crawl_status=DONE · url=(빈칸) · title=[네이버지도] 돼지통…`.

규칙:

| | |
|---|---|
| 패턴 | `https?://[^\s\p{Z}\x0B<>"']+` (대소문자 무시) — **공백·꺾쇠·따옴표에서 끊는다** |
| 여러 개면 | **마지막 것**을 쓴다. 앱들은 설명을 앞에, 링크를 끝에 붙인다 |
| 뒤 문장부호 | `. , ; : ! ? ) ] } " ' »` 를 걷어낸다. **단 닫는 괄호 `) ] }` 는 짝이 맞으면 URL 의 일부로 본다** |
| 스킴 없으면 | 뽑지 않는다. `naver.me/x` 는 링크로 안 본다 — 서버로 보낼 값은 http(s) 로 확정한다 |
| 하나도 없으면 | 지금까지처럼 **텍스트로 등록**한다(동작 불변) |
| 남은 설명 텍스트 | **버린다.** 제목은 크롤링한 값이 더 깔끔하고(네이버는 `PlaceDetailBase.name` = `돼지통 역삼2호점`), 그게 기존 URL 공유의 동작과도 같다. ⚠️ **되돌릴 수 없는 손실이다** — 이 화면에는 본문 입력칸이 없고 편집 가능한 것은 제목뿐이라, `회의 정리 … 참고 https://x.test/y` 같은 메모형 공유는 메모가 통째로 사라진다. 아래 QA 항목에서 사용자 확인을 받는다 |

**닫는 괄호의 짝 세기** — 무조건 자르면 정상 URL 이 조용히 망가진다. 등록 뒤에는 앱에서 `url` 을 고칠 수단이 아예 없어(상세 화면 편집은 제목·태그·폴더·핀뿐) **영구 손상**이다.

```
https://en.wikipedia.org/wiki/Cat_(disambiguation)   '(' 1 · ')' 1 → 짝이 맞다  → 그대로
여기(https://naver.me/52aGF4S5)                       '(' 0 · ')' 1 → 짝이 없다 → 잘라낸다
```

🔴 **패턴에 `\p{Z}\x0B` 가 붙어 있는 이유 — 이게 없으면 두 플랫폼이 실제로 갈린다.** 자바/코틀린의 `\s` 는 **ASCII 전용**(` \t\n\x0B\f\r`)이고 iOS 가 쓰는 ICU 의 `\s` 는 `[\t\n\f\r\p{Z}]` 다. 그대로 두면 **전각 공백(U+3000)·NBSP(U+00A0)** 에서 안드로이드만 안 끊긴다 — 한국어 공유 텍스트에 실제로 나오는 문자다. 2026-08-05 리뷰가 실측으로 잡았다: `링크　https://naver.me/x　끝` → 안드로이드는 `https://naver.me/x끝` 을 뽑아 **등록이 FAILED**, iOS 는 성공. 양쪽에 `\p{Z}`(공백 계열 전부)와 `\x0B`(ICU 의 `\s` 에는 없다)를 명시하면 두 집합이 **정확히 같아진다**(공백 U+0020 은 `\p{Z}` 의 Zs 에 들어 있다).

⚠️ **한 군데만 플랫폼이 다르다**: 값 **전체**가 http(s) 아닌 URL 일 때(`file:///…`·`ftp://…`) iOS 는 `nil` 을 돌려줘 다음 provider 로 넘어간다 — provider 가 로컬 파일을 건네줄 수 있는 건 iOS 뿐이고, 파일 경로를 텍스트인 척 등록하지 않기 위한 기존 계약이다. Android 에는 그 경로가 없어 텍스트로 등록된다.

⚠️ **iOS 는 `NSDataDetector(.link)` 를 쓰지 않는다.** 애플의 휴리스틱이라 Android 정규식과 어디서 갈리는지 열거도 테스트도 안 된다(스킴 없는 링크·이메일까지 잡고 괄호 균형을 자체 규칙으로 맞춘다). **두 네이티브가 글자 단위로 같은 규칙**을 갖는 쪽을 택했다.

> 🔴 **2026-08-06 — 서버가 스스로 다시 긁는다. 앱은 한 줄도 안 바뀐다.**
> 실패의 상당수가 "안 되는 링크"가 아니라 **"타이밍이 나빴던 링크"** 였다. 운영 EC2 IP 가 인스타에서 소프트 블록되는데
> 그 차단은 10~20분이면 풀린다(운영 DB 실측: 12:45 실패 → 12:54 성공 / 15:18 실패 → 15:36 성공).
> 그런데도 그 순간 들어온 공유가 영구 `FAILED` 로 확정돼 **인스타 19건 중 11건(58%)** 이 "분석 실패"로 남았다.
>
> 이제 다시 해볼 만한 실패(상대의 일시적 상태 — 소프트 블록, 연결·읽기 타임아웃)는 `FAILED` 로 굳히지 않고
> **`PENDING` 을 유지한 채 20분 뒤로 예약**한다(`ArchiveItem.scheduleCrawlRetry`). 5분마다 도는 배치가
> 기한이 된 것을 다시 긁는다(`ArchiveCrawlRetryScheduler`). 최초 1회 + 재시도 3회로 **최악 60분 안에** 확정된다.
>
> **이 위 표는 그대로 유효하다** — 재시도 중인 항목은 `PENDING` 이라 앱이 이미 "분석 중"으로 그린다(`CrawlStatusBadge`).
> 사용자는 링크를 공유해두고 나중에 모아보기에서 보므로 20분 지연을 알아채지 못한다. **앱 계약이 안 바뀐 것이 이 설계의 장점이다.**
>
> ⚠️ **대상 자체가 원인인 실패는 여전히 즉시 `FAILED`** 다 — 비공개·삭제된 게시물, 알아볼 수 없는 주소, 본문 없는 페이지.
> 다시 걸어도 같은 답이 오고 외부 사이트만 더 때린다. 어디까지가 "다시 해볼 만한"인지는 `CrawlExceptionRetryableTest` 가 못 박는다.

> **본문 자리 문구는 `crawl_status`로 갈라야 한다** *(2026-08-01, 실사용 버그로 발견)*. 처음 구현은 `bodyText ?? "자료를 분석하고 있어요…"` 한 줄이라
> **`FAILED` 항목에도 기다리라는 안내가 떴다** — "분석 실패" 배지와 한 화면에서 모순됐고, 영원히 바뀌지 않는 상태인데 사용자는 기다리게 됐다.
> 실패 문구가 **재시도를 암시하지 않는 이유**: 재크롤링은 위에 적힌 대로 범위 밖이라,
> 없는 기능을 가리키는 문구("다시 시도해 주세요")를 쓰면 안 된다. `DONE`인데 본문이 없는 조합은 안내 문구를 지어내지 않고 영역을 비운다
> (요약이 없으면 영역 자체를 만들지 않는 규칙과 같은 방향 — `specs/0010`의 "S-25-B AI 요약 표시" 항목).
>
> **두 안내 문구 모두 본문과 다른 스타일이다** — `body-small` + `color.muted`(`design.md` §7 상태 패턴). 본문과 같은 스타일로 두면
> "링크 내용을 가져오지 못했어요"가 그 링크의 첫 문장인지 시스템 안내인지 구분되지 않는다. 이 화면이 서로 모순되는 말을 한 것이 애초의 버그였으므로,
> **어느 글자가 자료의 것이고 어느 글자가 앱의 것인지**도 함께 분명히 한다.
>
> ⚠️ **크롤링 실패 자체는 버그가 아니다.** agoda처럼 클라이언트 렌더링(SPA) 사이트는 서버가 받은 HTML에 글자가 0자라
> `JsoupUrlCrawler`가 "본문을 찾을 수 없는 링크예요"로 떨어진다(2026-08-01 실측: HTTP 200 · 315KB · `og:title` 없음 · 텍스트 0자).
> 네이버 블로그 PC 주소와 같은 경로다.

## 엣지케이스
- **ID 토큰 만료(Android, 구현 중 보정)**: 최초 스펙은 refresh 토큰으로 별도 REST 갱신을 직접 구현한다고 가정했으나, Firebase Auth Android SDK의 `currentUser.getIdToken(false)`가 만료 시 자동으로 갱신을 처리하므로(SDK 내부 동작, `forceRefresh` 플래그와 무관) 별도 REST 호출 코드를 작성하지 않았다. SDK 갱신 자체가 실패하면(예: refresh 토큰도 만료) `getIdToken` 호출이 실패하고 `ShareActivity`는 "앱을 열어 로그인해주세요"로 안내 후 종료한다(로컬 큐잉 없음 — 사용자가 앱에서 재로그인 후 다시 공유해야 한다).
- **공유 텍스트가 URL 형식이 아닌 임의 텍스트**: 그대로 `title`/`body_text` 후보로 받는다(0010과 동일하게 URL 여부만으로 `url` 필드 채움 여부를 가르고, 내용 자체는 검증하지 않는다).
- **크롤링 실패(대상 사이트 차단/타임아웃)**: **2026-08-06 개정** — 서버가 20분 간격으로 3번까지 스스로 다시 긁는다(위 상태 표의 개정 주석 참고).
  그래도 안 되면 `FAILED`로 남고 사용자가 입력한 제목만 남는다. **앱에서 누르는** 재시도는 여전히 범위 밖(`specs/OPEN.md` 기록) —
  자동 재시도가 대부분을 흡수하므로 급하지 않다.
- **동일 링크 반복 공유**: 중복 검사 없음 — 매번 새 항목 생성(0010도 중복 방지 언급 없음, 동일 정책 유지).
- **iOS 익스텐션 시간 제한(약 30초)**: 등록 API 응답만 기다리므로(크롤링은 비동기) 여유 있게 끝난다는 전제 — 그래도 타임아웃 시 "등록하지 못했어요" 처리.
- **네이티브 UI의 디자인 토큰 동기화**: `specs/design.md`는 Dart(`tokens.dart`) 기준이라 네이티브(Swift/Kotlin) 쪽엔 자동 반영되지 않는다. Android는 시스템 기본 다이얼로그를 사용하고, iOS `ShareViewController`는 현재 색·간격·라운드 값을 수동 미러링한다. 토큰 변경 시 iOS 네이티브 파일도 함께 갱신한다.
