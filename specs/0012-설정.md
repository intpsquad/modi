## 데이터 (엔티티 연결)
- **프로필 수정**: `users.nickname`, `users.profile_image` — `GET`/`PATCH /me/profile`(`UserService`, 로 구현 완료). PATCH는 upsert(유저 행 없으면 생성), GET은 없으면 404. 사진 업로드는 `POST /me/profile/photo/upload-url`로 MinIO presigned PUT URL을 발급받아 클라이언트가 직접 업로드한 뒤, 그 결과 공개 URL을 `profileImage`로 PATCH — 상세는 `specs/0001-architecture.md` MinIO 절.
- **알림 설정**: `notification_settings` — `GET`/`PUT /me/notification-settings` — `all_enabled`, `poke_enabled`, `knock_enabled`, `schedule_day_before_enabled`, `schedule_dday_enabled`, `room_member_joined_enabled`, `room_member_left_enabled`, `assigned_todo_added_enabled`. 설정 행이 없는 유저는 GET에서 전부 `true`인 기본값을 반환(행 생성 안 함), PUT이 upsert한다. **"전체 알림" 동작(2026-08-08 변경)**: 전체 알림은 개별을 막는 마스터가 아니라 **개별(화면 노출 7종)이 모두 켜졌는지를 나타내는 파생 스위치**다 — 켜면 개별 전부 ON·끄면 전부 OFF로 일괄 세팅하고, **개별은 전체와 무관하게 각각 토글 가능**(전체 꺼도 골라 받기). `all_enabled`는 저장 시 "개별 전체 ON 여부"로 맞추는 파생값이며 **발송 게이트로 쓰지 않는다** — 실제 발송은 개별 flag만으로 판정한다(서버 `PushNotifier`에서 `allEnabled &&` 게이트 제거, `docs/backend/notification-all-toggle-handoff.md`). 이전(마스터 차단) 동작은 폐기.
- **S-40-A 현재 방 설정**: `rooms`의 `name`/`cover_image`/`goal`/`goal_detail`/`start_date`/`end_date` — S-10(`CreateRoomRequest`)과 동일 검증 규칙을 재사용하는 `PATCH /rooms/{roomId}` 구현 완료. 앱이 기존값을 모두 프리필할 수 있도록 `GET /rooms`의 `RoomSummaryResponse`도 `goalDetail`/`coverImage`를 반환한다.
  - **대표 이미지 업로드**: 설정 화면에서 갤러리/카메라로 대표 이미지를 변경한다(기존값 프리필). **2단계** — `POST /rooms/cover-image`(multipart)로 URL을 받아 `PATCH /rooms/{id}`의 `coverImage`로 전달. 이전에 저장이 `coverImage: null`을 하드코딩하던 버그를 함께 제거했다. 계약: `docs/api/room-cover-image.md`.
- **S-40-B 멤버 관리**: 개인 진행률이 포함된 `GET /rooms/{roomId}/members/progress`를 재사용한다. 화면 최초 진입은 `GET /rooms/{roomId}/invite-code`로 유효한 현재 코드를 조회하고, 만료된 경우에만 새 코드를 만든다. 사용자가 명시적으로 재발급하면 `POST /rooms/{roomId}/invite-code/reissue`가 기존 코드를 즉시 무효화한다. 공유 선택지는 S-10-A와 같은 `InviteShareData`(방 id·이름·대표 이미지·초대 코드)를 사용한다. 카카오는 `FeedTemplate`(대표 이미지·방 이름·"참여하기"), 인스타는 코드 복사 후 `instagram://`, 더보기는 `share_plus` OS Native Share Sheet다.
- **S-40-C 방 나가기**: `room_members` 행 삭제 후 남은 멤버 수를 카운트 → 0이면 같은 트랜잭션에서 `rooms`도 즉시 하드 삭제(CASCADE로 하위 전체 정리, 0002 확정). 삭제 타이밍은 2026-07-30 확정: **즉시 하드 삭제**(유예 기간·배치 삭제 없음) — `specs/OPEN.md` 확정 기록 참고.
- **S-40-D 종료된 방**: `GET /rooms/past` — 내가 속했던 방 중 `status=ENDED`인 것만, 이름/기간/최종완료율(방 전체 todos 기준, 0002 "방 진행률" 계산값). "종료 요약"(최다 기여 멤버·아카이브 하이라이트 등, 0002 "종료 요약" 계산값)은 S-05 상세 화면 전용이라 이 목록에는 포함하지 않는다 — `specs/0013-종료된-방.md` 참고.
- **회원 탈퇴** *(2026-08-03 확정, `UserService.withdraw`)*: `DELETE /me`, 204 응답. 소속된 모든 방을 먼저 자동으로 나가고(방마다 기존 `RoomService.leaveRoom` 재사용 — 마지막 멤버면 그 방도 하드 삭제), `users` 행을 지운다. 나머지는 DB 레벨 FK로 정리된다(`V9__account_deletion_cascades.sql`) — 좋아요·콕찌르기·투두담당·알림설정은 `ON DELETE CASCADE`(개인 활동 기록이라 함께 삭제), 다른 멤버가 남은 방의 `archive_items.created_by`는 `ON DELETE SET NULL`(공유 콘텐츠라 자료는 남기고 작성자만 지움). Firebase 인증 계정도 `FirebaseAuth.deleteUser`로 완전히 삭제하되, DB 정리가 끝난 뒤 별도로 시도한다 — DB 삭제가 실패하면 재시도할 수 있어야 하고, 반대로 Firebase 쪽만 실패해도 앱 데이터는 이미 정리됐으니 탈퇴는 완료로 본다(로그만 남김).
